# ORX 実装計画（IMPLEMENTATION_PLAN）

> 本計画は PROJECT.md（WHAT/WHY）と CLAUDE.md（HOW）から導出した作業分解である。
> 矛盾時は PROJECT.md → CLAUDE.md → 本計画 の順で優先。
> 進捗は `docs/PROGRESS.md` で追跡し、各セッション開始時に最初の未完了項目から再開する。

## 0. 読み方と運用

- 作業項目IDは `P{n}-{連番}`。タグは `P{phase}/C{component}/H{hypothesis}`。共有基盤は `C*`、特定仮説に紐づかない評価装置は `H*`（全仮説の検証を支える装置の意）と表記する。
- 各フェーズ内の項目は**依存順**（CLAUDE.md §3 の依存方向 `common ← {sim,skills,business,perception} ← anchoring ← kg ← agent ← exp`）に並べてある。上から順に実装する。
- 各作業単位の前に `P{n}/H{n}: <一文宣言>` を行い、単位完了ごとに関連テスト→全テストを実行する（レポジトリを赤のまま放置しない）。
- **フェーズゲート**（ハードゲート）: (a) 全テスト緑、(b) §9 完了基準の測定値を PROGRESS.md に記録、(c) フェーズデモコマンドの出力を提示、(d) CLAUDE.md §7 規約でコミット。未達なら次フェーズに進まない。
- §5 の設計判断 D1–D4 は推奨案を明記した。**本計画の承認をもって推奨案の承認とみなす**（個別に上書き指定があればそれに従う）。

## 9. テスト戦略（必須4種＋不変条件）

1. **単体**: `tests/` が `src/` をミラー。各公開関数に最低1テスト。
2. **CQ回帰**（`tests/cq`）: P0でフレームワーク、各フェーズで語彙追加と同時に拡充。
3. **SHACL検証**: 全書込パスの適合（来歴・確信度・時刻欠落の拒否を含む）。
4. **リプレイ同一性**: 記録→リプレイで指標バイト一致（P0ゲート、以後常時）。
5. **不変条件テスト**: import-linter契約（実装済み: oracle/ORコア分離・依存方向）、`owl:sameAs` 直書き検出（ASTまたはグラフ検査）、エージェントの真値直アクセス不在、劣化ノブのsim側限定、IRI文字列連結検出。
6. **オフライン保証**: 全テストは `stub`/`cache` モードのみ。新規プロンプト記録は明示的 `--record` 実行のみ。

## 10. 設計判断（D1–D4）— 推奨付き

### D2: 忠実度の対象述語集合 v0（P0で必要）★計画承認と同時に確定したい
- **推奨（v0最小集合）**: `rdf:type` / `orx-st:inZone`（位置の離散セル; 連続位置はRMSEで別評価）/ `orx-st:on`・`orx-st:contains` / `orx:hasIdentifier` / 同一性対応（`orx:anchoredTo` 経由の真値物体ID対応→同一性F1）。
- 代替: 最初から状態述語・能力述語まで含む拡張集合 — 早期はノイズ源が増え、忠実度の感度が落ちるため不採用。P2で業務述語、P3で能力統計を**追加**する（oracle と CQ を同時更新）。

### D3: 来歴・確信度・時刻のRDF表現（P0で必要)★同上
- **推奨（a）クレーム単位 named graph**: 各主張をクレームIDのnamed graphに入れ、メタグラフでグラフIRIに来歴(prov拡張)・確信度・観測時刻・有効期間を付与。SPARQLは `GRAPH` で来歴横断、SHACLはメタグラフを検証。pyoxigraph・pySHACL双方と相性が良い。
- 代替: (b) RDF-star — pySHACLの対応が弱く検証パスが崩れる。(c) n-aryクレームノード — SHACLは楽だがクエリが冗長で世界状態の読み出しが重い。

### D1: アンカリングスコア関数（P1開始時に最終確認）
- **推奨（a）ゲート付きlog-odds融合**: 時空間整合の硬いゲート（同時刻同座標にあり得るか）を通過したペアに対し、知覚署名（埋め込みcos類似）・記号ID一致・位置整合の重み付きlog-oddsを加算、θ_merge/θ_split で確率的マージ/分裂。重み・閾値はコンフィグ（劣化掃引で感度分析可能）。
- 代替: (b) シム生成ペアで較正したロジスティック回帰 — 真値由来の学習データがORコアに漏れる管理が複雑。(c) Dempster-Shafer — 表現力は高いが監査性が下がる。いずれもP1の結果次第で再訪可。

### D4: T1タスク実行器（P1、C7不在期間の扱い）
- **推奨**: P1では決定的スクリプト実行器（世界グラフへのSPARQL→スキル指示の固定方針）でT1を駆動し、LLM計画はP2のC7から。同一性解決の効果をLLMの揺らぎと交絡させないため。
- 代替: C7を前倒し — 交絡と費用が増えるため不採用。

## 11. 性能・コスト・安全ガードレール

- 性能予算: 記録≤実時間2倍（60秒エピソード）、リプレイ≤30秒/条件。P0-13で知覚パスを実測し予算比を報告。
- ライブAPI: テストと `orx demo` からは呼ばない。初回ライブ記録（P2）前にトークン見積を提示。>50エピソードの新規記録・〜1Mトークン超のプロンプト集合は事前承認。
- 秘匿情報をコード・設定・ログ・フィクスチャに書かない。`data/` 配下の削除はしない。
- 軽微な設計決定は `docs/design/decisions.md`（ADR）に記録済み・随時追記。

## 12. リスクと順序の注意（PROJECT.md §13 の実装観点への落とし込み）

- **評価装置を最初に建てる**: P0でoracle・replayを先に固め、以後の全機能はこの装置で測ってから進める。
- macOS描画/MPS問題はP0-10/P0-12/P0-13で最初に潰す（リスク登録簿対応）。
- pyoxigraphストアはテストフィクスチャで毎回生成（状態漏れ防止）。
- 新述語追加時は CQ と oracle 述語リストの両方を同時更新（P2-03 で仕組み化: 同期テスト）。
- グラフ肥大は有効期限付き主張＋陳腐化率監視で常時把握（P0-15/P4-02）。
