# CLAUDE.md — ORX 開発作業規約

このリポジトリは Ontological Robotics 検証プロジェクト（ORX）。**プロジェクトの目的・仮説・スコープ・完了基準はすべて `PROJECT.md` が定義する。** 本書は開発作業の規約のみを定める。矛盾時は PROJECT.md が優先。

機能追加・設計判断の前に必ず PROJECT.md の該当箇所（仮説H1–H7、不変条件§5.2、スコープ§4）を確認すること。**どの仮説にも紐づかない機能は実装しない。** 迷ったら実装せずユーザーに確認する。

---

## 1. 環境とセットアップ

- macOS / Apple Silicon 専用。**CUDA前提のコード・依存を絶対に追加しない**（PyTorchはMPS、フォールバックはCPU）。
- Python 3.11+、依存管理は `uv` のみ。`pip install` を直接実行しない。

```bash
uv sync                      # 環境構築（pyproject.toml が唯一の依存定義）
uv run pytest -q             # 全テスト
uv run pytest tests/cq -q    # コンピテンシー質問（CQ）回帰のみ
uv run orx --help            # CLI エントリポイント（typer）
```

- 新規依存の追加は `uv add <pkg>` を使い、追加理由をコミットメッセージに書く。重量級依存（ROS、CUDA系、分散系）は PROJECT.md §4.2 / §10 によりスコープ外。
- `OPENAI_API_KEY` は環境変数からのみ読む。**コード・設定ファイル・ログ・テストフィクスチャにキーや応答原文中の秘匿情報を書き込まない。** `.env` は gitignore 済みであることを変更しない。

## 2. MuJoCo / macOS の既知の注意点

- 対話ビューア起動は `mjpython` が必要（`uv run mjpython script.py`）。**ヘッドレス実験では一切ビューアを使わない。**
- レンダリングはオフスクリーン `mujoco.Renderer`（224px、CLIP入力に整合）。EGL/GLFWのLinux向け環境変数設定をコピペしない。
- 物理ステップと知覚・推論は非同期分離（目安: 物理500Hz / 知覚2Hz）。**シムのステップループ内でグラフクエリ・LLM呼び出し・ディスクI/Oを行わない**（PROJECT.md 不変条件4）。
- CLIP は `open_clip_torch` を `mps` デバイスで。初回ロードが遅いためプロセス内シングルトンで保持する。

## 3. アーキテクチャ規律（コードレビューの判定基準）

PROJECT.md §5.2 の不変条件をコードで強制する。違反するPR/変更は完了とみなさない。

1. **生データ（画像・点群・生メッセージ）を世界グラフ（C6）に書かない。** `data/runs/` に保存し、グラフには参照IRIと蒸留結果のみ。
2. **世界グラフへの全書込は来歴・確信度・時刻付き。** 書込APIは `orx.kg` の公開関数のみを使い、pyoxigraph への直接INSERTを他モジュールから行わない。SHACL検証はテストで担保。
3. **同一性は `orx:anchoredTo`（確信度付き）。`owl:sameAs` を直書きしない。** マージ・分裂が可逆である設計を壊さない。
4. **`orx.oracle`（C8）は sim 真値と評価のみに依存し、ORコア（anchoring/kg/agent）を import しない。** 逆方向（ORコア→oracle）の import も禁止。評価の独立性が最重要。
5. **エージェント（C7）はツール経由でのみ世界を知る。** ベースライン B0/B1 の実装でも、シム真値への直接アクセスは書かない（真値に触れてよいのは oracle と実験ランナーの採点部のみ）。
6. **全実験コードは記録（C9 replay）を経由する。** 記録なしで結果だけ出すスクリプトを作らない。

モジュール依存方向: `common ← {sim, skills, business, perception} ← anchoring ← kg ← agent ← exp`、`oracle` と `replay` は横断だが上記4・6に従う。循環 import を作らない。

## 4. コーディング規約

- 型ヒント必須。全メッセージ・設定・能力契約は pydantic モデル（`src/orx/common/schemas.py` 起点）で定義し、dict の素通しをしない。
- **例外: ベンダースキーマ（`configs/robots/`）は意図的に異質・非統一**。これは実験変数なので「きれいに正規化」しないこと。正規化はリフティング層（`ontology/mappings/`）の仕事。
- 乱数は `orx.common.seeding` から派生注入。`random.seed()` / `np.random.seed()` をモジュール内で直接呼ばない。
- ログは structlog 形式（JSON lines）で `data/runs/<run_id>/` に。print デバッグを残さない。
- IRI生成は `orx.common.iri` の関数のみ。文字列連結でIRIを作らない。
- オントロジー（TTL）編集時は必ず `uv run pytest tests/cq -q` でCQ回帰を確認。CQに答えられなくなる語彙変更はリグレッション（PROJECT.md §6）。
- docstring は日本語可。識別子（変数・関数・クラス）は英語。

## 5. テスト方針

- 新規モジュールには単体テストを同時に作成。テストは `tests/` でソース構成をミラーする。
- 必須テスト種別: ①単体、②CQ回帰（`tests/cq`）、③SHACL検証（書込パスの適合）、④**リプレイ同一性**（記録→リプレイで指標が一致すること。P0完了基準）。
- LLM・埋め込みを呼ぶテストは**必ずキャッシュフィクスチャを使う**（`data/cache/llm`）。CIや再実行で実APIを叩くテストを書かない。新規プロンプトの初回記録は明示的な `--record` フラグ付き実行のみ。
- テストでの真値アクセスは oracle 経由のヘルパに限定。

## 6. 実験の実行規約

- 実験はすべてコンフィグ駆動（`configs/experiments/`）。条件変更のためにコードを書き換えない。
- 実行は `uv run orx exp run <config>`。出力（`reports/`, `data/runs/`）には構成ハッシュ・シード・OpenAIモデルスナップショット名が自動で焼き込まれることを壊さない。
- OpenAI 呼び出し: モデルはコンフィグのスナップショット名固定、temperature 0、全応答キャッシュ。**モデル名のハードコード禁止。**
- 比較実験は「記録 → 反実仮想リプレイ → 対比較」を基本単位とする（PROJECT.md §7.2）。物理シムの回し直しで条件比較をしない。
- コスト注意: 新規記録セッションの前に概算トークン量を見積もり、大量実行（>50エピソードの新規記録）はユーザーに確認してから行う。

## 7. Git / 変更管理

- ブランチ: `phase{N}/<topic>`（例 `phase0/oracle-fidelity`）。main へは全テスト緑で。
- コミットメッセージ: 1行目に要約、本文に**関連する仮説ID・コンポーネントID・フェーズ**（例 `H2/C5/P1`）を記す。依存追加時は理由を明記。
- `data/`（runs, cache）はコミットしない。`ontology/`・`configs/`・`tasks/` は実験の再現に必須なので必ずコミットする。
- PROJECT.md の変更（スコープ・仮説・完了基準）は Claude Code が独断で行わない。提案としてユーザーに提示する。

## 8. Claude Code への行動指針

- **やる**: 不変条件・依存方向の自己チェック、テスト同時作成、CQ回帰の実行、小さな単位での実装と検証、Phaseの完了基準（PROJECT.md §9）への進捗の明示。
- **やらない**: スコープ外機能（実機・ROS・分散・フォトリアル）の追加、評価コード（oracle）とORコアの結合、キャッシュを迂回した実API乱用、`data/` 内成果物の削除、PROJECT.md の無断改訂。
- 実装前に対象 Phase と仮説を一文で宣言してから着手する（例: 「P1/H2: anchoring の時空間整合スコアを実装」）。曖昧な要求は実装前に質問する。
- 長時間タスク（記録セッション、掃引実験）は途中経過をログで確認可能にし、中断・再開可能に作る。

## 9. よくある落とし穴（先回りメモ）

- `mujoco.Renderer` を物理ステップごとに生成しない（生成は1回、`update_scene`→`render` を回す）。
- MPS で未対応の演算が CPU フォールバックして激遅になることがある。知覚パイプラインの初回実装時に1バッチのプロファイルを取り、目標（PROJECT.md §10 性能予算）と比較する。
- pyoxigraph はプロセス内ストア。テスト間で状態が漏れないよう、ストアはフィクスチャで毎回生成する。
- SPARQL の述語集合は忠実度評価（oracle）と合意が必要。新述語を増やしたら `tasks/competency_questions/` と oracle の対象述語リストの両方を更新する。
- 劣化ノブはシム側（C1/C4）にのみ実装する。アンカリングや kg 側に「ノイズを知っている」コードを書くと実験が無効になる。
