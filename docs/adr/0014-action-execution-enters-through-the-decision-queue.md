# ADR-0014: アクション実行は判断キューを通して入る

- 状態: 採択
- 日付: 2026-10-04
- 関連: ADR-0012（learning-worker が人の判断を適用する）、ADR-0011（要求は作業キューに置く）、設計書 §9.2（実行フロー）、§9.3（安全ガード）、M8-21

## 文脈

M5 でアクション層（意味契約・前提検証・承認・実行・補償）を実装したが、**運用経路に入口が無かった**。
`build_command_handler` が知っているコマンドは `resolve_discrepancy` と `curate_concept` の 2 つで、
アクションを実行する経路はライブラリとテストの中にしか無い（所見 89）。

設計書 §9.2 の実行フローは「前提検証 → 承認 → 実行 → `ActionEvent` → `Expectation` 生成」であり、
**`riskClass ≥ medium` は承認必須**（§9.3）。つまり実行は**人の判断を待つ**。

## 決定

**アクション実行は `learning_decisions` の作業キューに `kind='action'` として入り、learning-worker が適用する。**

- API に `/commands/execute_action` を足し、`ExecutionCommand` を検証してキューに積む（適用しない）。
- learning-worker が引いて、設計書 §9.2 の順序どおりに適用する。
- 期待は `expectations` 表に書く（M8-18 / M8-20）。

## 選択肢

### A. 判断キュー（採択）

利点:

- **冪等が既にある。** `decision_id` + `ON CONFLICT DO NOTHING` で、UI の再送・HTTP の再試行で
  同じアクションが 2 回実行されることを表の側で防ぐ。**アクションの二重実行はこの基盤で最悪の
  失敗である**（業務システムを 2 回変える）。これを自前で作り直す理由が無い。
- **人の判断という形が同じ。** ADR-0012 が作ったのは「人の判断を受け取って適用する」経路で、
  承認付きの実行はその最も素直な例である。承認は判断であり、実行はその適用である。
- **「受け付けた」と「適用した」を分ける形が維持される。** HTTP の応答で実行の成否を返さない
  ——前提検証とレート制限で落ちることがあり、それを人に伝えるのは画面の仕事である。
- サービスもワーカーも増えない。

欠点:

- learning-worker の名前が「学習」なのに、アクションを実行する。**役目は「人の判断の適用」で
  一貫しているが、名前が狭い。**
- 表の `kind` の CHECK を広げる DDL が要る（alembic 0008）。

### B. 専用のワーカー（action-worker）を足す

利点: 名前が仕事に合う。実行だけを止める運用ができる。

欠点: **6 番目のワーカーになる。** 冪等・キュー・周期実行・疎通検査を作り直すことになり、
ADR-0012 と同じ構造が 2 つできる。CLAUDE.md の「便利だからとサービスを増やす」に抵触する。
実行を止めたいなら、契約の `riskClass` か承認方針で止めるのが設計の筋である。

### C. API が同期で実行する

利点: 実装が短い。結果がすぐ返る。

欠点: **却下。** (1) 前提検証は信念クエリを伴い、実行は業務システムへの書き戻しを伴う
——HTTP のタイムアウトが人の承認を失わせる。(2) 冪等を自前で持つ必要がある。(3) API の
プロセスが業務システムを変える経路を持つことになり、読み取り中心の層に実行の責任が混ざる。

### D. イベントログに流す

**却下。** ADR-0011 と同じ理由である——実行の要求は**主張ではない**ので `EventEnvelope` に
席が無い（様相格子のどれにも当たらない）。所見 62 / 63 の繰り返し。

## 帰結

### 良くなること

- 設計書 §9.2 の順序が production のコードで 1 箇所に揃う（これまで G5 のテストの中にあった）。
- 二重実行を表が防ぐ。
- 既定では**何も実行できない**: 契約レジストリ・信念の読み出し・期待の書き込みを運用者が明示
  配線するまで、適用は失敗として記録される（ADR-0012 の書き戻しと同じ形）。

### 悪くなること・残る穴

- **レート制限はワーカーのメモリにある。** `RateLimitState` はプロセス内で、再起動で消える。
  冪等の鍵は「同じ判断」を防ぐが、「別の判断で短時間に 2 回」は再起動後に通る。表に移すのは
  別タスク（§9.3 の「同一対象への短時間の反復」を永続化する必要がある）。
- **`ActionEvent` をイベントログに出していない。** トピックが無く、`ActionEvent` は
  `EventEnvelope` ではない（dataclass）。いまは `Expectation.action_event` が ID を保持する
  だけで、実行の記録そのものは表に残らない。
- **前提の信念は「いまの信念」で見る。** 人が承認した時点の信念ではない。承認から適用までに
  状態が変われば前提は落ちる——これは**正しい**（古い前提で実行しない）が、人には
  「承認したのに実行されなかった」と見える。画面に理由を返す経路が要る。

## 不変条件への影響

- 不変条件 4（イベントの冪等）: 影響なし。キューはイベントログではない。
- 不変条件 2（追記専用）: 影響なし。表は作業項目で、アサーションではない。
- **不変条件 3**: 期待は信念ではないので様相を持たない。実行が生む信念（効果の観測）は
  別経路で `observed` / `inferred` として入る。

## オントロジー版

変更なし（0.5.0）。`ActionEvent` / `Expectation` は既に定義済み。

## 未決

1. **レート制限の永続化。** 表に移すか、Redis を入れずに済む形（`expectations` の
   `created_at` を数える）で足りるか。
2. **`ActionEvent` の永続化。** 表か、`EventEnvelope` に載せる写像を作るか。後者なら
   「実行は主張か」という問いに答える必要がある（実行したことは観測可能な事実である、と
   読めば `observed` の席がある）。
3. **補償の入口。** 実行と同じ形でキューに入れるか、実行の失敗から自動で走らせるか。
   自動は危険（補償自体が業務システムを変える）なので、いまは入口を作っていない。
