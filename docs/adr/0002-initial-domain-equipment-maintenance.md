# ADR-0002: 初期ドメインを「製造・設備保全」とする

- 日付: 2026-10-03
- 状態: 採択
- 触る層: ontology / bridge / reasoning（検証シナリオ全般）

## 文脈

設計書 §1.2 は初期候補ドメインを 4 つ挙げる（製造・設備保全 / 倉庫・在庫 / 施設・エネルギー / 物流ヤード）。設計原則 P6「最小オントロジー・観測駆動成長」と §16 Phase 0 の「1 ドメイン・20〜30 型」に従い、初期は 1 ドメインに絞る必要がある。`docs/TASK.md` §7-2 の未決事項。

この選択は `ontology/domain/` の内容、`SynthWorld`（M2-01）の題材、そして G3・G5 のゲート検証シナリオを規定する。

## 選択肢

1. **製造・設備保全** — 物理: 振動・電流・温度、PLC 状態。業務: CMMS 作業指示、MES 稼働実績、保全計画。狙う不一致: 状態不一致（稼働/停止）、未実施作業。
2. 倉庫・在庫 — 狙う不一致: 存在不一致（幽霊在庫）、同一性不一致。
3. 施設・エネルギー — 狙う不一致: 規範不一致（契約超過）。
4. 物流ヤード — 狙う不一致: 時間不一致、SLA 違反予兆。

## 決定

選択肢 1「製造・設備保全」を採る。理由:

- **設計書 §14 のワークドエグザンプル（ライン 3 のポンプ P-101）が同ドメインである。** §14 は観測→三源統合→不一致起票→確認→予測→アクション→Expectation 検証までの全系列を具体値付きで記述しており、これを**そのまま G3・G5 のゲート検証シナリオに使える**（TASK.md M3-09 / M5-09）。他ドメインを選ぶと検証シナリオを自前で設計し直すことになり、設計書との対応検証が弱くなる。
- **事象計算の例（§3.8）が設備保全で書かれている。** `Running` / `UnderMaintenance` / `StartCmd` / `StopCmd` / `Fault` / `MaintStart` / `MaintEnd` と遅延分布まで提示済みで、`ontology/process/*.lp` の初期実装がそのまま起こせる。
- **WM のモデル族が明確。** §4.2 は設備・プロセス領域に Koopman 作用素モデルを推奨し、「Koopman 固有関数がフルーエントに対応づけやすく、整合残差が解釈しやすい」とする。M4-02 の koopman 実装と初期ドメインが一致する。
- **多変量時系列のみで成立する。** 映像を必要としないため、不変条件 9（生映像を永続化しない、人の映るデータを扱わない）との摩擦が最小。倉庫・物流ヤードはカメラ前提で、同一性束縛（M2-07）に外観埋め込みが絡み、開発初期の負荷が高い。
- §14 は予備品在庫（SKU-77）の存在不一致にも触れており、**倉庫ドメインの要素（類型 1）を最小限で併せ持てる**。五類型の検出規則（M3-05）の検証に必要な多様性は確保できる。

## 影響

- 不変条件への影響: 9（生映像の非永続化）への摩擦を最小化する方向に働く。他は影響なし。
- オントロジー版: `ontology/domain/` の初版内容を規定する（MINOR 加法の起点）。再接地不要（既存データなし）。
- テスト・運用への影響: `SynthWorld` は振動・電流・PLC 状態に相当する多変量時系列を生成する。G3 は類型 1〜3 の注入シナリオ、G5 は §14 の完走を検収条件とする。
- 第 2 ドメイン（倉庫・在庫）の追加は Phase 3 相当（§16）。追加時に「新概念追加が既存プローブを壊さない」（非機能要求の拡張性）を検証する機会になる。

## 未決

なし。第 2 ドメイン追加の時期は M6 以降に別 ADR で判断する。
