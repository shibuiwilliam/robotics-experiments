# ADR-0010: 不一致の起票イベントは拠点トピックに出し、中央集約は別の仕事にする

- 日付: 2026-10-04
- 状態: 採択
- 触る層: reasoning（起票通知）、services（照合ワーカーの配線）

## 文脈

照合ワーカー（`services/reconcile_worker.py`）は五類型の不一致を検出するが、**出力先が
設定されていなかった**（`TODO(question)`。`docs/PROGRESS.md` 既知の制約）。`sink` が
`None` のまま起動するため、検出しても誰にも届かない。

トピックは `make seed` の時点で両方作られている（`scripts/topics.py`）。

| トピック | `scripts/topics.py` の説明 |
|---|---|
| `<site>.reasoning.discrepancy` | 照合エンジンが起票した不一致（五類型）とその状態遷移 |
| `central.reasoning.discrepancy` | 拠点横断で集約した不一致（中央の照合・監査用） |

`.claude/rules/knowledge.md` のトピック命名の例には `central.reasoning.discrepancy` が
挙がっており、「中央に出すのが既定か」が読み取りづらい。関連: 設計書 §6.1（トピック命名と
実体単位の順序）、§8.2（不一致のライフサイクル）。

## 選択肢

1. **拠点トピック（`<site>.reasoning.discrepancy`）に出す。中央集約は転送役の仕事にする。**
   - 利点: 検出器は自拠点のことだけを知っていればよい（1 ワーカー 1 拠点という配置と一致）。
     拠点が自分の記録を持つので、中央が止まっていても起票は失われない。`scripts/topics.py`
     自身が中央トピックを「拠点横断で**集約した**不一致」と定義しているので、検出器の
     出力先として読むのは定義と食い違う。
   - 欠点: 全拠点を見たい購読者（中央の監査）が転送役を必要とする。転送役は未実装。
2. 中央トピック（`central.reasoning.discrepancy`）に直接出す。
   - 利点: 転送役が要らない。全拠点を 1 トピックで購読できる。
   - 欠点: 各拠点のワーカーが中央のブローカーに到達できることを要求する。拠点に自分の記録が
     残らないので、中央への送信に失敗した起票は拠点側から再現できない。中央トピックの定義
     （集約済み）と中身（生の検出結果）が食い違う。
3. 両方に出す。
   - 利点: どちらの購読者も満たせる。
   - 欠点: **同じ不一致が 2 つの `event_id` を持つ。** 不変条件 4 の冪等性は `event_id` に
     依るので、2 本流すと「同じ不一致なのに別のイベント」になり、下流が二重に数える。
     同じ `event_id` で 2 トピックに流すと、冪等記録（`processed_events`）が
     `(consumer_group, event_id)` を鍵にしているため片方しか処理されない。どちらにしても壊れる。

## 決定

**選択肢 1。** 既定は拠点トピックで、`SBP_REASONING_DISCREPANCY_SCOPE=central` で中央に
切り替えられるようにする（拠点別の運用もありうる、という元の未決を設定で残す）。

**両方に出す案は採らない。** 冪等性が `event_id` で定義されているので、同じ不一致を 2 本
流す形はこの基盤では表現できない。中央集約が必要になったら**転送役**（拠点トピックを購読して
中央トピックに再発行し、`causation_id` に元の `event_id` を入れる）を作る——そうすれば
「中央のイベントは拠点のイベントから導かれた」ことが来歴に出る。

## 影響

- **不変条件 3**: 起票イベントの様相は `inferred`（五類型の検出器は規則である）。
- **不変条件 4**: 1 つの不一致に対してイベントは 1 本。`correlation_id` に
  `discrepancy_id` を入れ、状態遷移の通知が同じ不一致に紐づくようにする。
- **不変条件 1**: `ontology_version` は不一致自身が持っているものを使う（検出時の版）。
- **オントロジー版**: 変更なし（0.5.0）。イベント型は `<core#Discrepancy>/kind<n>` と
  `vocab` から組み立てる（新しい個体を置かない）。
- **テスト**: 単体で封筒の中身（様相・確信度・主体の選び方・型 IRI）を固定。統合で
  照合ワーカー → Redpanda → 購読までを通す。

## 未決

- **不一致の永続化と API 露出が無い。** イベントは通知であって不一致そのものではない
  （`EventEnvelope` に全体を入れる場所が無い）。UI には不一致キューの型とロジックがあるが、
  API 側に資源が無く、知識グラフにも投影表にも不一致が書かれていない。**通知だけでは UI が
  中身を読めない**ので、別タスク（M8-12）として起票した。
- **複数実体が関わる不一致の主体**。パーティションキーは 1 つしか選べないので、類型 4
  （同一性）では辞書順で最小の実体を主体にし、残りは順序保証の単位から外れる。先頭ではなく
  最小にしたのは、同じ不一致が再検出されたときに同じパーティションへ行くためである。
- **転送役**（拠点 → 中央）は未実装。必要になった時点で作る。
