# ADR-0034: 主体は仮名の IRI で持ち、消去は対応表の行で行う（H-05 の方針案）

- 日付: 2026-11-08
- 状態: **提案**（法務の確認待ち。採択するまで実装しない）
- 触る層: api（resolver の契約）、knowledge（対応表の置き場）。コードの変更は採択後

## 文脈

不変条件 2（追記専用）と個人データの消去要求は直接ぶつかる。生映像・音声は持たず（不変条件 9）、`Person` の個人識別はプローブで型レベルに禁止している。
**残るのは「人の判断」に付く主体の IRI** で、コードで確かめた置き場は次の通り:

| 置き場 | 内容 | 追記専用か |
|---|---|---|
| イベントログ（Redpanda）・知識グラフ | 人の回答の主張の `RecordEvidence.source = answered_by`（`integration/human_answer.py`）。監査隔離の単位でもある | はい |
| `learning_decisions`（alembic 0005） | `decided_by` の列と、`payload` の JSON に `resolved_by` / `approved_by` など | 行は書いたら変えない運用 |
| `discrepancies` | `assignee_role`（ロールで持つ。個人を指さない） | — |

主体の IRI が個人を直接指す（氏名・社員番号・メールを含む）形だと、消去要求のたびに追記専用の層を書き換えることになり、as-of の再構成も壊れる。

## 決定（提案）

1. **`principal_resolver` が返す主体 IRI は、個人を直接指さない仮名（不透明な識別子）にする。** 例 `urn:sbp:principal:<ランダム>`。氏名・社員番号・メールを IRI に含めない。契約として ADR-0029 の resolver に課す。
2. **仮名と本人の対応は基盤の外**（IdP、または基盤の追記専用の外に置く削除可能な表）に持つ。基盤の追記専用の層は仮名しか知らない。
3. **消去要求は対応表の行を消すことで満たす。** 文は消さない（不変条件 2 を守る）。消した後は、その仮名が誰かを基盤の内側からは辿れない。as-of の再構成は仮名のまま保たれる。
4. 人の判断の `note`（自由記述）に個人情報を書かない運用とし、UI に注意を出す。自由記述の消去は 3 の対象外なので、必要なら別途 ADR。

## 未決（法務に確認する）

- 仮名化（対応表の削除）で消去要求を満たすと見なせるか。満たさないなら、文の物理削除の例外手順を ADR で別に定める（不変条件 2 の例外なので MAJOR 相当の扱い）。
- 仮名が行動の履歴から再識別されうる場合（小さな拠点で担当者が 1 人など）の扱い。
- 保存期間の定め（対応表を一定期間後に自動で消すか）。

## 結果（採択した場合）

- 実装は resolver の契約テスト（仮名の形式の検査）と対応表の追加が中心で、追記専用の層は変えない。H-25 の残り（主体の認可・`decision_id`）と同じ時に設計するのが手戻りが少ない。
- 本 ADR は H-05 の回答ではなく**方針案**である。H-05 は法務の確認が出るまで「待ち」のまま残す。
