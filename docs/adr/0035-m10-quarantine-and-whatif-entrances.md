# ADR-0035: M10 を起こし、隔離キューと What-if の入口を作る（H-27 の (3)(4)）。隔離キューは「写像で落ちた入力」から書く

- 日付: 2026-11-08
- 状態: 採択（人の指示: H-27 のうち SHACL 隔離の運用経路と What-if の入口を実施、2026-11-08）
- 触る層: knowledge（隔離キュー）、integration（取込の失敗行を返す）、services（ingest-worker・learning-worker）、api、reasoning（What-if。ADR-0036）

## 文脈

H-27 の (3) 隔離キュー（`quarantine` 表は alembic 0001 にあるが書く者がいない）と (4) What-if の入口（`run_scenario` を呼ぶ者がいない）。(1) 同一性束縛と (2) LLM の入口は
知覚の契約・費用の方針が要るので扱わない。

隔離キューについて、コードで確かめた事実:

1. **構造が壊れた入力は、いま捨てられている。** 取込の写像に失敗した行は `IngestResult.failed` に `(外部 ID, 理由)` として積まれるだけで生の行を持たず、ログに警告が出る。
   取込のカーソルは読んだ行の `updated_at` の最大まで進むので、**失敗した行は二度と読まれない**。資産台帳の行も、型がオントロジーに無い行は `skipped` に入るだけで、
   台帳は毎周期全行を読むのに人の目に触れない。設計書 §3.9 / §5.7 の「構造制約違反は隔離キュー（登録しない、人が確認、捨てない）」と食い違う。
2. **`pyshacl` による検証（`validate_graph`）を運用の入力に当てられる形が、いまは無い。** `AssetShape` は `locatedIn` を必須にするが、資産台帳に場所の列は無い
   （場所は空間束縛が出す確率的述語で、運用経路が無い）。台帳の行を `AssetShape` に当てると全件が違反になり、取込が止まる。形状を緩めるのはオントロジーの変更（MAJOR 相当）で、
   運用に入口を作る目的の外にある。
3. 隔離表は `event_id uuid PRIMARY KEY` で、拠点の列が無い。

## 決定

1. **M10「運用の入口 その 2」を起こす。** M9 の目的と G9 は変えない。タスク: M10-01 隔離キュー（書く側）、M10-02 隔離の読み書き（GraphQL `quarantine` とコマンド）、
   M10-03 What-if のジョブ、M10-04 What-if の読み出し（GraphQL `scenarios`）、M10-05 G10。
2. **隔離キューへ書くのは、取込が構造の理由で受け付けなかった入力**とする: 写像に失敗した行、型がオントロジーに無い台帳の行。
   理由は人が読める文で残し、**生の行（`fields`）をそのまま `payload` に保存する**（捨てない）。SHACL の `ValidationOutcome` からも積める入口
   （`QuarantineStore.add_outcome`）を同じ型で用意するが、**運用の入力に当てる形状の評価は将来**（`AssetShape` に場所が要る件が空間束縛の運用経路に依存するため。H-27 に残す）。
3. **冪等。** 隔離の識別子 `event_id` は `(拠点, 情報源, 表, 外部 ID, 理由)` の uuid5。台帳は毎周期全行を読むので、同じ行が同じ理由で落ち続けても 1 行にしかならない。
   理由が変われば別の行になる。確認済み（`reviewed_at`）の行は、同じ理由で再び落ちても開き直さない（人が「対応不要」と決めたものを再び積まない）。
4. **表に拠点の列を足す**（alembic 0015、`site`）。既存行は無い（書く者がいなかった）。
5. **隔離は信念ではなく作業項目**（ADR-0011 / 0013 と同じ扱い）。推定の入力にしない（不変条件 6）。確認の記録は `learning_decisions` の新しい種類 `quarantine_review` として
   コマンドで積み、learning-worker が `reviewed_at` / `resolution` を埋める（受け付けと適用を分ける。ADR-0012）。確認者は ADR-0029 の主体の束縛に従う（`reviewed_by`）。

## 結果

- 取込の失敗行は、人が確認できる形で残る。`mapping_violations` 指標は従来どおり。
- 隔離の読み出しは ABAC の拠点分離に従う。`payload` は業務システムの生の行で個人情報を含みうる——H-05（消去要求）の対象に入る場所として ADR-0034 に追記する。
- **レビューで足した扱い**（独立レビュー、2026-11-08）: 壊れた入力が書き込みを壊さないよう、NUL 文字・NaN を無害化してから保存する。理由の文は入力値を含めず
  （型と場所だけ。`describe_failure`）、識別子を安定させる。同じ理由で未確認の行は生の入力を最新に更新する。健全な行は隔離の失敗より先に送る。
  **台帳の行が壊れた編集を受けても、その資産の直前の有効な文は閉じない**（隔離に積み、人が確認する）。
- **隔離の行は、元の行が直っても自動では解消しない**（確認は人が行う。自動解消は元の行の再取込と突き合わせる設計が要るので別途）。
- 限界: 形状（SHACL）の評価を運用の入力に当てていない。UI に隔離の画面は作らない（GraphQL とコマンドまで）。

## 未決

- `AssetShape` の `locatedIn` を台帳の列として持つか、形状側を緩めるか（ontology の判断。空間束縛の運用経路と合わせて決める）。
