# ADR-0011: 追加観測の要求は作業キュー（投影表）に持ち、観測手段は設定で割り当てる

- 日付: 2026-10-04
- 状態: 採択
- 触る層: knowledge（作業キュー）、reasoning（観測手段のレジストリ）、services（スケジューラの配線）、infra（alembic）

## 文脈

エピステミック・スケジューラのワーカー（`services/scheduler_worker.py`）は、要求 →
クエリの変換と効用による選択まで実装されているが、**要求の供給元**と**観測手段の割り当て**が
`TODO(question)` として残っていた（`docs/PROGRESS.md` 既知の制約）。供給元が無いため
`step()` は常に 0 を返す。

関連: 設計書 §8.7（エピステミック・スケジューラ）、§6.1（イベントエンベロープ）、
§3.5（様相）、M3-06（解決 → 学習信号。`LearningArtifacts.observation_requests` が要求を出す）。

## 選択肢

### 問い 1: `ObservationRequest` をどこから取るか

1. **イベントログに載せる**（`<site>.reasoning.request` トピックを足す）。
   - 利点: 順序と冪等（`event_id`）が付く。来歴が残る。
   - 欠点: **`EventEnvelope` に載らない。** 封筒は「誰かの主張」を運ぶ形で、`modality` ＋
     `belief` ＋ `evidence` を必須に持つ。追加観測の要求は**主張ではなく指令**であり、
     様相格子（`observed` / `inferred` / `predicted` / `planned` / `normative` /
     `hypothetical`）に**席が無い**。「これを測ってほしい」はどれでもない。載せるには封筒に
     任意ペイロードを足すことになり、「全イベントが同じ形」という §6.1 の前提が崩れる。
     要求が持つ `reason` と `utility` を入れる場所も無い。
2. **投影表（作業キュー）に持つ。**
   - 利点: 「まだ満たされていない要求の一覧」を引くのが自然（これは状態への問い合わせで、
     イベントの再生では答えられない）。既存の `quarantine`（SHACL 違反の隔離キュー）が
     **同じ形の作業キュー**で、`reviewed_at` / `resolution` を直接更新する先例がある。
   - 欠点: 「状態はイベントの投影」という原則からの逸脱に見える。
   - MacBook 上のコスト: 表 1 つ。行数は未解決の不一致の数に比例し、小さい。
3. メモリに持つ（現状）。
   - 欠点: 再起動で消える。選ばなかった要求を次の周期で再評価する設計（劣モジュラの前提）が
     再起動で壊れる。

### 問い 2: 観測手段（`ObservationMeans`）をどう割り当てるか

1. **設定ファイル（`observation/<domain>.yaml`）で持つ。**
   - 利点: `reliability/*.yaml`（情報源信頼性、M1-06）と `value/*.yaml`（業務価値）と同じ形。
     コストと信頼度は**拠点が持つ計測器の性質**であり、拠点ごとに違う。
   - 欠点: 設定ファイルが 1 つ増える。トップレベルのディレクトリも 1 つ増える。
2. オントロジーに `Probe` × `FluentType` の対応として持つ。
   - 利点: 「どの概念をどう確かめられるか」は世界についての知識に見える。
   - 欠点: **コストと信頼度が拠点ごとに違う**ので、オントロジーに置くと拠点差をオントロジー版
     で管理することになる——拠点が計測器を更新するたびにオントロジーの版が上がり、再接地の
     判定に無関係な変更が混ざる。さらに、プローブ（センサ由来）と概念の対応は
     **すでに `ProbeSpec.grounds` が持っている**ので二重管理になる。
3. コードに直書きする（現状の `_DEFAULT_MEANS`）。
   - 欠点: 閾値・設定は `Settings` か設定ファイルに置く規約（CLAUDE.md）に反する。

## 決定

- **問い 1 は選択肢 2**（作業キュー）。決定的なのは「要求は主張ではない」ことである——
  様相格子に席が無いものをイベントログに載せる形は、この基盤では表現できない。
  「状態はイベントの投影」の原則は**世界の状態**（信念）についての規律であり、作業キューは
  世界の状態ではない。既存の `quarantine` がこの区別の先例になっている。
- **問い 2 は選択肢 1**（設定）。`observation/<domain>.yaml` に
  `フルーエント IRI → 手段（kind / reliability / cost）` を持ち、宣言の無いフルーエントには
  既定手段を当てる。**既定を「人への質問」にしない**——頻度上限に当たって何も選ばれない周期が
  出るうえ、「自動で人に聞き続ける」挙動は望ましくない。

## 影響

- **不変条件 2（追記専用）**: 作業キューはアサーションではないので対象外。ただし
  **要求の行は消さない**——`satisfied_at` を立てるだけにして、「観測を要求したが満たされな
  かった」履歴が残るようにする（`quarantine` と同じ扱い）。
- **不変条件 3**: 観測の結果は `observed` のイベントとして別経路で戻る。要求自体は様相を
  持たない（イベントではないため）。
- **不変条件 5**: フルーエント IRI は設定ファイルに書くが、コードには書かない。設定の
  キーがオントロジーに存在することを読み込み時に検査する。
- **オントロジー版**: 変更なし（0.5.0）。新しい概念を置かない（置かないことがこの ADR の
  決定の一部である）。
- **テスト**: 単体で手段レジストリ（既定の当て方・未知 IRI の拒否）とキューの意味
  （未充足だけを返す・行を消さない）、統合で実物の Postgres に対するキューの往復。
- **構成**: トップレベルに `observation/` が増える。`docs/development-rules.md` §3 の
  ディレクトリ表を同じコミットで更新する。

## 未決

- **要求を書く側が未実装。** 要求は照合の解決（`apply_resolution`）から出るが、解決は人の
  判断であり、その入力経路を受けて実行するワーカーは M8-08 である。本 ADR はキューの形と
  読み出し側（スケジューラ）を決めるところまでで、**書き込み側は M8-08 が繋ぐ**。
- **要求が満たされたことの判定**。`observed` のイベントが戻ってきたとき、どの要求を満たした
  かを突き合わせる処理は未実装。`mark_satisfied` の API は用意するが、呼ぶ側は未定である
  （実体 × フルーエント × 区間の重なりで判定するのが素直だが、「どれだけ測れば満たされたか」は
  手段によって違う）。
- **手段を複数持つフルーエント**。いまは 1 フルーエント 1 手段。複数の手段から選ぶ
  （安い順に試す、など）のはスケジューラの選択に手段次元を足すことになり、別の設計が必要。
