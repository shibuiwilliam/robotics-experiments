# ADR-0021: UI のアクション承認は、契約の要約と判断の状態を読む 2 つの資源で支え、失敗は理由をそのまま返す

- 日付: 2026-11-08
- 状態: 採択
- 触る層: knowledge（判断の履歴）、api（読み出し資源）、apps/ui（承認フォーム）

## 文脈

`/commands/execute_action` は M8-21（ADR-0014）で立ったが、**UI に押す場所が無い**。人が不一致キューから
「緊急点検を起票する」などを承認する画面と、落ちた理由（前提未達・レート制限）を人に返す経路が要る。
ADR-0014 の「悪くなること」に「承認したのに実行されなかったと人には見える。画面に理由を返す経路が要る」とある。

確かめた事実:

1. UI は**どのアクションを提案できるか**を知る手段が無い。契約（`actions/*.yaml`）は API から読めない。
2. 判断（`learning_decisions`）の**状態を読む資源が無い**。表には `applied_at` / `failed_at` / `error` /
   `artifacts` があるが、API が返さない。
3. **失敗した判断は自動では再試行されない。** `mark_failed` が `failed_at` を立て、`pending` は
   `failed_at IS NULL` の行だけを引く。`_apply_action` の docstring は「再試行の対象になる」と書いていたが実装と
   食い違っていた（所見 127）。前提は後で満たされうるが、再実行は人が**新しい判断として再投入**する。
4. 実行要求 `ExecutionCommand` の `target`・`severity`・`correlation_id` は不一致から埋められる。

## 選択肢

### 問い 1: UI が提案できるアクションをどう知るか

1. **契約の要約を返す GraphQL 資源 `actionTypes`。** 契約（`ActionRegistry`）から、アクション型・対象型・リスク級・
   承認の要否と条件・面ごとの前提の説明・期待する効果と期限・補償・レート制限を返す。契約が唯一の正で、UI に写さない。
2. UI に契約の写しを持たせる。契約を変えるたびに UI が古くなり、承認の要否を取り違える（所見 83 の形）。

### 問い 2: 結果をどう返すか

1. **判断の状態を読む資源 `decisions(subject, kinds, limit)`。** `pending` / `applied` / `failed`、失敗の理由、
   適用の要約（期待 ID など）を返す。主語は不一致 ID や実体 IRI。
2. 実行の成否を HTTP の応答で返す。ADR-0012 が退けた形（人が適用を待ち、失敗で判断が失われる）。
3. イベントログで通知する。作業項目の状態は主張ではない（様相格子に席が無い）。

### 問い 3: 失敗の扱い

1. **理由をそのまま見せ、新しい判断として再投入できると明記する。** 同じ判断は再試行されない（事実 3）ので、
   「待てば直る」と読ませない。再投入は新しい冪等の鍵。
2. 失敗を自動で再試行する。レート制限や前提未達は人の状況判断を要し、業務システムを変える操作の自動再試行は危険。

## 決定

問い 1: `actionTypes`。問い 2: `decisions`。問い 3: 理由を見せ、再投入を促す。

- どちらも GraphQL（読み取りのみ）で、要求者（ABAC）を必須にする（既定は拒否）。
- UI のフォームは、アクション型を契約の一覧から選び、対象・深刻度・`correlation_id` を不一致から自動で入れる
  （人が書き換えない）。**理由は必須**。承認が要る契約には、承認の条件とロールを出す。
  **前提未達の上書きは、既定で閉じた別の折りたたみで理由を書かせる。**
- 冪等の鍵はフォームごとに 1 つ（解決のフォームと同じ）。
- **補償は実行しない**（H-08 の判断待ち）。契約の要約に補償先を表示するだけ。

## 帰結

- **不変条件 2**: 読み出しのみ。表も契約も変えない。
- **不変条件 12**: 契約の読み出しに秘密は出ない。
- **構成**: ワーカー数・alembic は変わらない。API に資源が 2 つ増える。
- **テスト**: 単体（契約の要約・判断の整形・UI の入力検査）、統合（API の `execute_action` → learning-worker →
  `decisions` が `applied` / `failed` を返す）。

## 未決

- **前提の事前判定。** 実行前に UI で「満たす / 満たさない」を予告するには、信念を読んで判定する層が UI に要る。
- **失敗した判断の再投入の補助。** 失敗の原因を直したあと、同じ内容で新しい鍵の判断をワンクリックで出す。
- **H-06 / H-07 / H-08 / H-25**（レート制限の永続化、`ActionEvent` の永続化、補償の入口、コマンド API の認証）は決めない。
