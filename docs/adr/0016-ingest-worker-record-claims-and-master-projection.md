# ADR-0016: 業務統合の取込は 6 番目のワーカーが周期実行し、記録の主張をイベントにし、資産台帳はアサーション + 投影で持つ

- 日付: 2026-10-25
- 状態: 採択
- 触る層: core（決定的な event_id）、knowledge（取込カーソル・台帳の投影）、integration（写像の主張・台帳の同期・計画）、services（ingest-worker）、infra（alembic）、ontology（0.6.0）

## 文脈

設計書 §2.5 の**記録パス**（CDC/API → スキーマ写像 → BusinessEvent → イベントログ → 信念更新）は、
M1 でライブラリとして組んだ（`IngestionPipeline`、写像 DSL、信頼性モデル、計画の取込）。しかし
**運用で呼ぶ者がいない**（`docs/PROGRESS.md` 所見 101）。`IngestionPipeline` を呼ぶのは G1 の統合テスト
だけで、`make seed` はオントロジーしか入れない。新規環境では `entities_of_type` が 0 件、照合ワーカーの
記録列は空のまま、計画は `planned` にならない。

M8-25 の計画中に、もう 1 つ欠落が見つかった（所見 115）。**取込を周期実行しても照合ワーカーには何も
届かない。** `IngestionPipeline` が出すイベントは `type = 記録型`（`ent:OperationLog`）・`p = 1.0`（記録が
存在する）である。照合ワーカーは `fluent_of_event` で `sbp-core:BusinessEvent/ent:Running` 形式の型だけを
拾い、`p` を「信頼性モデルを通した記録由来の確率」として読む（`rules/kind2.py`）。記録の**主張**
（MES は P-101 が稼働中と言っている）をフルーエントの確率に変える段が無く、G3 はそれをテストの中で手で
組んでいた。

さらに資産台帳（設計書 §7.1「マスタ: 定期同期」）の入口が無い。読み手（`entities_of_type` /
`most_specific_types` / `part_whole_edges`）は素の三つ組（`<P-101> rdf:type ent:Pump`）を読むが、
`AssertionStore` は reifier と triple term だけを書き、素の三つ組を書かない。

関連: 設計書 §2.5、§3.12（実体 ID は業務 ID から派生した安定 IRI）、§6.1（冪等性）、§7.1〜§7.4、§8.2
（類型 2 の記録由来尤度）。ADR-0006（写像 DSL）、ADR-0009（接地対象は知識グラフから型で引く）、
ADR-0012（専用ワーカーの先例）。

## 選択肢

### 問い 1: 取込をどこで周期実行するか

1. **6 番目のワーカー `ingest-worker` を足す。**
   - 利点: ADR-0012 と同じ。業務システムの遅延・障害が照合や信念更新に影響しない。1 ワーカー 1 プロセス
     の規約を保つ。SIGTERM・疎通検査・冪等は `services/runtime.py` をそのまま使える。
   - 欠点: プロセスとワーカー一覧が 1 つ増える（文書の更新が要る）。
   - MacBook 上のコスト: 既定では起動しない（`scripts.dev --workers ingest`）。周期で表を引くだけ。
2. 照合ワーカーに相乗りする。
   - 欠点: 駆動が 2 種類（Kafka の consumer と業務システムのポーリング）混ざり、`step()` の意味が曖昧に
     なる。業務システムの応答待ちが窓の判定を止める。
3. 周期ジョブ（cron 相当）。
   - 欠点: ADR-0012 と同じく、ワーカーの仕組みを再実装することになる。

### 問い 2: 記録の主張をどこで確率にするか

1. **統合層が主張イベントを出す。** 写像 DSL に任意の `claims`（`{fluent: ent:Running, field: running}`）を
   足し、`IngestionPipeline` が既存の「記録が存在する」イベントに加えて、主張ごとに
   `type = sbp-core:BusinessEvent/ent:<Fluent>`・`modality = observed`・
   `p = σ(ReliabilityModel.log_likelihood_ratio(record_says))`（一様事前）を出す。
   - 利点: 信頼性モデルは統合層の持ち物（設計書 §7.3）で、変換の場所が 1 つになる。照合ワーカーは変更
     不要（様相 `observed` が記録列に入る、所見 47）。信念更新の三源化（M8-26）が同じイベントを使える。
   - 欠点: 写像 DSL の拡張（ADR-0006 の範囲を足す）。イベントが記録 1 件あたり 1 + 主張数に増える。
2. 照合ワーカーと信念ワーカーがそれぞれ記録型を解釈する。
   - 欠点: 「どの記録型のどの列がどのフルーエントの主張か」の知識が推論層の 2 か所に重複する。
     `EventEnvelope` は記録の中身（payload）を運ばないので、そもそも主張の値が取れない。

### 問い 3: 資産台帳を知識グラフにどう置くか（2026-10-25 に利用者が選択）

1. **アサーション + 投影。** 台帳の各行を二時制アサーション（`observed`、来歴 = 台帳同期）として追記し、
   現在有効な文から素の三つ組の投影グラフ `urn:sbp:g:master:<site>` を毎回作り直す。
   - 利点: 不変条件 1・2 を守る（台帳も「誰かの主張」で、変更は `tx_to` を閉じて追記）。投影は文から
     再計算できる（「状態はイベントの投影」）。読み手とそのテストを変えない。
   - 欠点: 書き込みが 2 段になる。投影は作り直す（投影であって文ではないので、置き換えは不変条件 2 に
     当たらない）。
2. アサーションのみ。読み手を reifier 経由（`tx_to` が開いている文）に書き換える。
   - 欠点: 読み手 3 つと単体テストの fixture の書き換えが大きい。
3. 参照グラフのみ（オントロジーと同じ扱い）。
   - 欠点: 来歴と as-of の履歴が残らず、設計書 §0.3 の「すべての事実は誰かの主張」から外れる。

### 問い 4: 冪等をどう保つか

取込は at-least-once である（送信の後にカーソルを進めるので、その間で落ちると同じ行を読み直す）。

1. **決定的な ID。** 取込イベントの `event_id` を決定的な UUIDv7（時刻部 = 記録時刻、乱数部 =
   `(source, table, external_id, updated_at, claim)` のハッシュ）にし、再送は `processed_events` で弾く。
   台帳・計画のアサーションは内容から導く `assertion_id`（uuid5）にし、再実行は差分無しになる。
   - 利点: 不変条件 4（UUIDv7 の `event_id` で冪等）の形のまま、読み直しが無害になる。
   - 欠点: UUIDv7 の乱数部をハッシュで埋める（RFC 9562 は実装依存の埋め方を許す）。
2. カーソルを送信の前に進める。
   - 欠点: 送信に失敗した行を二度と読まない（所見 52 の取りこぼし）。

## 決定

- **問い 1 は選択肢 1**（`services/ingest_worker.py`）。`scripts/dev.py` の `WORKERS`・
  `docs/development-rules.md`・層別ルールのワーカー一覧を同じ変更で更新する。CLAUDE.md の一覧は
  確認待ちのブランチ（X-15）に足す。
- **問い 2 は選択肢 1**。最初の対象は `operation_log.running → ent:Running`。
- **問い 3 は選択肢 1**。オントロジーに台帳の記録型 `ent:AssetRegisterEntry ⊑ sbp:Record` を足す（0.6.0、
  MINOR）。台帳の行は `rdf:type`（`vocab.ent` に実在する型だけ）と `sbp:partOf` のアサーションになる。
- **問い 4 は選択肢 1**。カーソルは `(site, source, table)` ごとの `pulled_through`（alembic 0010
  `ingest_cursors`、後退しない upsert）で、**送信の後に進める**。
- **開発の外界はファイルの SQLite のモック**（`MockBusinessSystem(db_path=…)`）。テストまたは開発者が台本を
  流し込み、ワーカーは production のコードとして取り込む。実システムのコネクタは設定で差し替える口だけを
  用意する（`SBP_INTEGRATION_MOCK_DB_PATH` が空ならコネクタ無しで起動し、`unwired` で報告する）。
- **計画**: 計画種 → 意図するフルーエントの対応は `plans.py` の遵守率の表の隣に置く（PlannedOperation →
  Running、PreventiveMaintenance → UnderMaintenance、Inspection → Inspected）。未知の計画種は推測せず
  飛ばしてログに出す。計画が変わったら旧文の `tx_to` を閉じて新文を足す。
- **1 周の順序**: 台帳 → 解決器の更新（投影から既知の実体を読む）→ 業務記録（送信）→ 計画。台帳を先に
  しないと、新しい設備の記録が `UnresolvedRef` になる。

## 影響

- **不変条件 1・2**: 台帳と計画はアサーションとして必須欄を持ち、変更は `tx_to` を閉じて追記する。投影
  グラフは文ではない（文から作り直せる派生物）。
- **不変条件 3**: 主張イベントは `observed`（記録がそう主張していることは観測された事実）。そこから
  信念を作るのは推論層で、出力は `inferred`。台帳のアサーションは `observed`。
- **不変条件 4**: 取込イベントの `event_id` は UUIDv7 の形のまま決定的になる。
- **不変条件 5**: フルーエント・型は `vocab` と写像の CURIE 展開から引き、IRI を直書きしない。
- **不変条件 6**: 主張イベントの確率は信頼性モデルだけから作り、信念を入力にしない。監査隔離は消費側
  （照合・信念更新）が引き続き適用する。
- **オントロジー版**: 0.5.0 → 0.6.0（MINOR、加法的）。既存のプローブ・クエリ・`schemas/` は壊れない。
  再接地は不要（台帳の個体は新規）。
- **構成**: ワーカーが 5 → 6。alembic が 9 → 10。
- **テスト**: 単体（主張の宣言と検査、主張イベントの確率、決定的 ID の性質、台帳の差分、投影、計画の
  置き換え、ワーカーの 1 周の順序とカーソル）、統合（外界の SQLite → ingest-worker → Kafka・知識グラフ →
  照合ワーカーの記録列。2 周目は何も増えない）。

## 未決

- **スキーマ指紋の永続化と `MappingDriftDetected` の送信。** いまは指紋がプロセス内のメモリにあり、
  再起動直後の比較は常に空になる。`<site>.integration.mapping` トピックはあるが送る者がいない。
- **SKU・拠点レイアウトの台帳。** 本 ADR の台帳は設備（と、部分−全体の全体側になるライン）だけ。
- **実システムのコネクタと資格情報。** 本リポジトリでは扱わない（ユースケース検証は別リポジトリ、
  ADR-0001）。資格情報の置き場は `docs/HITL.md` H-01 と連動する。
- **台帳から消えた設備の信念。** 台帳の文は `tx_to` で閉じるが、その設備についての既存の信念をどう扱うか
  （接地対象から外れるだけでよいか）は決めていない。
