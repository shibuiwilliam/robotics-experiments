# ADR-0008: UI は Vite + React（TypeScript）で、GraphQL クライアントと UI ライブラリを入れない

- 日付: 2026-10-03
- 状態: 採択
- 触る層: api（読み取りのみ）/ infra（compose の `ui` profile）

## 文脈

M7-04 で 4 つのビューを作る（`docs/TASK.md` §3、設計書 §12.2）。

| ビュー | 役割 |
|---|---|
| 不一致キュー | 証拠の並置（観測 / 記録 / 計画）、解決入力が**学習信号になる** |
| 信念ビュー | 三源の寄与と as-of スライダ（「いつ時点でそう信じていたか」） |
| 期待ボード | Expectation の状態（Active / Fulfilled / Violated / Undetermined） |
| 概念 curation | `ConceptProposal` の採否と却下理由の記録 |

`docs/TASK.md` §7 の未決 4「UI の技術選定（M7-04）— フレームワークは着手時に ADR」に対する決定。

制約が 3 つある。

1. **UI は読み取りと「人の判断の投入」だけを担う。** 信念を直接書く経路を UI に作らない
   （不変条件 1・2。書き込みは `/commands/*` の承認フローを通る）。
2. **MacBook で開発・ビルドできること。** Compose 全体 6 GB 以内（CLAUDE.md）。UI は任意 profile
   だが、開発時は `npm run dev` をローカルで動かす。
3. **検証できること。** CLAUDE.md の完了の定義は「型が通る、テストがある」。`node_modules` が
   巨大だと、型検査とテストが現実的な時間で回らなくなり**この定義を満たせなくなる**。

## 選択肢

### 1. Vite + React + TypeScript、GraphQL クライアントと UI ライブラリを入れない（採択）

- 利点: 依存が 2 本（`react`, `react-dom`）。GraphQL は `fetch` に POST するだけなので
  クライアントライブラリ無しで足りる（クエリは 4 本、ミューテーションは無い）。型は
  `schemas/` ではなく GraphQL スキーマから手で書くが、**本数が少ないので手書きが追える**。
- 欠点: キャッシュ・楽観更新・購読を自分で書くことになる。
- MacBook 上のコスト: `node_modules` 約 60 MB、`tsc --noEmit` と `vitest` が数秒。

### 2. Vite + React + Apollo Client / urql + MUI など

- 利点: キャッシュ・正規化・購読が最初からある。見た目も早く整う。
- 欠点: `node_modules` が数百 MB になり、型検査とテストが遅くなる。**キャッシュが
  二時制と相性が悪い**——`asOf` が違うだけの同じ `subject` は別の事実であり、
  正規化キャッシュは「同じ ID なら同じエンティティ」と仮定して上書きする。二時制の
  UI でその仮定は誤りで、キャッシュの設定でそれを打ち消す作業が利得を食う。
- MacBook 上のコスト: 初回インストールが数分、開発サーバのメモリが数百 MB。

### 3. SvelteKit

- 利点: ランタイムが小さく、記述量が React より少ない。
- 欠点: この基盤に Svelte の知見が無く、`.svelte` は Python 側の lint / format の
  仕組みに乗らない。**言語が 3 つ目になる**（Python / TypeScript / Svelte のテンプレート記法）。
- MacBook 上のコスト: 選択肢 1 と同程度。

### 4. UI を作らず、SPARQL / GraphQL を直接叩いてもらう

- 利点: 作らないのが一番安い。
- 欠点: **解決入力が学習信号になる**という設計の中心（設計書 §8.3、§12.2）が実装されない。
  不一致を人が解決した結果を基盤に返す経路が無いと、照合は「起票して終わり」になる。

## 決定

選択肢 1。**依存を増やさないことを設計の一部として扱う。**

理由は 3 つ。

1. 二時制の UI で正規化キャッシュは利得にならない（選択肢 2 の欠点）。`asOf` スライダを
   動かすたびに**別の事実の集合**が返るのであって、同じエンティティの更新ではない。
   キャッシュを無効化して使うなら、最初から入れない方が単純である。
2. GraphQL の呼び出しは 4 本で mutation が無い（API 層に mutation を作っていない）。
   `fetch` に POST する 30 行で足りるものに、クライアントライブラリは重い。
3. 依存が少ないほど `tsc --noEmit` と `vitest` が速く、完了の定義（型が通る、テストがある）を
   毎回満たしやすい。**検査が遅いと検査しなくなる。**

状態管理も入れない。4 ビューは互いに状態を共有せず、各ビューが自分のクエリ結果を持つだけで足りる。
共有したくなったら、そのときに必要性を示して入れる。

### UI が持たない機能（意図的）

- **信念の直接編集。** 書き込みは `/commands/*` の承認フローを通る（設計書 §9.2）。UI に
  「この信念を正しい値に直す」ボタンを置くと、追記専用（不変条件 2）と承認フローの両方を迂回する。
- **「正しい値」の入力欄。** 不一致の解決は「どちらが正しいか」ではなく**解決の種別**
  （記録が誤り / 観測が誤り / 両方正しく定義が違う / 系統的な偏り）を選ぶ形にする。真偽ではなく
  信念を管理する、という原則が UI の形に出る必要がある。
- **仮説シナリオの既定表示。** `hypothetical` は明示的に切り替えたときだけ出す。混ぜて表示すると
  「決まったこと」と読まれる（不変条件 3）。

## 影響

- **不変条件**: 1・2（UI から信念を書かない）、3（`hypothetical` を既定で表示しない）、
  9（人の映る映像を表示する機能を作らない。UI が扱うのは記号と確信度だけ）、
  12（API のエンドポイントは `.env` の `SBP_API_URL` から読み、UI のソースに URL を書かない）。
- **オントロジー版**: 変更なし（UI は読み取り側）。再接地は不要。
- **テスト**: `vitest` で純粋関数（証拠の並置、三源の寄与計算、as-of の時刻変換）を検査する。
  DOM のテストは最小限にし、**表示の正しさより「人の判断が正しく基盤に戻ること」を優先する**。
- **運用**: `make up --profile ui` で起動。ビルド成果物は静的ファイルで、API とは別オリジン。

## 未決

- 認証の実装。ABAC（M7-06）は要求者を受け取る形まで作ったが、**UI がどう認証するかは決めていない**。
  現状の UI は開発用に固定の要求者を送る。本番の認証方式を決めるまで公開しない。
- 購読（`/stream/{topic}`）の UI への反映。現状はポーリングで、長時間開くと負荷が読めない。
