# ADR-0029: コマンドの「誰が」は認証済みの要求者から決める（H-25）

- 日付: 2026-11-08
- 状態: 採択
- 触る層: api（app・commands）、apps/ui（ヘッダ）

## 文脈

`/commands/*` は要求者を解決せず、`resolved_by` / `decided_by` / `approved_by` / `answered_by` を本文の自称で受けていた（M8-29 のレビュー、H-25）。
人の回答は確信度 0.98 の `observed` として信念に入り、`answered_by` は監査隔離の単位でもあるので、他人の名での注入が最も効く。

## 決定

1. **要求者を解決できなければ受けない**（401）。`principal_resolver` が無い構成でもコマンドは受けない（既定は拒否、ABAC と同じ）。
2. **エージェントは人の判断を出せない**（403）。解決・採否・承認・回答は人の判断で、エージェントの出力は `inferred` に限る（不変条件 3）。
3. **主体の欄（`IDENTITY_FIELDS`）は要求者で埋める。** 本文に無ければ入れ、あれば要求者と一致を要求する（食い違いは 403、キューに届かない）。
   UI が自分の主体を本文にも入れている現行の契約は保つ（契約テストは変えない）。
4. UI の開発ビルドは `VITE_SBP_DEV_PRINCIPAL` を `X-SBP-Principal` で送る。本番の認証方式（H-02）が決まったら resolver を差し替えるだけでよく、コマンド側は変えない。

## 結果

- 他人の名で回答・承認・解決できない。`decided_by` は認証された主体になるので、監査隔離と来歴が自称に依存しない。
- 統合テストはハンドラ（`build_command_handler`）を直接呼ぶ経路で、HTTP の認証は単体テストが通す。

## 限界（未決のまま）

- **認可（誰が何を判断してよいか）は無い。** 要求者が解決できれば 4 コマンドとも通る。回答者ごとの権限・確信度は ADR-0018 の未決で、H-25 に残す。
- 開発用 resolver はヘッダを名乗るだけで認証ではない（`SBP_ENV=dev` 専用）。本番の認証は H-02。
