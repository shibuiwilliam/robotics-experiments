# ADR-0023: 推定パスの先頭は「エンコードジョブ」で、観測はスプールから受け、WM の重みは置き場に直列化する

- 日付: 2026-11-08
- 状態: 採択
- 触る層: worldmodel（重みの直列化・エンコード）、knowledge（潜在索引への書き込みの利用）、scripts（`encode` / `train_koopman`）

## 文脈

設計書 §2.5 の推定パス（観測 → 潜在 → プローブ → 事象昇格）の先頭、**観測窓 → `WorldModel.encode` → `LatentIndex.write`
を運用で回す者が無い**（所見 101）。潜在索引に書くコードは `test_bridge_worker_e2e` / `test_g4_worldmodel` にしか無く、
新規環境では bridge-worker が読む潜在が空である。M8-24 は「エンコーダをどこで動かすか」を ADR で決めるタスクだった。

確かめた事実:

1. 設計書 §12.1 はエンコーダを**エッジ**に置く。エッジは現場のセンサに近い層で、本リポジトリの外にある
   （ADR-0001: ユースケース検証・実機は別リポジトリ）。
2. `KoopmanModel` は numpy だけで、**学習済みの重みを直列化する経路が無い**（`WorldModelRegistry` は場所と版の管理のみ。
   PROGRESS の既知の制約）。直列化が無いと、学習したプロセスの外でエンコードできない。
3. 観測の入口の契約が無い。`EventEnvelope` は主張を運ぶもので、観測窓（数値の配列）を運ぶ形ではない。
4. 不変条件 9: 生映像・音声を永続化しない。永続化するのは潜在と記号だけ。

## 選択肢

### 問い 1: エンコーダをどこで動かすか

1. **本リポジトリの「エンコードジョブ」（`scripts/encode.py` + `sbp.worldmodel.encoding`）。** 観測窓の入口を
   Protocol（`ObservationSource`）にし、現場のエッジは**スプール**（JSONL）に窓を置く。ジョブは窓を読み、
   WM の重みをロードして `encode` し、潜在索引に書く。新しいプロセス種別（ワーカー）は増やさない。
2. 6 番目に続く 7 番目のワーカー。常駐のサービスにするが、観測の到着方式（スプール・ストリーム）が決まらないまま
   ワーカーの形（周期・readiness）を固定すると、決め打ちになる。ジョブなら cron やエッジのフックから起動できる。
3. bridge-worker の前段に埋め込む。bridge-worker は「読むだけ」の層（潜在 → プローブ → イベント）で、重みのロードと
   観測の入口を持たせると責務が混ざる。
4. 本リポジトリの外（エッジ）に全部任せ、入口の契約だけを決める。契約（潜在索引の表と WM 版の登録）は本リポジトリが
   持つので、結局エッジが `LatentIndex.write` を呼ぶ形になる——エッジに本リポジトリの内部 API を依存させる。

### 問い 2: 観測の入口

1. **スプール（JSONL）。** 1 行 = 1 窓（実体・チャンネル名・時刻・値）。ファイルは現場のエッジが置き、ジョブは
   読み取り専用。参照実装 `JsonlObservationSource` を置き、他の入口（ストリーム・DB）は Protocol で差し替える。
2. Kafka の観測トピック。`EventEnvelope` に配列を載せる契約変更を要する。

### 問い 3: WM の重みの直列化

1. **numpy の `.npz`（`allow_pickle=False`）+ メタ。** Koopman は配列だけで足りる。pickle は使わない（読み込みで任意コードが動く）。
   メタ（モデル ID・版・チャンネル・設定）を検証し、版は `latest` を禁じる（`WorldModelRegistry` と同じ規約）。
2. torch の `state_dict`。jepa_ts 用。今回の範囲外（Koopman だけ）。

## 決定

問い 1: エンコードジョブ。問い 2: スプール（JSONL）。問い 3: `.npz`。

- `sbp.worldmodel.serialization`: `dumps(model) -> bytes` / `loads(data) -> KoopmanModel`。置き場は `ArtifactStore`
  （`models/<model-slug>/<version>/koopman.npz`）。未学習のモデルは保存しない。ロードは版・チャンネル・次元を検証し、
  食い違えば失敗する。
- `sbp.worldmodel.encoding.EncodeRunner`: 窓 → 潜在（窓内で埋め込みが埋まった全時刻）→ `LatentIndex.register` / `write`。
  **実体ごとのウォーターマーク**（`WatermarkStore`、worker 名 `encoder`）で、処理済みの時刻以前の窓を再エンコードしない
  （潜在索引への書き込みは上書きなので壊れはしないが、無駄）。**書いた後にウォーターマークを進める**（所見 52）。
- 窓の値そのものは永続化しない（潜在だけ。不変条件 9）。スプールは現場の置き場で、ジョブは削除も書き換えもしない。
- 学習は `scripts/train_koopman.py`（スプールの履歴窓で `fit` → 直列化 → `ArtifactStore.put`、上書きしない）。
- 健全性（`health()` の `latent_shift` / `pred_error`）と推論遅延をジョブの戻り値に出す（M8-15 が指標に書く）。

## 帰結

- **不変条件 5**: WM 版・プローブ ID は設定（`SBP_BRIDGE_WM_VERSION`）から。IRI を直書きしない。
- **不変条件 6・10**: ジョブは真値（`sbp.testing`）を読まない（`scripts` は import-linter の対象）。窓の模擬は現場側（テスト）。
- **不変条件 9**: 観測値は永続化しない。
- **構成**: ワーカー数は 6 のまま。alembic の変更なし。スプールの置き場は設定で渡す（既定値を置かない）。
- **テスト**: 直列化の往復・改ざん拒否・版違い拒否、ウォーターマークの冪等、実 Postgres への書き込み → bridge-worker が読める。

## 未決

- **観測の実センサ接続。** 現場のエッジ（本リポジトリ外）が窓をスプールに置く部分。
- **jepa_ts の直列化。** torch の重みの形式。Koopman で運用が回ってから決める。
- **スプールの保持と掃除。** 処理済みの窓の削除・アーカイブはエッジ側の運用。
- **多拠点・複数 WM 版の並走。** 版ごとにジョブを起動する想定だが、カナリアの切り替えは未設計。
