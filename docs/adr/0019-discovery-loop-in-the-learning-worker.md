# ADR-0019: 概念発見は learning-worker の周期処理にし、運用の入口は反復する不一致だけにし、再提案は signal の指紋で抑える

- 日付: 2026-11-07
- 状態: 採択
- 触る層: knowledge（解決済み不一致の読み出し）、reasoning（signal 源・抑制・提案の生成・プロンプト）、services（learning-worker）、tests（fixture）

## 文脈

設計書 §8.6 の概念発見（検出 → 提案 → curation）は G6 でライブラリとして通ったが、**周期で回す者が無い**。
`concept_proposals` 表（M8-19、ADR-0015）と curation（learning-worker の `_apply_curation`）は有るのに、
提案を表に書く側が無く、UI の概念 curation は空のままである。H-10（却下した提案の再提案を抑えるか）は、
周期実行を入れて初めて実害になる——次の周期が同じ signal から同じ提案をまた出す。

確かめた事実:

1. 入口 (a) 低被覆クラスタは潜在、(b) 整合残差の持続は残差の指標を要るが、**どちらの入力も運用に無い**
   （M8-24 / M8-15）。入口 (c) 反復する不一致だけが運用の入力（`discrepancies` 表）で足りる。
2. 提案には LLM が要る（`sbp.llm`、`concept_proposal` タスク）。**live のプロバイダは H-04 待ち**で、運用の
   組み立てが作れるのは replay（fixture 必須、無ければ失敗）まで。discovery はホットパス禁止の契約
   （不変条件 11）に含まれず、LLM を使ってよい。
3. プロンプトの組み立てと出力スキーマはテスト（`test_g6_evolution.py`）の中にしか無い。

## 選択肢

### 問い 1: 誰が周期で回すか

1. **learning-worker に周期処理を足す**（ADR-0017 と同じ形）。「実行 → 期待 → 検証 → 学習 → 進化」を 1 つの責務に
   閉じ、新しいプロセスを増やさない。欠点: `step()` の周期がまた 1 つ増える。
2. 7 番目のワーカー。LLM と Postgres と Oxigraph の配線が重複し、責務が薄い。
3. scheduler-worker。スケジューラは「何を観測するか選ぶ」読み取り中心で、提案を表に書く責務を混ぜない。

### 問い 2: 運用の入口

1. **(c) 反復する不一致だけ。** 解決済み（`Resolved` / `Learned`）の `(実体, 類型, 解決結果)` を
   `repeated_discrepancy_signals` に渡す。signal の供給は差し込み式にして、(a)(b) の入力が運用に乗ったとき足せるようにする。
2. 3 入口すべてを作り、入力が空の入口は空で動かす。動かない経路を「実装済み」に見せる（所見 32 の形）。

### 問い 3: 再提案の抑制（H-10）

1. **signal の指紋で、LLM を呼ぶ前に抑える。** 指紋 = `(trigger, 実体の集合, 類型)`。既に提案がある指紋は、
   `proposed` / `accepted` / `revised` なら常に、`rejected` なら冷却期間の間、抑える。冷却後に同じ signal が
   再び出れば再提案する（状況が変わった可能性。人が再度判断できる）。
2. 提案の名前で抑える。LLM は同じ signal に別の名前を付けうるので、名前では防げない。
3. 抑えない。人が毎周期同じ提案を却下することになり、curation の信頼が落ちる。

### 問い 4: 周期あたりの提案数

**上限を置く**（既定 3）。強い signal から。上限は curation の人手を守る（ADR-0012 の人への質問の頻度上限と同じ考え）。

## 決定

問い 1: learning-worker。問い 2: (c) のみ、signal 源は差し込み式。問い 3: 指紋で抑制（冷却 30 日）。問い 4: 上限 3。

- 周期 `SBP_REASONING_DISCOVERY_PERIOD_S`（既定 86400 秒）、冷却 `SBP_REASONING_DISCOVERY_REJECTION_COOLDOWN_DAYS`
  （既定 30）、上限 `SBP_REASONING_DISCOVERY_MAX_PROPOSALS_PER_CYCLE`（既定 3）。
- **LLM が使えない・失敗したら提案を作らない**。ログと件数に残し、黙って成功にしない。provider が無ければ
  `unwired` に数える（M8-30 の形）。replay で fixture が無い場合も失敗として数える。
- 出力は pydantic（スキーマ）で検証してから `ConceptProposal`（`PROPOSED`、来歴に `provider / model / prompt_version`）。
  **自動採用しない**（設計書 §8.6、不変条件 11）。`rejected_alternatives` が空の提案は既存の検証が拒否する。

## 帰結

- **不変条件 3**: 提案は仮説的な作業項目で、アサーションではない（様相格子に席が無い。ADR-0015）。
- **不変条件 9**: 人の映る事例から個人に関する概念を作らない（プロンプトの制約）。潜在の重心は表に置かない（ADR-0015）。
- **不変条件 11**: LLM は発見・提案にだけ使う。ホットパスから呼ばない（import-linter の契約で保たれる）。
- **構成**: ワーカー数は 6 のまま。alembic の変更なし。設定が 3 つ増える。
- **テスト**: 単体（指紋・抑制の各状態・冷却・上限・LLM 失敗・provider なし）、統合（実 Postgres。解決済みの不一致 →
  提案が 1 件、2 周目は何も増えない、却下は冷却中は再提案されず、冷却後は再提案される）。fixture は replay の手書き JSON。

## 未決

- **入口 (a)(b) の運用接続。** 潜在（M8-24）と整合残差の指標（M8-15）が運用に乗ったときに足す。
- **live の LLM プロバイダ（H-04、M8-10）。** それまで運用の発見は replay の fixture があるときだけ提案を出す。
- **採択後のオントロジー MINOR 起票の追跡**（ADR-0015 の未決 1）。
- **冷却期間の提案ごとの調整**（却下理由によって冷却を変える等）。
