# ADR-0017: 期待の検証は learning-worker の周期処理にし、期限切れだけを検証し、記録の存在は投影表から引く

- 日付: 2026-11-07
- 状態: 採択
- 触る層: knowledge（記録の存在の投影・期限切れの期待の読み出し）、reasoning（検証の純粋な部分）、services（learning-worker、ingest-worker）、infra（alembic 0011）

## 文脈

設計書 §8.5 は「アクション実行 → 期待の生成 → 期限までの検証 → 学習」を定める。M8-21 までで
「承認 → 実行 → 期待の書き込み」は運用に乗ったが、`verify_expectation`（M5-04）を呼ぶ運用コードが無く、
期待は `Active` のまま期限を過ぎても動かない（`docs/PROGRESS.md` 所見 103）。

設計の前に確かめた事実（所見 118）:

1. `verify_expectation` は**期限前でも**観測が無ければ `Undetermined` にする（`Expectation.verify` は、
   判定が `None` の面が残れば `Undetermined`）。期限切れの `expire` と違って期限を見ない。周期ジョブが
   素朴に全 `Active` を回すと、「まだ検証できない」が「判定不能」として記録される。
2. 記号側（業務効果）の検証は `records_present[記録型 IRI]` を要るが、**運用に「この実体にこの型の記録が
   あるか」を引ける場所が無い**。取込（ADR-0016）は存在イベントを出すだけで、台帳以外の記録は永続しない。
3. 潜在側（物理効果）は `current_beliefs` が使える（belief-worker の `inferred`）。
4. `ExpectationStore.upsert` は状態の後退を拒否し、`ObservationQueue.enqueue` は
   `(discrepancy_id, fluent)` で冪等なので、検証パスを再実行しても二重にならない。

## 選択肢

### 問い 1: 誰が検証を回すか

1. **learning-worker に周期処理を足す。**
   - 利点: 期待の書き手・信念の読み手・観測要求キューの書き手が既にここにある（ADR-0012 / 0014）。
     「実行 → 期待 → 検証 → 学習」が 1 つの責務に閉じ、新しいプロセスも依存も増えない。
   - 欠点: `step()` が 2 種類の周期（判断キューと検証）を持つ。
2. 7 番目のワーカー（expectation-worker）。配線（Postgres・Oxigraph・キュー）がほぼ重複し、
   ワーカー数が増える割に責務が薄い。
3. scheduler-worker。スケジューラは「何を観測するか選ぶ」読み取り中心の責務で、期待の状態を書く責務を
   混ぜると ADR-0011 の分離が崩れる。

### 問い 2: いつ検証するか

1. **期限（`Expectation.deadline` = 最も遅い効果の期限）を過ぎた `Active` だけ。**
   観測が早く揃っても待つ。信念は後で動きうるので、早期の判定は撤回できない（`Fulfilled` は終端に近い）。
   所見 118-1 の誤記録も起きない。
2. 観測が揃ったら期限前でも検証する。早く学べるが、後で信念が変わっても判定を戻せない。将来の拡張とする。

### 問い 3: 記録の存在をどこから引くか

1. **投影表 `business_records`（alembic 0011）。** ingest-worker が記録 1 件ごとに
   `(site, entity, record_type, external_id, revision, recorded_at)` を追記する（`ON CONFLICT DO NOTHING`、
   送信の後・カーソルの前）。検証は「期待の作成時刻以降に `recorded_at` を持つ記録があるか」を引く。
   - 追記専用の投影で、真実のフラグではない（業務システムが system of record のまま）。
2. 業務トピックを再読する。保持期間に依存し、検証のたびに全走査になる。
3. 知識グラフに記録をアサーションで持つ。ADR-0016 が「記録はイベント、台帳と計画だけアサーション」と決めたのを覆す。

### 問い 4: 結果をどう扱うか

| 結果 | 扱い |
|---|---|
| `Fulfilled` / `Violated` / `Undetermined` | `ExpectationStore.upsert` で状態を進める（後退しない） |
| `Undetermined`（期限切れ） | 観測できなかった**物理効果**ごとに観測要求を積む（`discrepancy_id = "expectation:<id>"`）。記録型は観測要求にできない（フルーエントではない） |
| `Violated` | 記号側が外れ → 類型 1（存在）、潜在側が外れ → 類型 2（状態）の `Discrepancy` を起票（`detector="expectation"`、証拠に期待の ID）。WM とプロセスオントロジーのどちらを疑うかは `VerificationResult.blames_*` が期待のペイロードに残る |

## 決定

問い 1: learning-worker。問い 2: 期限切れのみ。問い 3: `business_records` 投影。問い 4: 上表。

## 帰結

- **不変条件 2**: 期待は状態の進行だけを書く。`business_records` は追記専用。アサーションは触らない。
- **不変条件 3・6**: 検証は信念（`inferred`）と記録の存在を読むだけで、様相を作らない。監査対象の記録を
  推定に入力する経路ではない（期待の検証は不一致の監査ではなく、アクションの結果の確認）。
- **不変条件 11**: LLM を使わない。
- **構成**: ワーカー数は 6 のまま。alembic が 10 → 11。設定が 1 つ増える（検証周期）。
- **テスト**: 単体（期限前は触らない、観測なし期限切れ → `Undetermined`、記号のみ外れ → 類型 1、
  潜在のみ外れ → 類型 2、観測要求の対象は物理効果だけ）、統合（実 Postgres / Oxigraph。満たす・外れる・
  観測なしの 3 本。2 周目は何も変わらない）。

## 未決

- **期限前の早期検証**（問い 2-2）。
- **`Learned` への遷移。** 検証結果を学習信号（WM の再学習・T の見直し）に変えて `Learned` にするのは別タスク。
- **`business_records` の保持期間。** 追記専用で単調に増える。検証に要るのは期待の作成時刻以降なので、
  古い行の削除（保持窓）を運用で決める。
- **規範（類型 5）への起票。** 期待が規範違反を含む場合の扱い。
