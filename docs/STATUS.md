## 運用経路の到達範囲（2026-10-25 の棚卸し）

設計書 §2.5 の三つのデータパスを `services/` と `scripts/` から辿った結果（10-17 の結果を 10-25 に
コードで再検証）。**各パスの先頭を運用で書くコードが無い**ので、新規環境では連鎖が始まらない
（`docs/PROGRESS.md` 所見 101〜103）。加えて、**運用の組み立てが既定値に頼って何かを渡していない**箇所が
ある（所見 108 / 109）。

| 経路 | 運用で動く段 | 運用に無い段（ライブラリとテストの中にだけある） |
|---|---|---|
| 推定パス | 潜在索引 → プローブ → 事象昇格 → `bridge.physical`（bridge-worker） | 観測 → `encode` → 潜在索引（M8-24）/ プローブ束を置き場に入れる（M8-23）/ 接地対象の実体の登録（M8-25。ドメイン TTL に設備の個体は無い）/ SHACL 検証・同一性・空間束縛（H-24） |
| 記録パス | — | コネクタ → 写像 → `integration.business`、計画の取込（M8-25） |
| 信念更新 | `bridge.physical` → 前向きフィルタ → Oxigraph、部分−全体の結合（belief-worker） | **記録と計画を入れていない＝運用では一源**（M8-26）/ Situation の参加関係を書く者がいない（読み側の述語は M8-28 で `hasParticipant` に直した）/ `partOf` を書く者がいないので結合の入力も空 |
| 照合 | 類型 2 の検出 → `discrepancies` 表 + 拠点トピック（reconcile-worker） | 記録側の入力（記録パスが無いので空）/ 実体の型（資産台帳が無いので業務価値は全件中間値。配線は M8-30 で済み）/ **抑制は構造的に 0**（類型 2 の抑制規則が常に偽、所見 113）/ 類型 1・3・4・5 |
