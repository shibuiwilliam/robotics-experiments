# PROMPT.md — SBP 開発を遂行するためのプロンプト集

- 日付: 2026-10-03（初版）
- 対象: Claude Code で SBP を開発するすべてのセッション
- 位置づけ: `docs/TASK.md` の計画を 1 セッションずつ確実に消化するための、コピー＆ペースト可能なプロンプトのカタログ。規約の実体は `CLAUDE.md` / `.claude/rules/` / `docs/development-rules.md` にあり、本書のプロンプトはそれらを**参照させる**（プロンプト内に規約を複製しない。規約が変わってもプロンプトが古びないため）。

---

## 0. 使い方

1. **1 セッション 1 タスク**を原則にする（タスクは 1 日以内の粒度に設計済み。TASK.md §2）。
2. `CLAUDE.md` は毎セッション自動で読み込まれる。層別ルール（`.claude/rules/*.md`）は該当ファイルを開いた時に自動で読み込まれる。したがってプロンプトで渡すべきは **(a) タスク ID、(b) 設計書の該当章、(c) 完了報告の形式** の 3 点だけでよい。
3. `<...>` はプレースホルダ。使用前に置換する（例: `<TASK_ID>` → `M0-05`）。
4. セッションの基本サイクル: **P-00（状況把握）→ P-10（タスク実行）→ P-12（完了処理）**。マイルストーンの境界では **P-02（着手計画）** と **P-03（ゲート検証）** を使う。
5. 大きな変更（新モジュール・オントロジー MAJOR・ストア変更・サービス追加）を含むプロンプトは、**plan mode（Shift+Tab）で投入**して計画の承認を先に行う。

## 1. セッション運営プロンプト

### P-00 状況把握（セッション開始時）

```text
docs/TASK.md と docs/STATUS.md を読み、現状を報告せよ。着手はまだしない。
報告に含めること:
1. 現在のマイルストーンと直近ゲートの状態
2. 進行中（[~]）タスクと WIP 制限（2 件）の充足状況
3. 次に着手すべきタスク 1 件とその理由（依存関係・TASK.md §2 の着手条件に照らして）
4. TASK.md §7 の未決事項のうち、そのタスクをブロックするものの有無
```

### P-01 計画の全体レビュー（週次・ゲート通過後）

```text
docs/TASK.md を読み、計画の健全性をレビューせよ。実装はしない。
確認: (1) 完了タスクのチェック漏れ（git log と突き合わせ）、(2) 粒度が 1 日を超えそうなタスクの分割提案、
(3) 直近で得た知見により順序・内容を見直すべきタスク、(4) §7 未決事項で期限が近いもの。
変更提案は diff 形式で示し、私の承認を得てから TASK.md に反映せよ。スコープ変更に当たる提案は ADR 起票とセットで示すこと。
```

### P-02 マイルストーン着手（各 M の最初に。plan mode で投入）

```text
マイルストーン M<N> に着手する。まず計画を立てよ。実装はまだしない。
1. docs/TASK.md の M<N> 節（目的・タスク一覧・ゲート G<N>）を読む。
2. docs/development-rules.md §3.1 の対応表に従い、docs/design/sbp-design.md の該当章を読む。
3. 以下を含む実行計画を提示せよ:
   - タスクの実行順と並行可能性（TASK.md の番号順を基本に、見直しがあれば理由付きで）
   - 新規に必要なオントロジー概念（あればオントロジー変更手順が先行することを明記）
   - ゲート G<N> の検証方法の具体化（統合テストのシナリオ案）
   - このマイルストーンで ADR が必要になりそうな判断ポイント
```

### P-03 ゲート検証（マイルストーン完了判定）

```text
マイルストーン M<N> のゲート G<N>（docs/TASK.md 参照）を検証せよ。
1. make check を実行し全緑を確認。
2. ゲート定義の統合テスト（G<N> のタスク）を make test-int で実行。
3. ゲートの追加条件（数値目標・再現手順など）を一つずつ検証し、証拠（コマンド出力・計測値）付きで判定表にまとめよ。
4. 全条件が緑なら: docs/TASK.md の M<N> 全タスクを [x] に、docs/STATUS.md の M<N> を完了に更新せよ。
5. 一つでも赤なら: 更新せず、不足を埋めるタスクを TASK.md に追記する提案を出せ（M<N+1> には着手しない）。
```

### P-04 セッション引き継ぎ（中断時）

```text
このセッションを中断する。次セッションが続きから再開できるよう、以下を整理して報告せよ:
1. docs/TASK.md の進行中タスクの状態（何が済み、何が未了か）
2. 未コミットの変更の内容と、コミットすべきか破棄すべきかの判断
3. 次セッションへの申し送り（ハマりどころ、確認待ちの点）
申し送りのうち設計判断に関わるものは ADR の「未決」に、タスク化すべきものは TASK.md への追記として提案せよ。
```

## 2. タスク実行プロンプト（汎用）

### P-10 タスク実行（基本形。大半のタスクはこれで足りる）

```text
docs/TASK.md のタスク <TASK_ID> を実装せよ。
手順:
1. TASK.md §2 の着手条件を確認（依存タスク完了・WIP 2 件以内・設計書該当章の読了）。満たさなければ着手せず理由を報告。
2. docs/development-rules.md §3.1 の対応表に従い docs/design/sbp-design.md の該当章を読む。
3. ブランチ feat/<module>-<topic> を作成して実装。オントロジー変更を伴う場合はコードより先に変更手順（CLAUDE.md）を回す。
4. TASK.md §1.1 の DoD を満たす（make check 緑・テスト・不変条件・docstring・相関 ID ログ）。
5. docs/TASK.md の該当チェックを [x] に更新し、同じブランチに含める。
完了報告の形式: 触った層 / 不変条件への影響（1〜12 のどれに触れたか）/ オントロジー版 / 追加したテスト種別 / ADR 要否。
```

### P-11 タスク分割（1 日で終わらないと判明したとき）

```text
タスク <TASK_ID> は 1 日粒度を超えることが判明した。TASK.md §2 に従い分割せよ。
1. 現時点の成果を、それ単体で DoD を満たす最小の完了点まで仕上げる（中途半端な状態でチェックを付けない）。
2. 残作業を <TASK_ID> の枝番または末尾連番の新タスクとして docs/TASK.md に追記（依存関係を明記）。
3. 分割理由を 1 行で TASK.md のタスク行に残す。
```

### P-12 完了処理（コミット・PR 整形）

```text
タスク <TASK_ID> の完了処理を行え。
1. make check を最終実行し緑を確認（赤なら完了処理を中断して修正）。
2. 生成物（vocab.py / schemas/）に差分がある場合は生成専用コミットに分離。
3. Conventional Commits（feat(<module>): ...）でコミット。TASK.md のチェック更新を含める。
4. PR 本文を作成: 触った層 / 不変条件への影響 / オントロジー版 / テスト種別 / ADR リンク / TASK.md のタスク ID。
```

## 4. 横断プロンプト

### P-20 オントロジー変更（概念の追加・変更が必要になったとき）

```text
<概念の説明> を表現する概念が必要になった。コードを書く前にオントロジー変更手順を実施せよ。
1. 標準（BFO/IAO/SOSA/PROV/OWL-Time/GeoSPARQL/QUDT）と既存 ontology/ に同等概念が無いか確認。あれば再利用で終了。
2. 無ければ ontology/core|domain/*.ttl に定義（必須注釈 4 点）、shapes/ に形状、フルーエント/事象型なら process/*.lp に initiates/terminates。
3. CHANGELOG.md に semver 判定を記す。MAJOR になる場合は中断し、ADR と再接地計画の草案を先に提示して承認を待て。
4. make gen → make ontology-check。生成差分は生成専用コミットに分ける。
5. その後に利用側コードを書く。
```

### P-21 ADR 起票（設計から逸れる判断・技術選定）

```text
<判断の内容> について ADR を起票せよ。docs/adr/0000-template.md の形式に従い、次の番号で docs/adr/ に作成する。
必ず埋めること: 関連する設計書の章、選択肢ごとの利点/欠点/MacBook 上のコスト、不変条件 1〜12 への影響、
オントロジー版（semver 判定）と再接地の要否、未決。
決定が docs/TASK.md のタスク・スコープに影響する場合は、TASK.md の更新案も同時に提示せよ。
```

### P-22 バグ修正

```text
バグ: <現象の説明>
修正手順（CLAUDE.md テスト方針に従う）:
1. 再現テストを先に書き、赤を確認する（修正より先）。
2. 原因を特定し、どの不変条件・層ルールに関わるかを報告。
3. 最小の修正を行い、再現テストと make check が緑になることを確認。
4. 同種バグを機械的に防げるなら、性質テストまたは lint 規則の追加を提案せよ。
```

### P-23 セルフレビュー（PR 前）

```text
現在のブランチの差分をレビューせよ。観点:
1. CLAUDE.md の不変条件 1〜12 への違反（特に: 直書き IRI、naive datetime、生スコアの belief 混入、UPDATE/DELETE、層依存の逆流）
2. 「やってはいけないこと」（CLAUDE.md 最終節）への抵触
3. 該当する .claude/rules/*.md の詳細ルールとの不整合
4. テストの欠落（DoD §1.1 に照らして）
指摘は 深刻度順に、該当ファイル:行 とともに列挙し、修正まで行え。
```

### P-24 ドキュメント同期チェック（規約・構成を変えたあと）

```text
直近の変更がドキュメント群と整合しているか検査せよ。対象: README.md のドキュメントマップ、

不整合を列挙し、修正して同じブランチに含めよ。進捗の記述が CLAUDE.md に混入していないことも確認すること。
```

### P-25 未決事項の解決

## 6. リカバリ・例外系プロンプト

### P-40 ブロックされたとき

```text
タスク <TASK_ID> が <理由> でブロックされた。次を行え:
1. 回避可能か検討（設計を逸れない範囲で）。逸れるなら案を ADR 草案として提示し、承認を待つ。
2. 回避不能なら: TASK.md の当該タスクに [~] とブロック理由を記し、依存しない次タスクを P-00 の基準で提案せよ。
3. 不明な業務仕様が原因なら推測で埋めず、TODO(question) をコードに、未決を ADR に残して質問を列挙せよ。
```

### P-41 make check が壊れているとき（自分の変更以外が原因）

```text
make check が現在のタスクと無関係な理由で赤い。
1. 原因を特定し、直近コミットとの関係を git log / git diff で切り分けよ。
2. 修正が小さければ fix/ ブランチで直し、再現テストを添えよ（P-22 の手順）。
3. 大きければ TASK.md に修復タスクを緊急で追記し、現在のタスクを中断して修復を優先せよ（壊れた main の上に積まない）。
```

### P-42 計画と実装が乖離してきたとき

```text
実装が docs/TASK.md・docs/design/sbp-design.md と乖離している疑いがある: <気づいた点>
1. 乖離点を列挙し、それぞれ「実装を設計に合わせる」か「設計・計画を改める（ADR 必須）」かの判断材料を示せ。
2. 私の判断後、選ばれた側の修正を実施せよ。設計書本文の変更が必要な場合は、変更箇所を明示した上で改版（版数と日付の更新）として行え。
```
