## 実装中に判明した事実

設計書の前提が外れた箇所と、テストが暴いた欠落の記録。**この節が本書の主眼**である。

### 1. MinIO の公開イメージが取得できなくなっていた（ADR-0003）

`make up` が `pull access denied` で失敗。Docker Hub と quay.io の両方にレジストリ API で
問い合わせ、タグを明示しても **HTTP 401** が返ることを確認した。匿名取得の経路を失っている。

`make bootstrap` から新規環境で再現できなければゲート G0 の条件を満たせないため、S3 互換の
SeaweedFS に置換した（サービス数は 4 のまま、API 契約は不変）。

**教訓**: 設計書がイメージ名を指定していても、それが取得できる保証は設計時点のものでしかない。
`make bootstrap` の再現性をゲート条件に入れておいたことで、この種の腐りが早期に検出された。

### 2. Oxigraph の公式イメージは distroless で healthcheck が書けない（ADR-0004）

シェルも wget も無く、CLI の `oxigraph query` は `--location`（ローカルストア）しか取れない。
稼働中のサーバと同じ location を開くと RocksDB のロックで競合するため、**コンテナ内から HTTP
疎通を確認する手段が存在しない**。

形だけの healthcheck（`oxigraph --version`）を置く選択は棄却した。バイナリが動くことしか
確認せず、サーバが落ちていても healthy になる——healthcheck が無い状態より悪い。疎通検査を
統合テストの fixture とワーカー起動時に移した。

### 3. 設計書が想定した RDF-star 記法が使えなくなっていた（ADR-0005）

設計書 §6.6 のクエリ例は「引用三つ組を**主語**に置く」旧 RDF-star 記法を使っている。
pyoxigraph 0.5 ではこれが `TypeError` になる。RDF 1.2 で quoted triple が **triple term** に
再定義され、**目的語位置にのみ出現できる**ようになったためである。

スパイクで確認した結果、`?a rdf:reifies <<( ?s ?p ?o )>>` の形なら as-of クエリまで動作する
（埋め込みストアと HTTP サーバの両方で検証）。要件は満たせるが記法が違う。設計書・層別ルール・
ADR に反映した。

**教訓**: `docs/PROMPT.md` の M0-11 プロンプトに「満たさない場合は実装に入らず ADR 草案を
提示せよ」と書いておいたことが効いた。実装前のスパイクで分かったため、手戻りは記法の決定だけで
済んだ。

### 4. Python の RML プロセッサが使えない（ADR-0006）

`morph-kgc` は依存に `pyoxigraph<0.4` を持ち、ADR-0005 で必須の 0.5 系と**衝突する**。さらに
duckdb / pandas / geopandas / neo4j / databricks を引き込み、4 サービス制約と相容れない。
`pyrml` は 2016 年で更新停止。

設計書 §7.2 の考え方（キー・必須制約・多重度の保存を写像の不変条件として検査する）は維持し、
実装手段だけを最小の YAML DSL に変えた。3 つの保存性を**宣言の一部**として持たせたので、
宣言の段階で保存性を壊す設定（キー以外を `external_id` に混ぜる、キー列を必須にしない）を
弾ける。

### 5. 自前の正規分布分位点が大きく外れていた

時刻ずれの許容プロファイル（類型 3 の判定閾値）に使う分位点を有理近似で書いたところ、
p95 が **565 秒**（正しくは 307 秒）になっていた。閾値がずれると時間不一致の判定が狂う。
標準ライブラリの `statistics.NormalDist` に置き換えた。

**教訓**: 「依存を増やさない」は良い方針だが、**標準ライブラリにあるものを自前で書く理由は無い**。
数値の正しさをテストで押さえていたため検出できた（設計書 §3.6 の「MES ±5 分」と突き合わせる
テストが落ちた）。

### 6. BOCPD の変化点確率がデータに反応していなかった

事象昇格の変化点検出が 1 件も検出しない。調べると変化点確率が**ハザード率一定**（0.0083）に
張り付いていた。原因は変化点項に「継続中の run の予測確率」を使っていたこと。成長項と同じ
予測確率が掛かるため、正規化で打ち消されてデータを一切見なくなる。

新しい区間は過去データを持たないので、その最初の観測は**事前予測**に従うのが正しい。修正後は
変化点 0.153 対 平常 0.004（35 倍）になった。

さらに判定基準を絶対閾値（0.3）からベイズ因子（事後 ÷ 事前、既定 5.0）に変えた。絶対閾値では
適切な値がハザード率に依存して扱いにくい。ハザード 1/60〜1/300 で同じ変化点が出ることを
テストで確認した。

### 7. SHACL の `sh:severity` を書く位置を誤り、設計の真逆の挙動になっていた

`sh:severity` は**シェイプの属性**であり（SHACL 仕様 §2.1.3）、`sh:sparql` の制約ノード内に
書くと無視されて既定の `sh:Violation` になる。そのため整合制約（排他フルーエントの衝突、
非対称な排他宣言）が Violation として動き、「登録して不一致候補にする」はずのものが
**隔離されていた**。

これは設計書 §3.9「検証は拒否ではなく証拠生成」の真逆であり、検出したい状態が消える。
`sh:severity` をシェイプ側に移し、Warning が登録を止めないことをテストで保証した。

**教訓**: 「Warning は登録を止めない」というテストを書いていたから見つかった。形状が通ることだけを
確認していたら、本番で不一致が静かに消え続けていた。

### 8. テストがオントロジーの欠落を 2 件暴いた（オントロジー 0.3.0）

SynthWorld に「合成世界は事象計算で説明できる状態変化しか作らない」という不変条件テストを
置いたところ、2 件の不整合が出た。

- **Faulted が再起動で解消していた。** 事象計算で `faulted` を terminates するのは `maint_end`
  だけなので、合成世界が「説明できない状態変化」を作っていた。整合残差は `A∘f` と `T∘A` の
  ずれを測るものなので、基準となる世界が事象計算と矛盾していると指標そのものが無意味になる。
- **`Accessible` を変化させる事象型が 1 つも無かった。** 設計書 §9.1 でアクションの物理前提
  （`P(Accessible(?pump)) >= 0.8`）に使われるのに、成立・不成立にする経路が無く、永久に初期値の
  ままになる。物理に即して 4 件追加した（`StopCmd` / `Fault` / `MaintStart` が initiates、
  `StartCmd` が terminates）。

あわせて `make ontology-check` に検査を追加した: **すべての FluentType は少なくとも 1 つの
EventType に変化させられること**。既存の `EventTypeShape`（すべての EventType は何かを
変化させる）の双対であり、片側しか検査していなかったためにこの欠落が通っていた。

### 9. `ontology-check` の生成物鮮度チェックが偽陽性を出していた

git status の前後比較で判定していたため、作業ツリーの状態に依存して誤検出した。内容ハッシュ
比較に変えた。さらに `make lint` の整形が生成物を書き換えて鮮度チェックと循環する問題があり、
生成の最終段で `ruff format` をかけて出力を正規化した。

### 10. 二時制クエリが拠点で絞っていなかった

統合テストで、ある拠点のストアが**他拠点のグラフまで読んでいる**ことが分かった。設計書 §6.3 は
グラフを `<modality>/<site>/<ontologyVersion>` で分割し、中央がフェデレーションすると定めている。
既定で自拠点のみを見るようにし、横断は `all_sites=True` を明示する形にした。

### 11. 事前に継続確率を足し込むと信念が飽和して観測が効かなくなっていた

**M3-02 の初版の欠陥。** 半マルコフの事前を作るとき、滞在時間分布の生存比（長寿命の状態では
対数オッズ ≈ +9）を事前に**加算**していた。結果、稼働が長く続いた設備の事前が 1 に飽和し、
「停止している」というプローブ出力が事後をほとんど動かせなくなった。

継続確率は「崩れにくさ」であって「真である証拠」ではない。マルコフ遷移
`事後 × 継続確率 + (1 − 事後) × 開始率` に直し、計画は重み 0.2 の**混合**として入れた
（上書きでも加算でもない）。設計書 §14 の事後 0.14 が再現できるようになった（実測 0.1302）。

### 12. 抑制規則が「系統誤差があること」だけで働いていた（2 段の欠陥）

**設計書 §8.2 は抑制を「信頼性モデルで説明できる系統誤差」に限定している。** 実装は 2 段階で
これを緩めていた。

1. 初版は「証拠の記録が何らかの系統誤差に当てはまる」だけを条件にしていた。月末一括計上
   （記録が**いつ入ったか**の偏り）で**状態の食い違い**まで抑制できてしまう。記録が遅れて
   入ったことは、記録が別の状態を主張していることの説明にならない。系統誤差の種別ごとに
   抑制してよい類型を限定した（`_BIAS_APPLIES_TO`）。
2. それでも G3 の注入テストで、注入した時間不一致が抑制された。原因は**規模を見ていない**
   こと。シフト境界の丸め（規模 8 時間）が 48 時間のずれまで説明してしまう状態だった。
   偏りが存在することと、その偏りがこのずれを説明することは別である。規模がずれを覆って
   いるかを第三の条件に加えた。終端の無い不一致は「規模で覆えた」と主張しない。

抑制は照合エンジンで最も危険な機能である（「不都合な不一致を消す装置」に転用されうる）。
条件を 3 つに増やしたのは慎重さではなく、1 つでも落ちると万能になるからである。

### 13. 事象計算の `.lp` が一度も実行できない状態だった

**M3-08 で clingo を回して初めて分かった。** `ontology/process/equipment-maintenance.lp` の
`clipped/4` が安全でない変数（`T0` と `T` が比較にしか現れない）を持ち、**接地できなかった**。
慣性規則が働かないので `holds_at` が一切導出されない。

M2 までは事象計算を Python 側（`bridge/lifting.py`）で実装していたため、`.lp` は「記号遷移 T の
宣言」として読まれるだけで実行されていなかった。`make ontology-check` は TTL と `.lp` の
**対応**（initiates / terminates の整合）を検査するが、プログラムとして**動くか**は検査して
いなかった。M3-08 の単体テストが接地・慣性・排他・前提条件を実行して確かめるようになった。

同時に、プログラム部名をファイル名から作っていたため `process/` と `norms/` に同名ファイルを
置くと後勝ちで規則が消えることも見つかった（親ディレクトリ名を含めて一意にした）。

### 14. 類型 3 の順序違反規則が存在しない順序を発明していた

観測時刻・記録時刻の前後を `<` で比較し、「観測の順序と記録の順序が違えば違反」としていた。
同時刻の対では等号が「より前ではない」に落ちるため、**片側だけが同時刻の対がすべて順序違反**
になる。同時刻の対に矛盾しうる順序は無い。等号の対を明示的に除外した。

### 15. 設計書のインタフェースが層依存と衝突した（ADR-0007）

設計書 §4.3 の `WorldModel` は `probe(z, probeIds[])` と `explain(z, probeId)` を持つ。プローブ ID を
引数に取る以上、`worldmodel` が `bridge` の型を知る必要があり、**層依存（`worldmodel ← bridge`）と
「WM は記号を決めない」という責務分担の両方に反する**。import-linter の契約が機械的にこれを
禁じているので、実装に入った時点で衝突が表に出た。

代わりに `attribute(state, weights)` を置いた。`weights` は線形汎関数の係数（線形プローブの重みが
そのまま入る）で、WM はそれが何の概念なのかを知らない。利用者から見た説明の情報量は変わらない
——説明サービスが受け取る `LatentSide` はプローブ ID・出力・WM 版・帰属をすべて持つ。

同じ理由で `health()` の整合残差も引数で受け取る形にした。渡されなければ 0 のままで、
「評価していない」ことが呼び出し側に見える。

### 16. 監査隔離マスクは `core` に置くしかなかった

`AuditMask` は記録尤度の計算（`reasoning`）と記号条件付けの生成（`worldmodel`）の**両方が必須
引数に取る**。しかし `worldmodel` は `reasoning` を import できない。CLAUDE.md の「層をまたぐ
結合は `core` の型と `eventlog` のイベントだけ」に従って `core/audit.py` に移した
（`reasoning.audit` は再輸出として残し、推論層から見た読み口を保っている）。

M3 の時点では `reasoning` 内にあっても動いていた。層をまたぐ契約であることが、実際に 2 つ目の
利用者が現れて初めて分かった。

### 17. 時間順を前提とする損失項をシャッフルしたバッチに当てると潜在が潰れる

`smoothness_penalty`（連続する潜在の差を罰する慣性項、設計書 §4.6 の L_phys の最小形）を
既定のバッチ（毎エポック並べ替え）に当てると、「無関係な標本どうしを近づける」ことになる。
実測で `latent_std` が 0.845 → 0.079 に落ち、段階ゲートが落ちた。

`contiguous_batches` 引数を足し、既定を偽にした。気付かずに時間順を仮定するほうが危険なので、
時間順が必要な項を使うときに明示させる形にしている。

### 18. 潜在の部分的な崩壊は AUROC に出ず ECE に出た

jepa_ts の分散項（VICReg）を実質 0 にして比較した:

| 構成 | latent_std | AUROC | ECE |
|---|---|---|---|
| 健全 | 0.9714 | 1.0000 | 0.0048 |
| 分散項なし | 0.1573 | 0.9984 | 0.0349 |

**分離はできるが確信度が壊れる。** ECE は昇格ゲートの上限 0.05 の手前まで悪化したが、AUROC は
0.9984 で基準（0.85）を大きく上回ったままだった。昇格ゲートが AUROC ∧ ECE ∧ 整合残差の AND に
なっている理由の実測的な裏付けで、AUROC だけを見ていると潰れかけた潜在を active にする。

### 19. 潜在索引の次元は「版ごとに固定」では足りなかった

`.claude/rules/knowledge.md` は「次元 D は `wm_version` ごとに固定。次元が変わる WM 更新は新
テーブル `latent_index_v<N>` を作る」と定めている。実装して分かったのは、**命名規約だけでは
運用で表を取り違える**ことである——`latent_index_v2` という名前からは次元が読めない。

`latent_index_registry(wm_version, table_name, dim)` を置き、アプリは登録表を引いてから書く
形にした。未登録の版では書き込みが成立せず、次元の食い違いは INSERT 前に落ちる。表名は
`latent_index_d<次元>` にして運用者が名前で判断できるようにした（規則の `v<N>` から逸れるが、
版と表の対応は登録表が持つので命名は補助情報である）。

### 20. 設計書のインタフェースが層依存と衝突した（2 件目）

M4 の ADR-0007 と同じ種類の衝突が M5 でも出た。``encode_intervention`` を
``ActionContract`` を受け取る形で書いたところ、``reasoning`` が ``actions`` を import することに
なり import-linter が落ちた（層は ``reasoning ← actions``）。

ADR には至らなかった。**介入の符号化に必要なのは「どのアクション型か」だけ**で、前提や効果は
要らない——契約を受け取る設計は、必要以上のものを要求していた。アクション型 IRI を取る形に
直して解決した。設計から逸れたのではなく、設計を実装に落とすときの引数の取り方の問題である。

### 21. 契約の CURIE 展開漏れは「静かに全アクションが実行不能」になる

``ActionContract`` の ``action_type`` / ``targets`` / ``compensation`` だけ CURIE を展開し、
前提と効果の中（``fluent``、``record_type``）を忘れていた。結果、前提の ``ent:Accessible`` が
展開されないまま残り、呼び出し側が渡す完全 IRI の信念と一致せず、**全アクションが「信念が無い」
として実行不能**になった。

エラーではなく「前提未達」として静かに落ちるのが厄介である。前提検証が「知らないことを満たして
いるとみなさない」設計（これ自体は正しい）と組み合わさると、展開漏れが安全側に倒れて気付きにくい。
スモークテストで前提が通らないことに気付いて見つけた。

### 22. 片側が未観測の期待を「成立」と判定していた

``Expectation.verify`` の初版は「記号側が通って潜在側が未観測」でも ``Fulfilled`` にしていた。
観測できていない期待を成立と呼ぶと、**検証していないものが学習信号に混ざる**。宣言されている面
すべてに判定が付いて初めて ``Fulfilled`` にするよう直した（単体テストが捕まえた）。

### 23. 訂正提案が学習信号に数えられていなかった

設計書 §8.2 の表は「物理が正しい → 記録訂正（書き戻し提案）」を第一の処置に挙げているが、
付録 A.2 の ``learning`` には対応する欄が無い（``labels_emitted`` / ``reliability_updates`` /
``concept_candidates``）。そのまま実装したため、**訂正提案だけを生んだ解決が「何も学ばなかった」
として ``Resolved`` に留まった**。

``corrections_proposed`` を加法的に追加した。G5 の統合テスト（ワークドエグザンプルの完走）が
これで落ちて見つかった——単体テストでは訂正提案と信頼性更新を同時に渡していたので通っていた。
**統合テストが「部品は正しいが繋ぐと通らない」を捕まえた**例である。

### 24. 被覆率は「区間を広げる」だけで買える（ゲートの設計の問題）

ゲート G5 の数値条件は「予測被覆率 ≥ 0.85」である。最初は固定幅の区間で持続予測を作り、先行
300 秒の被覆率が 0.800 に落ちた。**幅を広げれば通る**が、それは較正ではなく調整である。

設計書 §8.5 の conformal を実装し（``conformal_halfwidth``）、較正データの残差分位点を半幅に
した。交換可能性の仮定の下で名目被覆が保証され、手で決める余地が無い。結果:

| 先行時間 | 被覆率 | CRPS | 区間幅 |
|---|---|---|---|
| 60 s | 0.9500 | 0.0372 | 0.0338 |
| 300 s | 0.8667 | 0.1548 | 0.9801 |

**ゲートは通ったが、先行 300 秒の区間幅は 0.98——ほぼ [0,1] 全域である。** 被覆率 0.87 はそれで
買っている。CRPS と ``reliable_lead_time``（60 秒）が「実際に使える地平は 60 秒まで」を示す。
設計書 §8.3 が「地平ごとの信頼できる先行時間を公開する」と言っているのはこのためで、被覆率を
単独の合格条件にすると無情報な予測が通る。**G6 以降のゲートに数値条件を足すときは、指標を 1 つ
だけ見ない。**

### 25. 「未知概念を仕込む」のが合成世界では難しい

ゲート G6 は「SynthWorld に未知概念を仕込み、発見できるか」を見る。実際にやってみると、
**仕込める概念が無かった**。

- ``VibrationAnomaly`` は 87.5% の時間成立する単一区間（02:41–06:11）。保留窓が全て真で
  AUROC が定義できない。
- ``Accessible`` は保留窓に両クラスが入る唯一のフルーエントだが、SynthWorld では実質的に
  ``Running`` の否定である。つまり「Running プローブが反応しない領域」= ``Accessible`` で、
  **発見がやや自明になる**。

``Accessible`` を使って機構（低被覆クラスタ → 弱ラベル → プローブ → 再接地）が通ることは確かめ、
**限界をテストの docstring とゲートの記録に明記した**。数値（AUROC 0.9995）は機構が動くことの
証拠であって、「独立した未知概念を見つけられる」ことの証拠ではない。

合成データのゲートは「機構が動くこと」までしか示せない、という一般的な教訓でもある。G2 の
AUROC 1.0 と同じ構図で、**測れたことと主張できることを分けて書く**必要がある。

### 26. 劣モジュラ性と「質問しすぎない」は別の機構である

スケジューラの最初の実装で、「同じことを 2 度確かめるバッチを作らない」ことを劣モジュラ性に
期待していた。実測すると、信頼度 0.95 の観測の後も残存エントロピーは 0 ではないため、
**コストが極小な重複観測は効用が正のまま残る**。

これは正しい挙動である。安いセンサ測定をもう 1 回するのは実際に少し情報を増やす。人への重複
質問を止めるのは劣モジュラ性ではなく**質問頻度の上限**の役目だった。2 つの機構を混同していた。

割引係数の足し引きではなく**残存エントロピーの追跡**に変えたのも同じ検討から出ている。割引係数
では「信頼度 0.95 の観測を 2 回」が「1 回の 2 倍の情報」になりうる（0.9 + 0.9 > 1.0 を 1.0 で
クリップするので）。残存エントロピーなら複利で正しく減衰する。

### 27. LLM をホットパスから外すのは「層」では表せない

不変条件 11（LLM をホットパスから呼ばない）を import-linter で検査しようとして、``sbp.reasoning``
全体を禁止できないことに気付いた。同じ層に**ホットパス（信念更新・照合）と非ホットパス（概念
発見・説明）が同居している**。

契約はモジュールを名指しする形にした（``sbp.reasoning.belief``, ``sbp.reasoning.coupling``,
``sbp.reasoning.rules``, ``sbp.reasoning.reconciliation``, ``sbp.bridge.lifting``,
``sbp.bridge.probes``, ``sbp.bridge.calibration``）。層の粒度では表せない不変条件があり、
その場合はモジュール単位で明示する。G6 のテストでも対象モジュールの本文を直接確かめ、契約が
誤って外されたことに気付けるようにした。

### 28. 不変条件 7 が「較正していない旧版」を作らせないので、版の違いは学習量で付けた

G7 のテスト設計は「プローブ v1 で接地 → v2 に上げて再接地 → as-of で両方の判断が返る」である。
最初は v1 を**較正していない版**にしようとした——現実の版上げでは較正手順自体が変わることも
あるからだ。``predict()`` が拒否した。不変条件 7（``belief`` には較正済みの値だけ）が、
較正されていないプローブから信念を作る経路をそもそも塞いでいる。

**不変条件が先に立っていることの確認になった**が、同時にテストで表現できる版差が狭まった。
v1 = 30 エポック、v2 = 500 エポック + 較正、という学習量の差に落とした。現実の版上げに近い形で
はあるものの、「アルゴリズムを変えた版上げ」の挙動は確かめていない（G7 の記録に明記した）。

### 29. 「runbook に従って第三者が実行できる」は機械では検査しきれない

ゲート G7 の条件に「runbooks に従って別セッションが再接地を実行できる」がある。自動テストに
できるのは**手順書が参照する記号が実在すること**まで——``plan`` / ``run`` / ``RegroundingReport``
が ``sbp.knowledge`` にあるか、という検査である。手順の分かりやすさ、前提の書き漏れ、
「この状態のときどうするか」の抜けは、人が読んで実行しないと分からない。

G7 を「条件つき通過」と記録した。**何を検査して何を検査していないかを区別せずに「通過」と
書くと、次に読む人は全部が検査済みだと受け取る。**

### 30. 二時制の UI に正規化キャッシュは使えない

M7-04 で GraphQL クライアント（Apollo / urql）を入れるか検討して、やめた（ADR-0008）。
正規化キャッシュは「同じ ID なら同じエンティティ」を前提に、新しい応答で古い値を上書きする。
**二時制ではこの前提が誤りである**——``asOf`` が違うだけの同じ ``subject`` は別の事実であり、
上書きすると「過去の判断を今の判断で塗り潰した」表示になる。

キャッシュを無効化して使うなら入れない方が単純で、依存が減ると型検査とテストが数秒で終わる。
**検査が遅いと検査しなくなる**ので、これは速度の話ではなく「完了の定義を毎回満たせるか」の話
である。

### 31. UI で最も重要な判断は「何を入力させないか」だった

不一致キューに「正しい値」の入力欄を置かなかった。解決の入力は**どの前提が崩れていたか**の
分類（記録が誤り / 観測が誤り / 定義の食い違い / 系統的な偏り / 判断不能）であり、真偽の宣言
ではない。「正」フラグを作らない（CLAUDE.md のやってはいけないこと）は、データモデルの話だと
思っていたが、**UI の形に出ないと意味が無い**ことが分かった。入力欄があれば人はそこに真偽を
書き、基盤は受け取ってしまう。

同じ理由で、理由の記入を必須にした（10 文字以上）。種別だけでは学習信号にならない——何を見て
そう判断したかが残らないと、後で信頼性モデルの更新を説明できない。設計書 §8.3 の「解決入力が
学習信号になる」は理由まで含めての話だった。

### 32. 「0 件」と「経路が動いていない」を UI が区別しないと、静かな故障が緑に見える

期待ボードの違反列、不一致キュー、概念提案のいずれも、空のときに注意書きを出すようにした。
「違反 0 件」と「違反を検出する経路が走っていない」は違う情報である。前者は良い知らせだが、
後者は障害であり、**画面上はどちらも空のリストに見える**。

読み込みが失敗したときも同じ問題がある。最後に成功した内容を出したまま黙っていると、空の
キューが「不一致なし」として読まれる。失敗を明示し、「空のキューを不一致なしと読まないこと」
と書いた。

### 33. プライバシー検証は陽性対照が無いと「測れていない」ことに気付けない

潜在復元攻撃を書いていて、最初の実装は「個体を同定できなかった」で成功としていた。これは
**攻撃の実装が壊れていても同じ結果になる**。区別するには、復元できるべきものが同じ攻撃で
復元できることを確かめる必要がある。

``PrivacyAudit.is_conclusive`` を入れ、陽性対照が失敗した監査は「安全」ではなく「測れていない」
として扱う（``leaks`` は安全側に真を返す）。シークレット走査でも同じ構えを取り、偽の鍵を食わせて
検出されることをテストにした——実装直後に自分のテストファイルを 3 件検出したので、走査が
空振りしていないことは確認できている。

攻撃を 2 種類に分けたのも同じ検討から出ている。**属性復元が成功するのは違反ではない**
（潜在から軸受温度が戻るのは基盤が機能している証拠、実測 R² > 0.8）。危険なのは個体同定だけで、
混同すると「潜在は何も表現してはいけない」という使えない結論になる。

### 34. ABAC を「既定は拒否」にすると既存のテストが落ちる。それが正しい

API に ABAC を入れたとき、``principal_resolver`` 未設定で信念クエリが全拒否になり、既存の
API テスト 3 件が落ちた。「未設定なら通す」経路を残せば落ちなかったが、**それは開発中の全開放
がそのまま本番に残る形**である。テスト側に要求者を渡すように直した。

拠点の判定でも同じ選択をした。グラフ名から拠点が取れなければ拒否する——「拠点が判らない＝
誰でも見てよい」と解釈すると、グラフ名の規約が変わった日に全拠点へ漏れる。

唯一「許可があれば見せる」にしなかったのが人に関わる概念である。外観埋め込み・従業員 ID は
ロールが許可していても返さない（不変条件 9）。**許可の設定ミスがそのまま個人情報の漏洩になる**
ので、許可の内側ではなく外側で止める。

### 35. ワーカーの「処理件数」は取得件数ではない

``step()`` の戻り値を「取り込んだイベント数」にしかけて、やめた。入れなかったイベント
（フルーエントを取り出せない、真偽でない、時刻が戻った、監査隔離）が件数に混ざると、
**何も信念を更新していないのに「100 件処理した」と見える**。戻り値は信念を更新した件数にし、
入れなかったものは理由別に ``ingest.skipped`` へ積んだ。

静かに捨てないことが要点である。パーティション設定の誤りは「実体内で時刻が戻った」の件数として
現れるが、捨てた記録が無ければその兆候が消える。

### 36. イベントが無いループでも周期判定を進める必要がある

最初の実装は「イベントが取れなければ早期 return」だった。これだと**イベントが止まっている間は
実体間結合も止まる**。結合はイベントとは独立に回すべき処理（信念の整合を取る）なので、
取得件数で分岐してはいけない。所見 32（「0 件」と「経路が動いていない」）と同じ構図が、
ワーカーのループにも現れた。

``sink`` が無いときに計算も止めないのも同じ理由である。書き込み先が無いときに計算まで止めると、
配線の誤りが「何も起きない」としてしか現れず、source と sink のどちらが欠けているか分からない。

### 37. 監査隔離はプローブ由来と記録由来で挙動が違う（意図的）

配線のテストで「監査対象の情報源から来たイベントは除外される」と書いたら落ちた。
``AuditMask.excludes_event`` は**記録由来のイベントだけ**を除外し、プローブ由来は除外しない。

これが「物理から記録を監査する」ことの中身である（不変条件 6）。物理観測まで除外したら、
記録を疑うための独立な証拠が無くなり、監査がそもそも成立しない。テストの前提が誤っていたので、
**両方の挙動を明示的に検査する形**に書き直した——非対称性は意図なので、テストで固定する価値がある。

### 38. import 境界の検査が `sbp` だけを見ていて、実運用で動くコードが外れていた

import-linter の `root_packages` が `["sbp"]` だけで、``services/`` と ``scripts/`` が
検査対象の外にあった。契約 7 本はすべて KEPT だったが、**ワーカーから真値（オラクル）を読んでも
検出されない状態**だった——不変条件 10 を機械で守っているつもりで、実運用で動く側が抜けていた。

`root_packages` に両方を足し、オラクル境界と LLM SDK の契約に `services` / `scripts` を加え、
「ワーカーは API 層を経由しない」契約を 1 本追加した（層を 1 周して依存が循環する形を防ぐ）。

**追加した契約が実際に落ちることを、違反を仕込んで確認した。** 落ちない契約は装飾である。
``services.runtime`` に ``from sbp.api import create_app`` と ``from sbp.testing.synth import
SynthWorld`` を一時的に入れ、両方が報告されることを見てから戻した。

このコミットで ``services/belief_worker.py`` の import を増やしたばかりだったので、
穴がちょうど広がった直後に気付いた形になる。

### 39. 「脆弱性なし」は skip を数えないと読めない

``pip-audit`` を入れて X-05 を実行可能にした。``--strict``（skip を失敗にする）は使えない
——sbp 自身が editable install なので PyPI に無く、必ず skip される。

``--strict`` 無しで走らせると、**照会できなかったパッケージがあっても「No known
vulnerabilities found」と出る**。所見 33（陽性対照）と所見 32（0 件と経路が動いていない）と
同じ構図である。``make audit`` で skip の表を読み、sbp 以外が skip されていたら落とすようにした
（この awk の判定も、偽の出力を食わせて動くことを確認済み）。

``make check`` には入れていない。脆弱性 DB の照会にネットワークが要り、`make check` は
Compose もネットワークも不要で通る、という方針を崩したくないためである。CI では独立したジョブに
し、`check` に依存させていない——**脆弱性は自分のコードの状態と無関係に増える**ので、lint が
落ちている間も結果は知りたい。

2026-10-03 の実施結果: ``uv lock --upgrade`` は差分なし（112 パッケージ、既に最新解）、
既知の脆弱性 0 件。

### 40. npm 側に実在の脆弱性があった（5 件、うち critical 1 件）

所見 39 で「npm 依存は未照会」と書いたので走らせたら、**5 件見つかった**（critical 1 / high 1 /
moderate 3）。すべて開発ツール側（vite の開発サーバ、vitest の UI サーバ、esbuild）で、
``vite build`` の成果物には入らない。それでも直した理由は 2 つある。

1. 開発者が信頼できない網で ``npm run dev`` を動かす経路は実在する（esbuild の脆弱性は
   「任意のサイトが開発サーバにリクエストを送って応答を読める」というもの）。
2. **「本番バンドルに入らないから無害」は、入らないことを毎回確かめ続ける前提に立っている。**
   その確認を省く日が来る方が、依存を上げるより高い。

``vitest`` を 4 系から 5 系（semver major）に上げて 0 件になった。61 件のテストと型検査、
ビルドはいずれも無変更で通り、バンドルサイズも同一（gzip 77.39 kB）。

**依存を少なく保った判断（ADR-0008）がここで効いた。** GraphQL クライアントと UI ライブラリを
入れていないので、照会対象が 199 パッケージ（ほぼ全部がビルドツールの推移的依存）で済み、
major 上げの影響範囲も小さかった。

未照会が 1 つ残る: コンテナイメージ。これは ``docs/PROGRESS.md`` の既知の制約に記録した。

### 41. ポーリング型の配線は at-least-once を壊す

ワーカーの配線を「``(件数) -> イベント列`` を返す source」として実装し、コミットした。翌の作業で
実物の ``KafkaEventConsumer`` を差そうとして、**この形が冪等性を壊す**ことに気付いた。

``sbp.eventlog.process_once`` は**副作用の前に**冪等記録を付ける（付けてからハンドラを呼び、
ハンドラが失敗したら記録を取り消す）。ポーリング型だと「ハンドラ = バッファに溜めるだけ」に
なるので、溜めた後に落ちたイベントは**「処理済みなのに信念に入っていない」状態で永久に失われる**。

ハンドラ自身が本体の仕事（信念更新と書き込み）をする形に直し、ワーカーは「このハンドラで最大
N 件処理してくれ」と driver に頼むだけにした。単体テストは一覧からハンドラを呼ぶ driver を渡し、
実運用は consumer を渡す——**ロジックのある部分（ハンドラ）は両方で同じものが動く**。

副作用として構築の順序が決まった。``KafkaEventConsumer`` はハンドラを構築時に受け取るので、
ワーカー → consumer → driver の順でしか組めない（``attach_driver`` を足した理由）。

**統合テストでこの性質を直接検査した**: ``sink`` を必ず失敗させるワーカーで 1 件流し、
``processed_events`` に記録が残っていないことを確かめる。残っていれば再配送でも飛ばされ、
その信念は永久に欠ける。

### 42. 共有トピックに新しい consumer グループを当てると履歴を全部読む

端から端までの統合テストを、最初は ``make seed`` が作る実在のトピック
（``siteA.bridge.physical``）で書いた。「テスト専用トピックは本番と同じ経路を通らない」と
考えたからだが、**これは誤りだった**。

consumer は ``auto_offset_reset="earliest"`` なので、テストごとに新しい consumer グループを
作ると**トピックの履歴を最初から読む**。他のテストが過去に流したイベント（``StopCmd`` の
古いイベント）が先に届いて ``max_events`` の枠を食い潰し、3 件期待したところに別のイベントが
入って落ちた。

テストごとにトピックを作る形に直した。トピック名は ``topic_name()`` で組み立てるので**命名規約
は本番と同じ経路を通る**——「本番と同じ経路」が指すのは機構（producer / consumer / 冪等ストア /
グラフストア）であって、トピック名そのものではなかった。

このテストが落ちたおかげで、実ストリーム上で実体単位の順序が保たれていることも確かめられた
（順序が崩れていれば「時刻が戻った」で捨てられて件数が合わない）。

### 43. 結合の事後をフィルタに書き戻すと複利で積み上がる

実体間結合（loopy BP）を周期サイクルに繋ぐとき、結果をどう扱うかで 2 通りある。

1. 結合の事後をフィルタの状態に書き戻す。
2. アサーションとしてだけ記録し、フィルタは触らない。

1 を選ぶと**同じ関係からのメッセージが周期ごとに複利で積み上がる**——2 周目は 1 周目の結合済み値
を事前としてまた結合するので、関係が強いほど無根拠に確信が増える。2 を選んだ。フィルタは
「自分の証拠だけによる推定」のまま保ち、結合は周期ごとの調整として別の文に書く。

付随して、**動かなかった信念は書かないことにした**（変化 0.01 未満）。追記専用なので、変化の
ない文を毎周期足すとグラフが単調に膨らむ（60 秒周期なら 1 日で 1440 件/実体）。二時制クエリの
履歴が結合の周期で埋まり、「いつ信念が変わったか」が読めなくなる。

収束しなかった結果は**書く**。``converged`` が偽でも「まだ振動している」という情報であって
無意味な値ではない。ただしログに出し、頻発するなら減衰係数と反復上限を見直す材料にする
——黙って捨てると、結合が機能していないことに気付けない。

### 44. ローカル名と IRI が混ざると結合が静かに 1 件も成立しない

前向きフィルタはフルーエントを**ローカル名**（``Running``）で持ち、集約規則
（``aggregatesAs``）は**フルーエント型 IRI** で引かれる。結合の鍵をローカル名のまま作ったので、
``PartWhole`` を 1 本も構築できず、**例外も警告も出さずに「結合対象なし」として通った**。

テストが「ラインの文が 2 件（フィルタ + 結合）になる」を見ていたので落ちて気付いた。件数を
見ずに「結合を呼んでいる」ことだけ確かめるテストだと通ってしまう形だった。

結合の経路は**フルーエント型 IRI で統一**した（不変条件 5 の canonical な識別子）。
アサーションの述語もその IRI をそのまま使うので、変換が 1 箇所（ingest の ``predicate_of``）に
集まる。

### 45. 既定グラフだけを見る SPARQL は何も返さない

``partOf`` を読むクエリを ``SELECT ?part ?whole WHERE {{ ?part partOf ?whole }}`` と書いたら、
データを投入しているのに 0 件だった。オントロジーは名前付きグラフに投入され
（``scripts/seed.py``）、インスタンスの関係もアサーションのグラフに入るので、**既定グラフだけを
見ると何も見えない**。

既定グラフと名前付きグラフの UNION にした（``DISTINCT`` を付ける——同じ三つ組が複数のグラフに
現れうる）。``knowledge`` の既存のクエリが一貫して ``GRAPH ?g`` を使っているのを見落としていた。

**推移閉包は展開しない**ことも決めた。``partOf`` は ``owl:TransitiveProperty`` だが、閉包を
結合に入れると同じ証拠が祖先へ複数の経路（孫 → 子 → 親 と 孫 → 親）で伝わって二重に数えられる。
多段の伝播は BP の反復が担う仕事である。

### 46. 照合はイベントごとに判定できない（窓が必要）

信念更新はイベント 1 件ごとに進むが、**照合は点ではなく区間を見る**。持続 τ を超えて乖離が
続いて初めて不一致とするので（既定 300 秒）、1 件のイベントでは判定が成立しない。照合ワーカーは
イベントを時間窓に溜め、周期ごとに検出規則へ渡す形になった（``sbp.reasoning.windows``）。

**窓の上限が τ を下回る設定は構築時に拒否する。** 下回ると、乖離が τ 続く前に古い刻みが
捨てられて**不一致が永久に検出されない**。しかも件数 0 として静かに通るので、設定ミスが
「不一致なし」に見える。``WindowStore.__post_init__`` で ``step × (capacity − 1) ≧ τ`` を検査し、
既定値（360 刻み × 10 秒 = 1 時間 ≧ 300 秒）が整合していることをテストでも押さえた。

**照合の周期を信念更新の周期と別の設定にした**（``reconcile_period_s`` 既定 120 秒 対
``bp_period_s`` 既定 60 秒）。同じ値にすると、照合を速くするために信念更新を遅くするか、
その逆をすることになる。照合は窓を見るので、τ より短い周期で回しても新しい判定材料は増えない。

### 47. 照合の両列は様相で振り分ける

窓の観測列と記録列をどう埋めるかで、イベントの様相が効いてくる。``observed`` は業務記録の存在
そのもの（統合層が出す）、``inferred`` は物理観測からの推定（接地層・信念更新が出す）。
**取り違えると、記録と観測を突き合わせているつもりで同じ側を 2 回見る**——乖離が常に 0 になり、
やはり「不一致なし」として静かに通る。

記録が無い刻みは ``None`` のまま残す。埋めると「記録が無かった」と「まだ届いていない」が
区別できなくなる。**刻みを揃えるのは観測側の時刻**で、記録は最も近い観測の刻みへ割り当てる
——逆（記録の時刻で刻みを作る）にすると、記録が無い期間の観測がどこにも入らない。

### 48. `__len__` を持つクラスは空のとき偽になる

``WindowStore`` に ``__len__`` を足したので、窓が 0 個の状態が falsy になった。テストで
``assert _store(...)`` と書いて落ちた——構築は成功しているのに偽である。コンテナとしては
正しい挙動だが、**「構築できたこと」の検査に真偽値を使えない**。

小さい話だが、同じ形は ``WindowStore`` を使う側にも現れる（``if store:`` が「窓を持っているか」
の意味になる）。意図がそれなら良いが、「設定されているか」の意味で書くと誤る。

### 49. 走査が見ていない場所にファイルがある間は、緑は「漏れていない」を意味しない

**実際に鍵をコミットした。** ``.envrc``（direnv、本物の Anthropic / Google API キー入り）が
未追跡のまま置かれていて、``make check`` は緑、その直後の ``git add -A`` で staging に入り、
そのままコミットされた。リモートが無く push もしていないため HEAD の 1 コミットに限定され、
``git reset --soft HEAD~1`` と staging からの除外で履歴から消せた。

原因は走査の対象だった。``git ls-files`` は**追跡済みファイルしか返さない**ので、
``git add`` される前のファイルは見えない。順序がこうなっていた:

1. ``.envrc`` が未追跡で存在（走査の対象外）
2. ``make check`` → 走査は緑（**見ていないものは報告されない**）
3. ``git add -A`` → staging に入る
4. ``git commit`` → 履歴に入る

``git ls-files --cached --others --exclude-standard`` に変え、**gitignore されていない未追跡
ファイルも走査する**ようにした。これで ``git add`` の前に検出される。``.envrc`` / ``.envrc.*``
を gitignore に加え、``.env`` と同様に「その名前のファイルが見えていたらそれ自体を報告する」
規則も足した。

**陽性対照で確認した**: 偽の鍵を書いた未追跡ファイルを置くと検出され、消すと緑に戻る。

教訓は「走査の対象範囲そのものが検査対象である」こと。所見 32・33・39 と同じ構図が、今度は
自分の手で実害になった——``make check`` の緑を「漏れていない」と読んだが、正しくは
「**走査が見た範囲には**漏れていない」だった。

残る注意: 取り消したコミットは reflog から到達可能なので、鍵を含む blob はローカルの object
store に残る（``git reflog expire --expire=now --all && git gc --prune=now`` で消える）。
push していないので外部には出ていないが、鍵の持ち主が入れ替えるかはその人の判断である。

### 50. 「未決」と思っていたことが設計書に書いてあった

bridge-worker を「潜在の取得元が未決」として実装を見送っていた。設計書 §2.5（三つのデータパス）
と §6.2（三層ストレージ）を読んだら、**答えが書いてあった**: 推定パスは「観測 → 潜在 z →
プローブ → 型付き確率的事象 → イベントログ」で、潜在は latent 層（列指向、1〜2 年保持）に置く。
raw 層（オブジェクトストア）から読むのは WM の MAJOR 更新で再潜在化するときだけである。

**未決として記録する前に正典を読むべきだった。** CLAUDE.md は「着手前に該当章を読む」と
書いてあり、それを飛ばして「決まっていない」と判断していた。自分の無知を設計の欠落として
記録するのは、後から読む人を誤らせる。

関連して決まったこと: **潜在をイベントログに載せない。** L0 は 100 ms 未満の階層で潜在は
数値ベクトルである。イベントログは「誰かの主張」を運ぶ場所であり、潜在は主張ではない
——載せると量に見合わないうえ、``EventEnvelope`` の意味（様相・確信度・来歴）が潜在に対して
定義できない。

### 51. TYPE_CHECKING だけの import は pyright を通って実行時に落ちる

``LatentIndex`` に ``since``（時刻順の読み出し）を足し、pgvector の値を numpy に戻す
``_from_pgvector`` を書いた。``numpy`` が ``if TYPE_CHECKING:`` の下でだけ import されていたので、
**pyright は通り、実行時に ``NameError`` になった**。既存のコードは numpy を注釈にしか使って
いなかったため、この形で問題が出ていなかった。

単体テストでは読み出しを関数で差し替えていたので、この経路は一度も実行されていなかった。
**統合テストが拾った**種類のバグである——「型が通る」と「動く」は別で、遅延 import は
その差が出る場所の 1 つ。

### 52. ウォーターマークは副作用の後に進める

接地ワーカーは「最後に処理した潜在の時刻」を持ち、それより後だけを読む
（``LatentIndex.since`` は右開——閉区間だと毎回 1 行が重複し、同じ変化点から事象を繰り返し
昇格する）。

**進める位置が重要だった。** 読み出しの直後に進めると、イベントの送信に失敗したときその
イベントは二度と昇格されない（潜在は索引に残っているが、もう読み直さない）。送信まで終えてから
進める形にし、**送信を必ず失敗させるテストでウォーターマークが進まないことを確認した**。
所見 41（冪等記録を副作用の前に付けると at-least-once が壊れる）と同じ構図が、別の層に現れた。

**1 点だけ読めたときも進めない。** 変化点は区間で定義されるので 1 点では判定できず、進めると
次のループで 2 点目が来ても 1 点目が読み直されない。例外は「プローブが何も返さなかった」場合
——これは潜在の問題ではないので進める（進めないと同じ潜在を永久に読む）。

### 53. 次元はマイグレーションが決める、という制約が効いた

統合テストで ``delays=4`` の koopman（12 次元）を使ったら、``no latent index table holds
12-dimensional vectors; add one in an alembic migration`` で落ちた。アプリは実行時にスキーマを
作らない設計（M4-08）なので、**存在しない次元は黙って作られずエラーになる**。

これは意図どおりの挙動である。次元が変わる WM 更新は新しい表と再接地ジョブを要する（knowledge
ルール）ので、テストのために実行時に表を作れてしまうと、その制約が検査されないまま残る。
``delays=8``（3 チャンネル × 8 = 24 次元）に変えて既存の表に合わせた。

### 54. 「保存できる」と「使える」を別にしないと、置き場が不変条件の抜け穴になる

プローブ重みの直列化（M8-01）で、較正器を欠いた `active` を**保存側で**拒否するだけでは
足りないことが分かった。置き場の中身は別の経路でも入る——手で置く、古い版のコードが書く、
修復のために `overwrite=True` で差し替える。**ロード側で同じ条件を検査する**ようにした
（`restore_probe` が `active` かつ較正なしを `CalibrationError` にする）。

同じ理由で `candidate` は未較正でも往復できるようにした。保存を禁じると、学習途中のプローブ
をプロセスの外に出す手段が無くなる。「保存できる」と「信念に入れられる」は別の条件である。

### 55. Protocol は実行時に何も強制しない（較正器の取り違えが通っていた）

`LinearProbe.attach_calibrator` の引数は `Calibrator` Protocol だが、`ConformalRegressor`
（回帰用で `apply` を持たない）を `type: ignore` 付きで渡すと取り付けられ、`predict` は
「較正器がある」と判断して進んでいた。型検査を通さない呼び出しは実際に起こる（動的な配線、
テストの近道）ので、`runtime_checkable` な Protocol への `isinstance` を取り付け時に入れた。
pyright は「常に真」と警告するが、**その警告自体が「静的にしか守られていない」ことの証拠**
なので抑止コメントに理由を書いて残している。

### 56. 成果物の置き場を上書き可能にすると、`latest` を禁じた意味が消える

レジストリは `latest` を禁じている（同じ版を名乗る別の重みが後から入り込むと、過去の信念の
説明が静かに変わる）。置き場の `put` が上書き自由だと、**版を明示していても同じことが起こる**
——キーは変わらないまま中身が入れ替わる。`ArtifactImmutableError` を既定にして、修復のときだけ
`overwrite=True` を明示する形にした。拒否されたときに中身が変わっていないことをテストで固定した。

### 57. プロパティパスは名前付きグラフを跨げない（型の問い合わせが 1 件も返らなかった）

接地対象の実体を型で引くとき、`?e rdf:type/rdfs:subClassOf* ?type` と 1 本のプロパティパスで
書いた。**0 件返った。** 原因は、パス全体が同じグラフ内で閉じることを要求されることである
——実際の配置ではインスタンスは信念グラフ、`subClassOf` の階層はオントロジーのグラフにある。

段を分けて（型の宣言 → 部分クラスの階層）、各段を「既定グラフ ∪ 任意の名前付きグラフ」の
UNION で書くと通った。`subClassOf*` の 0 段は項の同一性なので、型が直接宣言されている場合も
同じ形で拾える。所見 45（既定グラフだけを見る SPARQL は何も返さない）の一段深い版で、
**UNION を足すだけでは足りない**——パスの途中にグラフ境界があると、UNION の外側に出る。

### 58. プローブ IRI を文字列で組み立てていた（来歴が辿れない証拠を作っていた）

接地ワーカーは `f"https://sbp.example/probe/{name}/1.0.0"` でプローブ IRI を作り、昇格した
イベントの来歴に入れていた。不変条件 5（IRI をコードに直書きしない）の違反だが、実害は
それより重い——**置き場に存在しない版の IRI が来歴に載る**。説明を求められたときに辿れない
証拠は証拠ではない。

M8-02 で `ProbeSet.probe_ids()` から渡す形にし、IRI を持たないフルーエントが出力に現れたら
`BridgeError` で落とすようにした。「来歴を空にする」より「落とす」を選んだのは、空の来歴は
下流で「プローブ由来でない」と読まれるためである。

### 59. ウォーターマークを永続化しないと「取りこぼす」と「重複する」のどちらかしか選べない

接地ワーカーのウォーターマークはプロセス内のメモリにあった。再起動すると `after=None` で
読み始めるので、**過去の潜在を全部読み直して同じ変化点から事象を昇格し直す**。これを避けて
「最新から始める」にすると、止まっていた間の潜在を飛ばす。どちらも静かに起こる。

投影表（`grounding_watermarks`、alembic 0003）に逃がした。設計で効いたのは**キーに WM 版と
階層を含めた**ことである——違う潜在空間の「どこまで処理したか」は意味が違い、版を上げたときに
古い値を流用すると新しい版の潜在を「もう処理した」ことにしてしまう。キーに版が入っていれば
新しい版は白紙から始まる（統合テストで固定した）。

UPSERT に `WHERE processed_through < EXCLUDED.processed_through` を付けて**後退を禁じた**。
後退を許すと、遅れて走ったループが進んだ位置を巻き戻し、同じ潜在が二度処理される。これは
SQL そのものなので単体テストの代役では確かめられず、統合テストでしか固定できない。

### 60. 開発機のポート退避が `.envrc`（direnv）にあり、`make` 経由の実行と食い違っていた

`make seed` が Postgres に繋がらなかった。実物の compose は 15432 / 19000 に退避して
稼働しているのに、`SBP_PG_DSN` は 5432 を指していた——退避の設定が direnv（`.envrc`）側に
あり、`make` を別のシェルから起動すると読まれない。統合テストは
`SBP_PG_DSN=...15432 SBP_S3_ENDPOINT=...19000` を明示して通した。

**`docs/runbooks/local-setup.md` に「`.env` で退避する」と書いてあるのに、実際の退避は
`.envrc` にある**。手順書と実際の配置が食い違っている状態で、第三者が runbook に従うと同じ
ところで詰まる（所見 29 の「runbook の第三者実行可能性」の具体例が 1 つ出た）。

### 61. 「両方のトピックに出す」は冪等性が許さない

不一致の起票先を決めるとき、拠点トピックと中央トピックの両方に出す案が自然に見えた。どちらの
購読者も満たせる。**しかし冪等性が `event_id` で定義されている**（不変条件 4）ので、2 本流すと
同じ不一致が 2 つの `event_id` を持ち、下流が二重に数える。同じ `event_id` で 2 トピックに
流すと、冪等記録が `(consumer_group, event_id)` を鍵にしているため片方しか処理されない。
どちらにしても壊れる。

拠点トピックを既定にし、中央集約が必要になったら**転送役**（拠点を購読して中央に再発行し、
`causation_id` に元の `event_id` を入れる）を作ることにした（ADR-0010）。選択肢を狭めたのは
設計の好みではなく、不変条件が 2 つを 1 つに落とした結果である。

### 62. イベントは通知であって不一致そのものではない（UI が読む先が無いことに気付いた）

起票イベントを組もうとして、`EventEnvelope` に不一致の全体（根拠アサーション・証拠・状態履歴・
学習信号）を入れる場所が無いことに気付いた。入れようとすると封筒に任意のペイロードを足すことに
なり、「全イベントが同じ形」という §6.1 の前提が崩れる。

封筒には「どの実体に、どの類型が、いつの区間で、どれだけの確信度で起票されたか」だけを載せ、
本体は `correlation_id`（= `discrepancy_id`）で辿らせる形にした。そこで分かったのは、
**不一致の本体を書く先がどこにも無い**ことである——照合ワーカーは sink に渡すだけで永続化せず、
`sbp.api` に不一致の資源は無く、知識グラフにも投影表にも書かれていない。UI（M7-04）には
不一致キューの型と並べ替えロジックがあるが、読む先が無い。M8-12 として起票した。

**UI が先に出来ていたことで露見した**。画面から遡って「この値はどこから来るのか」を辿ると、
経路が存在しないことが分かる。

### 63. イベントログは「主張」しか運べない——要求（指令）は様相格子に席が無い

追加観測の要求（`ObservationRequest`）をイベントログに載せようとして止まった。`EventEnvelope`
は `modality` と `belief` を必須に持つ形で、**要求は主張ではない**。様相格子
（observed / inferred / predicted / planned / normative / hypothetical）に「これを測ってほしい」
は無い。`reason` と `utility` を入れる場所も封筒に無い。

載せるには封筒に任意ペイロードを足すことになり、「全イベントが同じ形」という §6.1 の前提が
崩れる。**作業キュー（投影表）にした**（ADR-0011）。「状態はイベントの投影」の規律は**世界の
状態**（信念）についてのもので、作業キューは世界の状態ではない——既存の `quarantine`
（SHACL 違反の隔離キュー、`reviewed_at` を直接更新する）が同じ区別の先例になっていた。

所見 62（イベントは通知であって不一致そのものではない）と同じ根から出ている。**封筒が運べる
のは「誰かが何かについて何を信じているか」だけである**。通知・要求・指令はそれぞれ別の器が要る。

### 64. 観測手段をオントロジーに置くと、計測器の更新でオントロジー版が上がる

「どのフルーエントをどの手段で確かめられるか」は世界についての知識に見えたので、オントロジーに
`Probe` × `FluentType` の対応を持たせる案を検討した。棄却した理由は**コストと信頼度が拠点ごとに
違う**ことである——拠点が計測器を更新するたびにオントロジーの版が上がり、再接地の判定に無関係な
変更が版履歴に混ざる。センサ由来のプローブと概念の対応は `ProbeSpec.grounds` が既に持っている
ので二重管理にもなる。

`observation/<domain>.yaml` に置き、**宣言したフルーエントがオントロジーに実在することを
読み込み時に検査する**（`vocab.FLUENT_TYPES` と突き合わせる）。タイプミスを通すと
「その概念は既定手段で観測する」という静かな挙動になる——`ent:Runnning` が既定手段に落ちても
エラーは出ない。

### 65. 事前は「要る鍵だけ」引く形にしないと、要求 1 件でも全設備を走る

スケジューラの事前供給元を `() -> 全信念` にしていた（M7 の雛形）。配線すると、要求が 1 件の
ときも知識グラフから全実体の信念を引くことになる——拠点に設備が数百台あれば毎周期それを走る。
`(鍵の列) -> 信念` に変え、要求が指す `(実体, フルーエント)` だけを引くようにした。

同期の SPARQL 呼び出しなので `asyncio.to_thread` に逃がしている（CLAUDE.md の非同期規約）。
**`planned` を事前に使わない**のも決めた——「計画どおりならこうなっているはず」が事前になると、
情報利得が計画との一致度に引きずられる。

### 66. 「健全に起動した」は「設定が正しい」を意味しない（Prometheus の環境変数）

`prometheus.yml` の `external_labels` に `${SBP_SITE_ID:-siteA}` と書いた。Prometheus は
**健全に起動し**、healthcheck も通った。`/api/v1/status/config` を見ると、ラベルの値は文字列
`${SBP_SITE_ID:-siteA}` のままだった——環境変数の展開には
`--enable-feature=expand-external-labels` が要る（しかも Prometheus は `${VAR}` だけを解釈し、
`:-default` の記法は知らない。既定値は compose 側で与える）。

healthcheck は「プロセスが応答するか」しか見ない。**設定が意図どおり効いているかは、
設定を読み返して確かめるしかない**。所見 32（「0 件」と「経路が動いていない」を区別する）と
同じ構えが、設定にも必要である。

### 67. ダッシュボードは手で書くと追従しない（生成物にした）

Grafana のダッシュボード JSON を手で書こうとして、25 指標ぶんのパネルを並べる作業になった。
手で書くと、指標を足したときにダッシュボードが追従せず**「測っているのに見えない」指標が
静かに増える**。`sbp.core.metrics.METRICS` からの生成物にし（`scripts/gen_dashboard.py`、
`make gen`）、契約テストで「コミットされている JSON が再生成と一致する」「全指標にパネルがある」
「パネルの系列名が列挙に実在する」を検査した。

M7-03 の「指標名を列挙で固定したので、ダッシュボードを後から作っても系列名がずれない」という
主張が、ここで機械検査になった。**閾値はダッシュボードに焼き込まない**——既定値は `Settings` が
持ち拠点ごとに上書きされるので、焼き込むと設定を変えても色が変わらない。

### 68. API を実物の依存で起動する経路がどこにも無かった（`make dev` が落ちる）

M8-06 で Prometheus の取り込み先を `/metrics` にして、取り込みが `down` のままなので調べた。

4 ワーカーには `build_worker()` があるのに API には無い、という非対称が残っていた。
ワーカーは統合テストが実物で起動するので気付くが、API は `TestClient` が `create_app` を
直接呼ぶので気付かない。

### 69. 開発用の認証は「dev 以外では作れない」形にした

API の要求者解決（ABAC の入口）は本番の方式が未決なので（ADR-0008 の未決）、開発用に
ヘッダ `X-SBP-Principal` で名乗る経路を作った。**ヘッダを名乗るだけで権限が付くのは認証では
ない**ので、`SBP_ENV` が `dev` 以外だと `dev_principal_resolver` が構築時に `ValueError` で
落ちるようにした。

「`dev` のときだけ有効」をフラグで分岐すると、分岐を書き忘れた経路が本番で通る。**作れない
ようにする**のが構造的な守り方である。統合テストは `SBP_ENV=test` で走るので、
「ヘッダを付けても拒否される」ことがそのまま回帰テストになっている。

許可する様相から `hypothetical` を外したのも同じ理由で、検討中の案が見えると「決まった」と
誤解される（authorization の規約）。

### 70. 指標の経路は 4 段あり、どの段も「動いているように見えて止まる」

M8-06 と M8-13 で指標を端から端まで通して分かったのは、段が 4 つあることである。

| 段 | 止まったときの見え方 |
|---|---|
| ワーカーが `metrics` 表に書く | 表が空。`/metrics` は 200 で系列 0 件 |
| API が `/metrics` を出す | **未配線だと 503**（ここだけ区別できるようにした） |
| Prometheus が取り込む | target が `down`。`up` 系列を見れば分かる |
| Grafana が描く | パネルが「no data」 |

**どの段でも最終的な見え方が「グラフが空」になる。** 区別できるようにしたのは API の段だけで
（未配線は 503、配線済みで空は 200）、他の段は Prometheus 自身の `up` / `scrape_samples_scraped`
を見るしかない。日次点検（OPS-01）では**指標そのものではなく取り込みの健全性を先に見る**必要が

なお **`external_labels` の `site` はローカルのクエリ結果には出ない**（Prometheus は外部ラベルを
federation / remote-write / アラートの時点で付ける）。設定は正しいが、ローカルで
`sbp_*{site="siteA"}` を期待すると空振りする。

### 71. 指標を書く側がまだ誰もいない

無い**。25 指標の値は、プローブ評価・信念更新・照合・再接地の各所で計算されているのに、
`metrics` 表には行かない。M8-06 は「経路を作った」ところまでで、「測っている」ところまでは

これは所見 70 の第 1 段に当たる。ダッシュボードが全部 no data のとき、いま分かるのは

### 72. 結合の経路を足しても、関係を書く側が無ければ入力は空

同一 Situation による結合（M8-07）を配線した。`SituationLink` も `propagate` の引数も M3-03 の
時点で用意されていたので、足したのは**クエリ 1 本と provider の戻り値の形**だけである。

配線してから気付いたのは、**`inSituation` を立てているコードがどこにも無い**ことである。
`vocab.core.inSituation` は存在し、クエリは正しく読むが、グラフに三つ組が入らない。所見 71
（指標を書く側が誰もいない）と同じ形で、**読む側を先に作ると「経路はあるが入力が空」になる**。

この形が M8 で繰り返し出ている（プローブの束ね → 置き場に入れる側が無い、観測要求のキュー →
書く側が無い、指標 → 書く側が無い、Situation の結合 → 関係を書く側が無い）。共通するのは
**「型と判定」「読み出し」「周期実行」は実装されていて、「誰が最初の値を入れるか」が空いている**
ことである。入れる側は多くの場合**人の判断を経る**設計（不一致の解決、概念の採択、計画の投入）
なので、M8-08（学習信号の適用ワーカー）がその入口になる。

provider の戻り値を `(PartWhole の列, SituationLink の列)` の対にしたのは、1 つの列に混ぜると
呼び出し側が型で分岐することになるためである。因子の形が違う（部分−全体は向きと集約規則を
持ち、同一 Situation は対称で規則を持たない）ので、列を分けておくほうが素直だった。

### 73. 寄与率は「大きさ」であって割合ではなかった（指標の単位が取り違えを暴いた）

`SourceContribution` は三源が事後をどれだけ動かしたかを**対数尤度比の絶対値**で持つ
（G3 の実測で observed 2.31 / record 1.34 / plan 0.97）。`contrib_observed` 指標の単位は
`ratio`（0〜1）なので、生の値をそのまま入れると `MetricSample` の値域検証が落ちた。

**落ちたのが良かった。** 正規化せずに書けていたら、ダッシュボードには 2.31 という「割合」が
出て、しばらく誰も気付かない。単位を型に持たせて値域を検証していることが、ここで取り違えを
捕まえた。docstring には「比で表す」とあるが実装は大きさで、**文書と実装が食い違っていた**
——指標の配線がそれを暴いた。

### 74. 指標の書き込み失敗は、規約の「握りつぶさない」の意図的な例外にした

CLAUDE.md は「例外は握りつぶさない。リトライは eventlog の consumer 層と `llm.Provider` の
2 箇所だけ」と定める。指標の書き込みでこれをそのまま守ると、**指標 DB の一時的な不調で推定
パスが止まる**。指標は観測であって信念ではないので、本末転倒である。

例外にする代わりに 3 つを守った: (a) エラーログを出す、(b) 落とした件数を `dropped_total` に
数える（「測っていない」と「書けていない」を区別できる）、(c) **再送しない**（古い標本の価値は
低く、再送バッファは無限に伸びうる。リトライ箇所を増やさないという規約も保つ）。

未配線（`sink=None`）のときも `dropped_total` に数える。溜め続けないためだが、数を残すことで
「ダッシュボードが空なのは配線していないから」が分かる（所見 70 の第 1 段）。

### 75. 25 指標のうち運用ループで測れるのは 7 つだけだった

### 77. 既定の UUID が学習信号の辿れなさを作っていた（統合テストで出た）

人の判断から学習信号を作るとき、不一致の本体が読めないので（M8-12）判断の行から最小の
`Discrepancy` を再構成した。統合テストで観測要求の `discrepancy_id` を確かめたら、
**判断が指していた不一致とは別の UUID** だった。

原因は `Discrepancy.discrepancy_id` が `default_factory=uuid4` を持つことである。渡さなければ
新しい ID が作られ、エラーも警告も出ない。**辿れない学習信号ができていた**——観測要求は
積まれるが、どの不一致から出たのか誰も分からない。

直し方は 2 つあった: (a) 識別子を引き継ぐ、(b) 引き継げないなら落とす。両方やった——
`row.subject` を UUID として解釈して渡し、UUID でなければ `ValueError` にした
（**推測で新しい ID を作らない**。辿れない学習信号は、無いほうがまだ分かる）。併せて API 側で
`discrepancy_id` を `UUID` 型にして、境界で弾くようにした。

**単体テストでは出なかった。** 代役のキューは要約の件数だけを見ていて、ID の一致を見ていな
かった。実物を通して「積まれた行の中身」を確かめたときに初めて出た——所見 32 の
「0 件と経路が動いていないを区別する」の親戚で、**件数が合っていても中身が違う**ことがある。

### 78. 実体 IRI の位置に不一致の ID が入る事故が、同じ再構成に潜んでいた

所見 77 を直すときに気付いた。再構成した不一致の `subjects` に `row.subject`（= 不一致の ID）
を入れていた。`subjects` は**実体 IRI** の位置なので、観測要求が「存在しない実体を測れ」と
言うことになる。スケジューラは `(実体, フルーエント)` で事前を引くので、該当なしで静かに
変換されず落ちる——**要求は積まれるが永久に満たされない**。

判断に実体が入っていればそれを使い、無ければ不一致の ID を入れる形に留めた（本体が読めない
間の制限）。**同じ再構成関数に 2 つの ID 取り違えが入っていた**のは、「文字列の ID を文字列の
フィールドに入れる」ときに型が守ってくれないためである。IRI 型と不一致 ID 型を分ければ
静的に防げるが、それは `core` の型の作り直しになるので ADR 相当の判断になる（未着手）。

### 79. 「受け付けた」と「適用した」を分けると、UI の約束が変わる

判断を同期的に適用する案を棄却した（ADR-0012）。人が書き戻しの完了を待つことになり、失敗
したら判断そのものが失われる。代わりに作業キューにしたが、**UI の意味が変わった**——
`submitResolution` の戻り値は「受け付けた」であって「適用された」ではない。

要約（`artifacts` 列）を残すようにしたのはこのためで、UI は後から「この判断で何が起きたか」
（観測要求が何件積まれたか、書き戻しが走ったか、何が記録だけで止まっているか）を読める。
**適用されなかったものの件数も要約に入れた**——`bags_recorded` が 3 なら「負例が 3 件できたが
再学習はしていない」が分かる。UI 側の表示は未実装（M7-04 は受領までしか見ていない）。

### 80. 「終端だけ守る」では状態の後退を止められなかった

不一致の表（M8-12）で、終端状態（`Learned` / `Suppressed`）から非終端への上書きを弾く
UPSERT を書いた。統合テストで `Resolved` の行を `Open` で上書きしたら**通った**——`Resolved` は
終端ではないので、終端チェックの対象外だった。

複数の経路（照合ワーカーと learning-worker）が同じ行を触るので、片方が古い状態で上書きする
事故は `Resolved` でも起こる。`DiscrepancyStatus.rank`（ライフサイクル上の位置を数値化）を足し、
`status_rank` 列で `WHERE status_rank <= EXCLUDED.status_rank` にした。**同じ位置なら内容の
更新として通す**（深刻度の再計算など）。

`Suppressed` は `Open` からの分岐だが、`rank` は `Learned` と同じ最上位にした——抑制した不一致が
非終端で上書きされないようにするためである。**遷移表（`_ALLOWED`）とは別の順序**を持つことに
なるので、単調性を単体テストで固定した。

遷移表はオブジェクトの中では正しく守られていた（`transition()` が弾く）。**壊れるのは
永続化の境界**で、2 つのプロセスが別々に読んだオブジェクトを書き戻すときである。型で守れる
範囲の外にあるものは、ストア側でもう一度守る必要がある。

### 81. 不一致の表は「投影」ではないと認めるのに ADR が必要だった

「状態はイベントの投影」は CLAUDE.md の禁止事項（「状態テーブルを直接更新して整合させる」）と
対になる規律である。不一致の表はこれを破る——**起票イベントから不一致を再構成できない**ので、
照合ワーカーが直接書くしかない。

破る理由を ADR-0013 に書き、表のコメントにも残した。重要なのは「投影のつもりで直接更新する」
のと「投影ではないと認めて直接更新する」の違いである。前者は規律が壊れていることに気付かない
が、後者は**なぜ例外なのかが読める**。

同じ判断が M8 で 3 回出た（観測要求のキュー・判断のキュー・不一致の表）。共通しているのは
**作業項目は世界の状態ではない**ことで、`quarantine`（M0 から存在する隔離キュー）が最初の
先例だった。規律の文言を「世界の状態（信念）はイベントの投影」と読み替えるのが正確である。

### 82. GraphQL のリゾルバは同期なので、非同期の読み出しを包む必要があった

不一致キューを GraphQL で返すとき、`DiscrepancyStore.queue` は async だがリゾルバは同期で
呼ばれる。リゾルバの中から `asyncio.run` は呼べない（すでにループの中にいる）。

スレッドを 1 つ使って新しいループを回す形にした（`api.factory._run_sync`）。**接続を 1 つ
共有している**ので、1 リクエストで `discrepancies` が複数回呼ばれる形になったら psycopg の
接続が競合しうる——いまは 1 クエリ 1 呼び出しなので足りるが、接続プールが必要になる境界を
docstring に書いた。

`strawberry` は async リゾルバも受けるので、そちらにすれば包む必要は無い。しかし
`BeliefSource`（既存）が同期なので、不一致だけ async にすると**リゾルバの形が 2 種類**になる。
揃えるほうを選んだ。

### 83. UI と API の契約が 5 箇所ずれていて、UI のテストは全部通っていた

M8-12 で不一致の資源を作り、UI を繋ごうとして突き合わせたら、**5 箇所ずれていた**。

| 箇所 | UI が持っていたもの | API が返す／要求するもの |
|---|---|---|
| 類型 | `EXISTENCE` / `TIME` / `STATE` / `IDENTITY` / `QUANTITY` | 番号 1〜5（`QUANTITY` は**存在しない**。実在する `NORM`（規範）が UI に無かった）|
| 状態 | `OPEN` `TRIAGED` …（大文字）| `Open` `Triaged` … |
| 解決結果 | UI 独自の 5 値（`RECORD_WRONG` / `SYSTEMATIC_BIAS` …）| 4 値（`physical_correct` …）。**`extra="forbid"` なので投入は 400 になる** |
| 証拠 | `observedEvidence: Belief[]`（三源が埋まっている）| IRI の列（埋め込む経路は存在しない。所見 62）|
| 主体 | `subject: string`（単数）| `subjects: string[]`（類型 4 は競合する 2 つの主張）|

**UI のテストは 61 件すべて通っていた。** 自分で決めた型に対して自分で作った fixture を当てて
いたので、API と合っているかは一度も検査されていなかった。M7-04 は「UI 完成」として `[x]` に
なっていたが、**実際には API に繋がらない UI だった**。

さらに悪いのは `SYSTEMATIC_BIAS` で、**API が受け付けない選択肢を人に選ばせていた**。抑制は
解決結果ではなく別の遷移（`Open → Suppressed`）で、信頼性モデルで説明できる系統誤差に限られる
——人がフォームで選ぶものではない。設計の意味がずれていた。

対処は 2 段である: (1) UI を API の契約に揃える、(2) **契約テストを Python 側に置く**
（`tests/contract/test_ui_api_contract.py`）。TypeScript を構文解析せず正規表現で値の列挙を
抜き出すだけにしたのは、`make check` に tsc への依存を入れないためである（「追加のインストール
無しで必ず走る」方針）。ずれを仕込んで落ちることを確認した（陽性対照）。

**手で写した型は必ずずれる。** ADR-0008 は「クエリが 4 本で mutation が無いのでコード生成を
入れない」と決めたが、その代わりに**ずれを検出する仕組み**が必要だった。生成を入れないこと自体は
今も妥当で、足りなかったのは検査である。

### 84. 三源の並置は「様相で分ける」では作れない

UI の不一致キューは観測 / 記録 / 計画の 3 列で証拠を並べる設計である（設計書 §8.2 の
「証拠並置」）。実装しようとして分かったのは、**三源は様相では分かれない**ことである。

- 業務記録由来のイベントの様相は `observed`（「この記録が存在する」は観測された事実）だが、
  そこから出る**信念**は `inferred` である。
- 物理観測（プローブ）由来の信念も `inferred`。
- `planned` だけは様相で分かれる。

つまり「観測の証拠」と「記録の証拠」を様相で振り分けると、**両方が `inferred` の山に入る**。
三源の区別は来歴の `contrib: {observed, record, plan}` にあり、信念を引いてから来歴を辿る
必要がある。さらに不一致が参照するアサーションを ID で引く API が無い（`query` は主語・述語で
しか絞れない）。

M8-16 では**参照 IRI の一覧**までを出し、三源の並置は M8-17 に分けた。UI の表の caption に
「三源の並置はまだ作れていない」と書いてある——**できていないことを画面に出す**ほうが、
空の 3 列を出して「証拠が無い」と誤読させるよりよい（所見 32 と同じ構え）。

### 85. UI が読んでいたトピックのうち 2 本は存在しなかった

所見 83 の「他のビューにも同じずれが残っている可能性が高い（未検証）」を検証した。**実在
しないトピックを 2 本読んでいた。**

| UI が読んでいた | 実在するか |
|---|---|
| `central.reasoning.discrepancy` | ある（ただし M8-16 で GraphQL に移した）|
| `central.reasoning.expectation` | **無い**。期待は拠点ごと（`<site>.reasoning.expectation`）|
| `central.reasoning.concept` | **無い**。概念提案のトピックはどこにも無く、出す周期ジョブも無い |

**存在しないトピックは空を返す。** `/stream/{topic}` は名前を受け取って読むだけなので、

`scripts/topics.py` に実在する」ことを機械検査した。

### 86. 期待と概念提案も不一致と同じずれ方をしていた

UI の `Expectation` と `ConceptProposal` も backend の型と別物だった。

| 型 | UI | backend |
|---|---|---|
| `Expectation` | `subject` / `deadline` / `symbolicVerdict` / `rolloutVerdict` / 状態は大文字 | `target` / `expected_effects` / `verification`（検証結果は入れ子）/ 状態は `Created` など |
| `ConceptProposal` | `label` / `rationale` / `supportCount` / `coverage` | `name` / `definition` / `superclass` / `signals` / `status` / `curation_note` …（`supportCount` と `coverage` は**フィールドとして存在しない**。`signals` の中にある）|

**3 つのビューすべてが同じ形で壊れていた。** 原因は 1 つで、「API の形を手で写した型を UI が
持ち、突き合わせる仕組みが無かった」ことである（所見 83）。1 箇所直して終わりではなく、
**同じ原因から 3 箇所壊れていた**のが実態だった。

API 資源を作る必要があり（M8-12 と同じ形）、1 日の粒度を超える。

### 87. 原文を正規表現で探すテストは、自分の書いた説明文を拾う

「`/stream/` に渡される文字列リテラル」を探す正規表現がそれを拾った。

コメントを落としてから探すようにした。**説明を書いたせいでテストが落ちる**のは、原文を
正規表現で検査する方式の構造的な弱点である——構文解析を入れれば防げるが、`make check` に
tsc への依存が入る（「追加のインストール無しで必ず走る」方針が崩れる）。コメントを落とす
前処理で足りる範囲に留めた。

### 88. 資源を足したら設定項目が 1 つ要らなくなった（M8-16 の追加を M8-18 が消した）

M8-16 で期待ボードのトピック名を直すために `VITE_SBP_SITE_ID` を必須の設定として足した
（トピック名が `<site>.<layer>.<class>` なので拠点が必要だった）。M8-18 で期待ボードを

設定を消した。API は `Settings.site_id` で絞るので、UI が拠点を知る必要は無い——**使わない
必須設定を残すほうが悪い**（起動時に落ちるのに、落ちる理由が「要らないもの」になる）。

M8-16 の判断は当時正しく（トピックを読む限り拠点は必要）、M8-18 が前提を変えた。こういう

「なぜこれが必要なのか誰も説明できない設定」になる。

付随して分かったこと: **`/stream/{topic}` に UI の購読者が 1 人も居なくなった**。購読方式が
未決のまま（ADR-0008 の未決）で、いまは誰も使っていない。

### 89. M5 の閉ループは library とテストの中にしか無かった

  インラインで組んでいる）。production には無い。
- **アクション実行自体が API コマンドとして配線されていない**。`build_command_handler` が

つまり G5（閉ループ）は「ライブラリとして組めること」をテストで確かめたが、**運用で回る形には
なっていない**。M8 で繰り返し出た「型と判定は実装済み、配線が無い」（所見 72）の、最も大きな
残りである。M8-20 として起票した。

**ゲートの意味を読み直す必要がある。** G5 は「ワークドエグザンプルを完走する統合テスト」で
通過したが、完走させたのはテストコードである。「統合テストが通る」と「運用で動く」の差が、
ここでも出た（所見 68 の API と同じ形）。

### 90. 投影の列が同名のプロパティと違う値を持っていた（M8-18 で自分が入れた）

M8-18 で `expectations` 表に `deadline` 列を出したとき、**最小値**（最初に期限が来る効果）を
入れた。`Expectation.deadline` プロパティは**最大値**（「最も遅い期限（全体の期限）」）を返す。

`from_record(r).deadline != r.deadline` が黙って成り立つ状態だった。どちらを見ているかで
答えが変わり、しかもどちらも `deadline` という名前なので読んで気付けない。M8-20 の調査中に
`Expectation.deadline` の実装を読んで見つけた。

再現テストを先に書いて赤を確認し（P-22）、列をプロパティに揃えた。**投影の列は同名の
プロパティと同じ値でなければならない。** 「最初の効果の期限」が必要になったら、それは別の
名前の列である。

自分で書いた docstring に「期限は最小値である」と**理由まで書いていた**（「ボードが期限の近い
順で並べる」）のが悪質だった——理由が書いてあると、読んだ人はそこで検討を止める。実際には
並べ替えに使えるのは最大値でも同じで、最小値である理由にはなっていない。

### 91. 同じことを計算する関数が 2 つできた

M8-20 で `expected_effect_for`（契約の効果 → 期待効果）を書いたら、`actions/execute.py` の
`planned_expectation_deadlines`（契約の効果 → 期限の列）と**期限の計算が重複**した。後者は
production の呼び出し元が無く、テスト 1 件だけが呼んでいた。

削除して、テストを `expected_effect_for` に向け直した。残しておくと、期限の起点の扱い
（`ensure_utc` のかけ方など）が片方だけ直されて食い違う。

**「使われていないが消すほどでもない」公開関数が、重複の種になる。** 新しい関数を書くときに
「これと同じことをしている既存の関数は無いか」を確かめる手間は、両方が残ったあとに食い違いを
見つける手間よりはるかに小さい。

### 92. 期待の区間をテストが決めていた

これが所見 89（M5 の閉ループがテストの中にしか無い）の実害である。G5 のテストは
`ExpectedEffect` を手で組み立てていて、区間の端をこう書いていた:

```python
ExpectedEffect(fluent=vocab.ent.WorkOrder, expected=1.0, lower=0.5, upper=1.0, ...)
ExpectedEffect(fluent=vocab.ent.Inspected, expected=0.9, lower=0.8, upper=1.0, ...)
```

契約（`actions/equipment-maintenance.yaml`）が宣言しているのは `threshold: 0.9` だけである。
`lower=0.8` は**テストの作者の見積り**で、契約と無関係だった。この期待で検証すると、
信念 0.85 は「契約（0.9 以上）を満たしていない」のに `Fulfilled` になる。

production に出すときに規則を決めた: **区間は契約の境界から作り、期待値は境界そのものを置く**
——契約が満たされる最弱の値である。これで `covers(observed)` が「契約の境界が保たれたか」と
一致し、`Violated` が「契約が守られなかった」を意味する。期待値を契約より強くすると
（下限 0.9 の契約に期待値 0.95）、`Violated` が「我々の勝手な見積りが外れた」に変わってしまう。

**テストの中で契約を組み立てると、契約の意味を決める権限がテストに移る。** テストは契約が
守られたかを確かめる立場なのに、守られたことの定義を自分で書いていた。

残った穴: **業務効果の下端は契約が何も言っていない**（`record_created` に `threshold` が無い）。
記録の存在に対する信念は情報源の信頼性で割り引かれるので 1.0 にはできず、
`Settings.actions.record_effect_floor`（既定 0.5）に置いた。**実データで較正していない暫定値**で、
合成データでは割引の実測値が出ない。既知の制約に記載した。

### 93. 冪等の鍵の既定値が、再試行で二重実行を作っていた

`ActionRequest.command_id` は `field(default_factory=uuid4)` である。M8-21 でワーカーから
呼ぶとき、そのまま既定に任せると**適用を再試行するたびに別の `command_id`** になる。

判断キューは `attempts` を数えて再試行する（前提が後で満たされうるので、これは正しい）。
つまり「前提で落ちた → 後で満たされて成功」の経路が普通にあり、**部分的に失敗した実行の
再試行で業務システムが 2 つの命令を見る**。

`uuid5(名前空間, decision_id)` で導くようにした。決定的で、同じ判断からは必ず同じ鍵が出る。

**既定値が便利な場所と危険な場所がある。** `uuid4` はテストや 1 回限りの呼び出しでは正しいが、
再試行される経路では「毎回違う値」が欠陥になる。`default_factory` は呼び出し側に
「指定しなくてよい」と伝えるので、指定しなければならない場所でも黙って通る。

### 94. 型の置き場所を import-linter が決めた

`ExecutionCommand`（アクション実行の引数）を最初 `sbp/api/commands.py` に書いた。API の入力
形式だからである。ワーカーが表から読み戻すときに同じ型で検証したくなり、import したら
**import-linter の契約「ワーカーは API を経由しない」が落ちた**。

正しい置き場所は `sbp.actions` だった。これは API の入力形式であると同時に、**適用側が読み戻す
ときの契約**でもある。そして読み戻す側は下位層にいる。`api ← actions` の向きなら API が
import できる。

**「誰が最初に使うか」で層を決めると間違う。** 最初に使うのは API だが、型が属するのは
アクションの意味契約と同じ場所である。層の lint が無ければ、ワーカーが API を import した
状態で動き続けていた（動くので気付かない）。

### 95. 配線の検査を実行の「前」に置く

`_apply_action` は、期待の書き込み先が配線されていなければ**実行する前に**失敗する。

順序を逆にすると（実行してから期待を書こうとして失敗）、**実行はしたが何も確かめられない**
状態ができる。アクションは業務システムを変えるので、取り消せない。

同じ形が ADR-0012 の書き戻しにもある（既定 `dry`）。「副作用を起こす前に、後片付けができる
ことを確かめる」という順序で、M8 で 2 回目に出た。

### 96. `<=` と `<` の違いが二重判断を許していた

M8-19 で `ConceptProposalStore.curate` の後退防止を `WHERE status_rank <= %s` と書いた。
M8-18 の `upsert` からそのまま写したのだが、**この 2 つは意味が違う**。

- `upsert` の `<=` は正しい。同じ状態の書き直し（冪等な再書き込み）を許す必要がある。
- `curate` の `<=` は誤り。採択済み（rank 1）の提案を却下（同じ rank 1）で上書きできる
  ——**2 人が別の判断を入れたとき、後の判断が黙って勝つ。**

統合テストが検出した（「2 回目の curation は `False` を返す」を先に書いていた）。`<` に直した。

**同じ形のコードを写すときに、述語の向きまで写してはいけない。** 「後退を防ぐ」という目的は
同じでも、「同じ位置への書き込みを許すか」は操作によって違う。`upsert` は冪等であるべきで、
`curate` は 1 回しか起こってはいけない。

### 97. 投影が一方向になる場合がある

不一致（ADR-0013）と期待（M8-18）は往復する投影だった。概念提案は**往復しない**——
`signals[].cluster` が `LatentCluster`（`centroid: NDArray[np.float64]`）を持ち、これを表に
入れない決定をした（ADR-0015）。潜在ベクトルは潜在索引のもので、作業項目表に置くと同じ値が
2 箇所にあり、再接地で片方だけが古くなる（索引は WM 版で無効化されるが、この表はされない）。

**所見 90 の反省を適用した。** 「同名なのに違う値」を黙って作らないために:

1. `from_record` の docstring に「`cluster` は `None` になる」と書いた。
2. **テストでそれを固定した**（`test_the_cluster_is_deliberately_not_restored`）。将来誰かが
   復元するようにしたら、ADR-0015 を読み直すために落ちる。
3. 代わりに**判断に要る 2 つのスカラー**（`support_count` / `coverage`）を書き込み時に導出して
   列に出した。重心を落とすと読み出し側で計算できず、UI の curation 検査（設計書 §11.2 の
   「標本 10 件未満は偶然のクラスタと区別できない」「被覆率 50% 超なら既存概念の調整で足りる」）
   が機能しなくなる。

**「落とす」決定と「導出して残す」決定は対になる。** 計算の文脈（重心）は捨てていいが、
**人の判断材料は捨てられない**。どちらも捨てると curation が「名前と定義を読んで決める」に
退化する。

### 98. 「記録するだけ」が画面を壊していた

`_apply_curation` は採否を**ログと要約に残すだけ**だった。表が無かった時期は正しかったが、
M8-19 で表を作った時点で穴になった——**採否を入れても提案が `proposed` のまま残り、同じ提案が
永久に curation の画面に出続ける。**

状態を進めるようにした。その際、**本体を読み戻さずに `jsonb_set` で状態と理由だけを差し替える**
——読み戻すと重心を欠いた提案を書き直すことになり、payload が劣化する（所見 97 の非対称性の
帰結）。

**「記録するだけ」は、読む先ができた瞬間に不足になる。** ADR-0012 で「自動適用しないもの」を
決めたが、`信頼性更新` / `負例バッグ` / `概念候補` の 3 つはいまも記録するだけである。それぞれ
読む先ができたときに、同じ見直しが必要になる。

### 99. ドキュメントの数値が静かに古くなっていた

2026-10-04 の棚卸しで、ドキュメントに手で書いた数値が実装から乖離していることが分かった。

| 記述 | 書かれていた値 | 実測 |
|---|---|---|
| `PROGRESS.md` のテスト件数 | 1151 / 108 / 61 | **1420 / 187 / 77** |
| 同じ節の ADR 件数 | 表に「7 件」、直後の文に「6 件」 | **15 件** |
| `TASK.md` M8-14 の配線済み指標 | 7 指標、残り 18 | **9 指標、残り 16**（`contrib_*` が 3） |
| `STATUS.md` の里程 | M0〜M7 のみ（M8 の行が無い） | M8 が 16 / 22 で進行中 |
| `README.md` のドキュメントマップ | 「M0〜M7 タスク分解」 | M8 を含む |

**同じ節の中で「7 件」と「6 件」が併記されていた**のが分かりやすい症状である。片方を直して
もう片方を忘れた痕跡で、**どちらも誰も読み返していない**ことを示している。

テストはコードの乖離を落として知らせるが、**ドキュメントの数値には検査が無い**。X-07 として
「機械で検査できる数値」（ADR のファイル数、マイグレーションの連番、ワーカー数、`METRICS` の件数と
配線済みの数、HITL が参照する ADR の実在）を契約テストに入れることにした。

**テスト件数そのものは検査しない。** テストを 1 件足すたびにドキュメントが落ちるのは本末転倒で、
「どこに書くか」を 1 箇所に絞るほうが先である。いまは `STATUS.md` と `PROGRESS.md` の 2 箇所に
書いていて、**それ自体が乖離の原因**だった。

### 100. 「未決」が 3 箇所に散っていた

人の判断を待つ事項が **`TASK.md` §7（5 件）/ 各 ADR の「未決」（9 ADR に 21 項目）/
コードの `TODO(question)`（M8 で 0 件になった）** の 3 箇所に分かれていた。

結果として:

- `TASK.md` §7 の 5 件のうち **2 件は既に決着していた**（CI 基盤は X-01 で GitHub Actions に、
  UI の技術選定は ADR-0008 で決定済み）が、消されずに残っていた。
- ADR の未決にも**解決済みのものが残っていた**（ADR-0010 の「不一致の永続化が無い」は M8-12 で、
  ADR-0011 の「要求を書く側が未実装」は M8-08 で、ADR-0013 の「UI の差し替え」は M8-16 で解決）。
- **「タスクが止まっている理由」と「誰の判断待ちか」が突き合わせられなかった。** M8-10 が

**散らばりは件数ではなく「突き合わせられるか」で評価する。** 3 箇所にあること自体は悪くなく
（入口が複数あるのは良い）、問題は**どこにも全体が無かった**ことである。

## 設計上の判断（ADR に至らなかったもの）

ADR を起票するほど大きくないが、後から「なぜこうなっているか」を問われる判断の記録。

| 判断 | 理由 |
|---|---|
| MIL は max ではなく noisy-OR 定式化 | max では 1 標本にしか勾配が流れず、長いバッグで学習が進まない |
| 勾配の適用を `LinearProbe.apply_gradient()` に集約 | MIL が private 属性を直接書き換えるのをやめ、学習則を 1 箇所に置いた。能動学習・連合学習を足すときも更新規則が 1 箇所で済む |
| 包含確率はモンテカルロ（標本 2000） | 一般のポリゴンに対する 2 次元ガウスの積分は解析解を持たない。標準誤差 0.011 は閾値（θ_1 = 0.8 など）に対して十分細かい |
| `most_likely_zone` は閾値未満で `None` | 「どこにあるか言えない」が、適当に最大値を返すより正しい答えである |
| 証拠が無い束縛は確率が事前（0.5）付近に留まる | 根拠なしに束縛しないことを、閾値ではなく確率計算の構造で保証する |
| 業務記録由来イベントの様相は `observed` | 「この記録が存在する」ことは観測された事実。記録が主張する状態の信念は `reasoning` が `inferred` で出す |
| 書き戻しの `dry` 判定を writer 呼び出しより手前に置く | 「dry のつもりで実際に書いた」事故を構造的に防ぐ。dry では writer を一度も呼ばない |
| 補償アクションを `WritebackCommand` の必須フィールドに | 既定値を持たせず、省略すると構築に失敗する。取り消せない書き戻しを基盤から出さない |

## 次の着手（2026-10-04 更新）

**M8「配線」が 16 / 22 まで進んだ。** ゲート G8 の 3 条件のうち 2 つ（G0〜G7 維持、
`TODO(question)` 0 件）は満たしており、残るのは M8-11（4 ワーカーを実物のサービス上で回す）である。

### M8 で分かった形

M8 の目的は「型と判定は実装済み、供給元と周期実行が未実装」を埋めることだったが、実際に出てきた
形はもう少し細かく、**4 つに分かれていた**。

| 形 | 典型 | 対処 |
|---|---|---|
| **供給元が無い** | プローブ束ねが無いので bridge-worker が走れない（M8-01/02） | 置き場と形式を決める |
| **置き場が無い** | 不一致・期待・概念提案・人の判断に表が無い（M8-12/18/19、ADR-0012〜0015） | **作業項目は信念ではないので表に置く**（イベントログに席が無い） |
| **呼び出し元が無い** | `MetricStore.write` / 契約 → 期待の変換 / アクション実行（M8-14/20/21） | 運用経路に出す |
| **読み先が別物だった** | UI の 4 ビューのうち 3 つが存在しない契約を読んでいた（M8-16/18/19） | 契約テストで機械検出できるようにする |

**4 つ目が最も危なかった。** UI は「動くはず」の形で出荷されており、読む先が存在しないトピックで
あることも、型が backend と別物であることも、**テストが 1 つも落ちない状態だった**（所見 83 / 85 / 86）。
`tests/contract/test_ui_api_contract.py`（16 件）がこれを機械検出するようになり、いまは
**UI がストリームを 1 本も読まない**ことまで固定している。

### M8-17 が難しい理由（着手前に読む）

設計書 §8.2 の「証拠並置」は、不一致の両側（物理の観測と業務の記録）を人に並べて見せる機能である。
いまの UI は参照 IRI の一覧までを出している。足りないのは 2 つ:

1. **アサーション ID で信念を引く API。** `AssertionStore.query` は主語・述語でしか絞れない。
   不一致は参照先を ID で持つので、ID 引きが要る（ADR-0013 の未決）。
2. **源の判定。** **三源は様相では分かれない**——業務記録由来の信念も推定を経ると `inferred` に
   なるからである（所見 84）。源は来歴の `contrib: {observed, record, plan}` にあり、
   「どの源が支配的だったか」はそこから読む。つまり**並置の単位は「様相」ではなく「寄与」**である。

この 2 つ目を間違えると、「`observed` の文と `inferred` の文を並べる」という**成立しない並置**を
作ることになる。

### 実データに当てるまで確かめられないもの（変わらず）

| 項目 | なぜ合成では足りないか |
|---|---|
| プローブの AUROC | SynthWorld の難度が低い（所見 25）。AUROC 1.0 は「機構が動く」の証拠であって性能の証拠ではない |
| 概念発見 | 仕込んだ `Accessible` が実質 `¬Running` で、発見がやや自明になる |
| 潜在復元攻撃 | 実データの潜在でなければ、個体同定の危険を測ったことにならない |
| 照合の適合率 | 注入ハーネスが作る不一致は、注入した通りに検出される |
| 再接地の所要時間 | 文の数が実運用と桁で違う |
| 業務効果の期待の下端 | 記録の信頼性による割引の実測値が合成では出ない（所見 92） |

**ユースケース検証は別リポジトリで行う**（CLAUDE.md、ADR-0001）。本リポジトリの役目は、そのときに
「何を測ったのか」が分かる形で基盤を渡すことである——そのためにゲートの記録には実測値と
**その数値が証明していないこと**を併記してきた。体制の決定は `docs/HITL.md` の H-18。

### 引き継ぐ注意点

- **数値を 1 つで語らない。** 昇格ゲートの AND 条件（AUROC + ECE + 整合残差）、予測の被覆率と
  CRPS と区間幅、プローブ評価と整合残差。1 つだけ見ると無情報なものが通る（G5 の実測で確認）。
- **「統合テストが通る」は「運用で動く」ではない。** G5 は閉ループをテストの中で完走させたが、
  production には生成コードが無かった（所見 89）。G7 の runbook も同じ形で「参照先が実在する」
  までしか機械で検査できていない。
- **型と判定だけでは動かない。** M8 で繰り返し出た形で、「誰が最初の値を書くか」が抜ける
  （所見 72）。新しい型を作ったら、書く側と読む側の両方を同じ PR で確かめる。
- **投影の列は同名のプロパティと同じ値にする。** 違う値を入れると、どちらを見ているかで答えが
  変わり、読んで気付けない（所見 90）。違う意味の値が必要なら別の名前を付ける。
- **既定値が便利な場所と危険な場所がある。** `uuid4` の `default_factory` は 1 回限りの呼び出しでは
  正しいが、再試行される経路では「毎回違う値」が欠陥になる（所見 93）。
- **人の判断待ちを推測で埋めない。** `docs/HITL.md` に 21 件ある。止まっているタスクには
  「H-NN の判断待ち」と書いて、理由と待ち先を突き合わせられる状態にする。
