## 実装中に判明した事実

設計書の前提が外れた箇所と、テストが暴いた欠落の記録。**この節が本書の主眼**である。

### 1. MinIO の公開イメージが取得できなくなっていた（ADR-0003）

`make up` が `pull access denied` で失敗。Docker Hub と quay.io の両方にレジストリ API で
問い合わせ、タグを明示しても **HTTP 401** が返ることを確認した。匿名取得の経路を失っている。

`make bootstrap` から新規環境で再現できなければゲート G0 の条件を満たせないため、S3 互換の
SeaweedFS に置換した（サービス数は 4 のまま、API 契約は不変）。

**教訓**: 設計書がイメージ名を指定していても、それが取得できる保証は設計時点のものでしかない。
`make bootstrap` の再現性をゲート条件に入れておいたことで、この種の腐りが早期に検出された。

### 2. Oxigraph の公式イメージは distroless で healthcheck が書けない（ADR-0004）

シェルも wget も無く、CLI の `oxigraph query` は `--location`（ローカルストア）しか取れない。
稼働中のサーバと同じ location を開くと RocksDB のロックで競合するため、**コンテナ内から HTTP
疎通を確認する手段が存在しない**。

形だけの healthcheck（`oxigraph --version`）を置く選択は棄却した。バイナリが動くことしか
確認せず、サーバが落ちていても healthy になる——healthcheck が無い状態より悪い。疎通検査を
統合テストの fixture とワーカー起動時に移した。

### 3. 設計書が想定した RDF-star 記法が使えなくなっていた（ADR-0005）

設計書 §6.6 のクエリ例は「引用三つ組を**主語**に置く」旧 RDF-star 記法を使っている。
pyoxigraph 0.5 ではこれが `TypeError` になる。RDF 1.2 で quoted triple が **triple term** に
再定義され、**目的語位置にのみ出現できる**ようになったためである。

スパイクで確認した結果、`?a rdf:reifies <<( ?s ?p ?o )>>` の形なら as-of クエリまで動作する
（埋め込みストアと HTTP サーバの両方で検証）。要件は満たせるが記法が違う。設計書・層別ルール・
ADR に反映した。

**教訓**: `docs/PROMPT.md` の M0-11 プロンプトに「満たさない場合は実装に入らず ADR 草案を
提示せよ」と書いておいたことが効いた。実装前のスパイクで分かったため、手戻りは記法の決定だけで
済んだ。

### 4. Python の RML プロセッサが使えない（ADR-0006）

`morph-kgc` は依存に `pyoxigraph<0.4` を持ち、ADR-0005 で必須の 0.5 系と**衝突する**。さらに
duckdb / pandas / geopandas / neo4j / databricks を引き込み、4 サービス制約と相容れない。
`pyrml` は 2016 年で更新停止。

設計書 §7.2 の考え方（キー・必須制約・多重度の保存を写像の不変条件として検査する）は維持し、
実装手段だけを最小の YAML DSL に変えた。3 つの保存性を**宣言の一部**として持たせたので、
宣言の段階で保存性を壊す設定（キー以外を `external_id` に混ぜる、キー列を必須にしない）を
弾ける。

### 5. 自前の正規分布分位点が大きく外れていた

時刻ずれの許容プロファイル（類型 3 の判定閾値）に使う分位点を有理近似で書いたところ、
p95 が **565 秒**（正しくは 307 秒）になっていた。閾値がずれると時間不一致の判定が狂う。
標準ライブラリの `statistics.NormalDist` に置き換えた。

**教訓**: 「依存を増やさない」は良い方針だが、**標準ライブラリにあるものを自前で書く理由は無い**。
数値の正しさをテストで押さえていたため検出できた（設計書 §3.6 の「MES ±5 分」と突き合わせる
テストが落ちた）。

### 6. BOCPD の変化点確率がデータに反応していなかった

事象昇格の変化点検出が 1 件も検出しない。調べると変化点確率が**ハザード率一定**（0.0083）に
張り付いていた。原因は変化点項に「継続中の run の予測確率」を使っていたこと。成長項と同じ
予測確率が掛かるため、正規化で打ち消されてデータを一切見なくなる。

新しい区間は過去データを持たないので、その最初の観測は**事前予測**に従うのが正しい。修正後は
変化点 0.153 対 平常 0.004（35 倍）になった。

さらに判定基準を絶対閾値（0.3）からベイズ因子（事後 ÷ 事前、既定 5.0）に変えた。絶対閾値では
適切な値がハザード率に依存して扱いにくい。ハザード 1/60〜1/300 で同じ変化点が出ることを
テストで確認した。

### 7. SHACL の `sh:severity` を書く位置を誤り、設計の真逆の挙動になっていた

`sh:severity` は**シェイプの属性**であり（SHACL 仕様 §2.1.3）、`sh:sparql` の制約ノード内に
書くと無視されて既定の `sh:Violation` になる。そのため整合制約（排他フルーエントの衝突、
非対称な排他宣言）が Violation として動き、「登録して不一致候補にする」はずのものが
**隔離されていた**。

これは設計書 §3.9「検証は拒否ではなく証拠生成」の真逆であり、検出したい状態が消える。
`sh:severity` をシェイプ側に移し、Warning が登録を止めないことをテストで保証した。

**教訓**: 「Warning は登録を止めない」というテストを書いていたから見つかった。形状が通ることだけを
確認していたら、本番で不一致が静かに消え続けていた。

### 8. テストがオントロジーの欠落を 2 件暴いた（オントロジー 0.3.0）

SynthWorld に「合成世界は事象計算で説明できる状態変化しか作らない」という不変条件テストを
置いたところ、2 件の不整合が出た。

- **Faulted が再起動で解消していた。** 事象計算で `faulted` を terminates するのは `maint_end`
  だけなので、合成世界が「説明できない状態変化」を作っていた。整合残差は `A∘f` と `T∘A` の
  ずれを測るものなので、基準となる世界が事象計算と矛盾していると指標そのものが無意味になる。
- **`Accessible` を変化させる事象型が 1 つも無かった。** 設計書 §9.1 でアクションの物理前提
  （`P(Accessible(?pump)) >= 0.8`）に使われるのに、成立・不成立にする経路が無く、永久に初期値の
  ままになる。物理に即して 4 件追加した（`StopCmd` / `Fault` / `MaintStart` が initiates、
  `StartCmd` が terminates）。

あわせて `make ontology-check` に検査を追加した: **すべての FluentType は少なくとも 1 つの
EventType に変化させられること**。既存の `EventTypeShape`（すべての EventType は何かを
変化させる）の双対であり、片側しか検査していなかったためにこの欠落が通っていた。

### 9. `ontology-check` の生成物鮮度チェックが偽陽性を出していた

git status の前後比較で判定していたため、作業ツリーの状態に依存して誤検出した。内容ハッシュ
比較に変えた。さらに `make lint` の整形が生成物を書き換えて鮮度チェックと循環する問題があり、
生成の最終段で `ruff format` をかけて出力を正規化した。

### 10. 二時制クエリが拠点で絞っていなかった

統合テストで、ある拠点のストアが**他拠点のグラフまで読んでいる**ことが分かった。設計書 §6.3 は
グラフを `<modality>/<site>/<ontologyVersion>` で分割し、中央がフェデレーションすると定めている。
既定で自拠点のみを見るようにし、横断は `all_sites=True` を明示する形にした。

### 11. 事前に継続確率を足し込むと信念が飽和して観測が効かなくなっていた

**M3-02 の初版の欠陥。** 半マルコフの事前を作るとき、滞在時間分布の生存比（長寿命の状態では
対数オッズ ≈ +9）を事前に**加算**していた。結果、稼働が長く続いた設備の事前が 1 に飽和し、
「停止している」というプローブ出力が事後をほとんど動かせなくなった。

継続確率は「崩れにくさ」であって「真である証拠」ではない。マルコフ遷移
`事後 × 継続確率 + (1 − 事後) × 開始率` に直し、計画は重み 0.2 の**混合**として入れた
（上書きでも加算でもない）。設計書 §14 の事後 0.14 が再現できるようになった（実測 0.1302）。

### 12. 抑制規則が「系統誤差があること」だけで働いていた（2 段の欠陥）

**設計書 §8.2 は抑制を「信頼性モデルで説明できる系統誤差」に限定している。** 実装は 2 段階で
これを緩めていた。

1. 初版は「証拠の記録が何らかの系統誤差に当てはまる」だけを条件にしていた。月末一括計上
   （記録が**いつ入ったか**の偏り）で**状態の食い違い**まで抑制できてしまう。記録が遅れて
   入ったことは、記録が別の状態を主張していることの説明にならない。系統誤差の種別ごとに
   抑制してよい類型を限定した（`_BIAS_APPLIES_TO`）。
2. それでも G3 の注入テストで、注入した時間不一致が抑制された。原因は**規模を見ていない**
   こと。シフト境界の丸め（規模 8 時間）が 48 時間のずれまで説明してしまう状態だった。
   偏りが存在することと、その偏りがこのずれを説明することは別である。規模がずれを覆って
   いるかを第三の条件に加えた。終端の無い不一致は「規模で覆えた」と主張しない。

抑制は照合エンジンで最も危険な機能である（「不都合な不一致を消す装置」に転用されうる）。
条件を 3 つに増やしたのは慎重さではなく、1 つでも落ちると万能になるからである。

### 13. 事象計算の `.lp` が一度も実行できない状態だった

**M3-08 で clingo を回して初めて分かった。** `ontology/process/equipment-maintenance.lp` の
`clipped/4` が安全でない変数（`T0` と `T` が比較にしか現れない）を持ち、**接地できなかった**。
慣性規則が働かないので `holds_at` が一切導出されない。

M2 までは事象計算を Python 側（`bridge/lifting.py`）で実装していたため、`.lp` は「記号遷移 T の
宣言」として読まれるだけで実行されていなかった。`make ontology-check` は TTL と `.lp` の
**対応**（initiates / terminates の整合）を検査するが、プログラムとして**動くか**は検査して
いなかった。M3-08 の単体テストが接地・慣性・排他・前提条件を実行して確かめるようになった。

同時に、プログラム部名をファイル名から作っていたため `process/` と `norms/` に同名ファイルを
置くと後勝ちで規則が消えることも見つかった（親ディレクトリ名を含めて一意にした）。

### 14. 類型 3 の順序違反規則が存在しない順序を発明していた

観測時刻・記録時刻の前後を `<` で比較し、「観測の順序と記録の順序が違えば違反」としていた。
同時刻の対では等号が「より前ではない」に落ちるため、**片側だけが同時刻の対がすべて順序違反**
になる。同時刻の対に矛盾しうる順序は無い。等号の対を明示的に除外した。

### 15. 設計書のインタフェースが層依存と衝突した（ADR-0007）

設計書 §4.3 の `WorldModel` は `probe(z, probeIds[])` と `explain(z, probeId)` を持つ。プローブ ID を
引数に取る以上、`worldmodel` が `bridge` の型を知る必要があり、**層依存（`worldmodel ← bridge`）と
「WM は記号を決めない」という責務分担の両方に反する**。import-linter の契約が機械的にこれを
禁じているので、実装に入った時点で衝突が表に出た。

代わりに `attribute(state, weights)` を置いた。`weights` は線形汎関数の係数（線形プローブの重みが
そのまま入る）で、WM はそれが何の概念なのかを知らない。利用者から見た説明の情報量は変わらない
——説明サービスが受け取る `LatentSide` はプローブ ID・出力・WM 版・帰属をすべて持つ。

同じ理由で `health()` の整合残差も引数で受け取る形にした。渡されなければ 0 のままで、
「評価していない」ことが呼び出し側に見える。

### 16. 監査隔離マスクは `core` に置くしかなかった

`AuditMask` は記録尤度の計算（`reasoning`）と記号条件付けの生成（`worldmodel`）の**両方が必須
引数に取る**。しかし `worldmodel` は `reasoning` を import できない。CLAUDE.md の「層をまたぐ
結合は `core` の型と `eventlog` のイベントだけ」に従って `core/audit.py` に移した
（`reasoning.audit` は再輸出として残し、推論層から見た読み口を保っている）。

M3 の時点では `reasoning` 内にあっても動いていた。層をまたぐ契約であることが、実際に 2 つ目の
利用者が現れて初めて分かった。

### 17. 時間順を前提とする損失項をシャッフルしたバッチに当てると潜在が潰れる

`smoothness_penalty`（連続する潜在の差を罰する慣性項、設計書 §4.6 の L_phys の最小形）を
既定のバッチ（毎エポック並べ替え）に当てると、「無関係な標本どうしを近づける」ことになる。
実測で `latent_std` が 0.845 → 0.079 に落ち、段階ゲートが落ちた。

`contiguous_batches` 引数を足し、既定を偽にした。気付かずに時間順を仮定するほうが危険なので、
時間順が必要な項を使うときに明示させる形にしている。

### 18. 潜在の部分的な崩壊は AUROC に出ず ECE に出た

jepa_ts の分散項（VICReg）を実質 0 にして比較した:

| 構成 | latent_std | AUROC | ECE |
|---|---|---|---|
| 健全 | 0.9714 | 1.0000 | 0.0048 |
| 分散項なし | 0.1573 | 0.9984 | 0.0349 |

**分離はできるが確信度が壊れる。** ECE は昇格ゲートの上限 0.05 の手前まで悪化したが、AUROC は
0.9984 で基準（0.85）を大きく上回ったままだった。昇格ゲートが AUROC ∧ ECE ∧ 整合残差の AND に
なっている理由の実測的な裏付けで、AUROC だけを見ていると潰れかけた潜在を active にする。

### 19. 潜在索引の次元は「版ごとに固定」では足りなかった

`.claude/rules/knowledge.md` は「次元 D は `wm_version` ごとに固定。次元が変わる WM 更新は新
テーブル `latent_index_v<N>` を作る」と定めている。実装して分かったのは、**命名規約だけでは
運用で表を取り違える**ことである——`latent_index_v2` という名前からは次元が読めない。

`latent_index_registry(wm_version, table_name, dim)` を置き、アプリは登録表を引いてから書く
形にした。未登録の版では書き込みが成立せず、次元の食い違いは INSERT 前に落ちる。表名は
`latent_index_d<次元>` にして運用者が名前で判断できるようにした（規則の `v<N>` から逸れるが、
版と表の対応は登録表が持つので命名は補助情報である）。

### 20. 設計書のインタフェースが層依存と衝突した（2 件目）

M4 の ADR-0007 と同じ種類の衝突が M5 でも出た。``encode_intervention`` を
``ActionContract`` を受け取る形で書いたところ、``reasoning`` が ``actions`` を import することに
なり import-linter が落ちた（層は ``reasoning ← actions``）。

ADR には至らなかった。**介入の符号化に必要なのは「どのアクション型か」だけ**で、前提や効果は
要らない——契約を受け取る設計は、必要以上のものを要求していた。アクション型 IRI を取る形に
直して解決した。設計から逸れたのではなく、設計を実装に落とすときの引数の取り方の問題である。

### 21. 契約の CURIE 展開漏れは「静かに全アクションが実行不能」になる

``ActionContract`` の ``action_type`` / ``targets`` / ``compensation`` だけ CURIE を展開し、
前提と効果の中（``fluent``、``record_type``）を忘れていた。結果、前提の ``ent:Accessible`` が
展開されないまま残り、呼び出し側が渡す完全 IRI の信念と一致せず、**全アクションが「信念が無い」
として実行不能**になった。

エラーではなく「前提未達」として静かに落ちるのが厄介である。前提検証が「知らないことを満たして
いるとみなさない」設計（これ自体は正しい）と組み合わさると、展開漏れが安全側に倒れて気付きにくい。
スモークテストで前提が通らないことに気付いて見つけた。

### 22. 片側が未観測の期待を「成立」と判定していた

``Expectation.verify`` の初版は「記号側が通って潜在側が未観測」でも ``Fulfilled`` にしていた。
観測できていない期待を成立と呼ぶと、**検証していないものが学習信号に混ざる**。宣言されている面
すべてに判定が付いて初めて ``Fulfilled`` にするよう直した（単体テストが捕まえた）。

### 23. 訂正提案が学習信号に数えられていなかった

設計書 §8.2 の表は「物理が正しい → 記録訂正（書き戻し提案）」を第一の処置に挙げているが、
付録 A.2 の ``learning`` には対応する欄が無い（``labels_emitted`` / ``reliability_updates`` /
``concept_candidates``）。そのまま実装したため、**訂正提案だけを生んだ解決が「何も学ばなかった」
として ``Resolved`` に留まった**。

``corrections_proposed`` を加法的に追加した。G5 の統合テスト（ワークドエグザンプルの完走）が
これで落ちて見つかった——単体テストでは訂正提案と信頼性更新を同時に渡していたので通っていた。
**統合テストが「部品は正しいが繋ぐと通らない」を捕まえた**例である。

### 24. 被覆率は「区間を広げる」だけで買える（ゲートの設計の問題）

ゲート G5 の数値条件は「予測被覆率 ≥ 0.85」である。最初は固定幅の区間で持続予測を作り、先行
300 秒の被覆率が 0.800 に落ちた。**幅を広げれば通る**が、それは較正ではなく調整である。

設計書 §8.5 の conformal を実装し（``conformal_halfwidth``）、較正データの残差分位点を半幅に
した。交換可能性の仮定の下で名目被覆が保証され、手で決める余地が無い。結果:

| 先行時間 | 被覆率 | CRPS | 区間幅 |
|---|---|---|---|
| 60 s | 0.9500 | 0.0372 | 0.0338 |
| 300 s | 0.8667 | 0.1548 | 0.9801 |

**ゲートは通ったが、先行 300 秒の区間幅は 0.98——ほぼ [0,1] 全域である。** 被覆率 0.87 はそれで
買っている。CRPS と ``reliable_lead_time``（60 秒）が「実際に使える地平は 60 秒まで」を示す。
設計書 §8.3 が「地平ごとの信頼できる先行時間を公開する」と言っているのはこのためで、被覆率を
単独の合格条件にすると無情報な予測が通る。**G6 以降のゲートに数値条件を足すときは、指標を 1 つ
だけ見ない。**

### 25. 「未知概念を仕込む」のが合成世界では難しい

ゲート G6 は「SynthWorld に未知概念を仕込み、発見できるか」を見る。実際にやってみると、
**仕込める概念が無かった**。

- ``VibrationAnomaly`` は 87.5% の時間成立する単一区間（02:41–06:11）。保留窓が全て真で
  AUROC が定義できない。
- ``Accessible`` は保留窓に両クラスが入る唯一のフルーエントだが、SynthWorld では実質的に
  ``Running`` の否定である。つまり「Running プローブが反応しない領域」= ``Accessible`` で、
  **発見がやや自明になる**。

``Accessible`` を使って機構（低被覆クラスタ → 弱ラベル → プローブ → 再接地）が通ることは確かめ、
**限界をテストの docstring とゲートの記録に明記した**。数値（AUROC 0.9995）は機構が動くことの
証拠であって、「独立した未知概念を見つけられる」ことの証拠ではない。

合成データのゲートは「機構が動くこと」までしか示せない、という一般的な教訓でもある。G2 の
AUROC 1.0 と同じ構図で、**測れたことと主張できることを分けて書く**必要がある。

### 26. 劣モジュラ性と「質問しすぎない」は別の機構である

スケジューラの最初の実装で、「同じことを 2 度確かめるバッチを作らない」ことを劣モジュラ性に
期待していた。実測すると、信頼度 0.95 の観測の後も残存エントロピーは 0 ではないため、
**コストが極小な重複観測は効用が正のまま残る**。

これは正しい挙動である。安いセンサ測定をもう 1 回するのは実際に少し情報を増やす。人への重複
質問を止めるのは劣モジュラ性ではなく**質問頻度の上限**の役目だった。2 つの機構を混同していた。

割引係数の足し引きではなく**残存エントロピーの追跡**に変えたのも同じ検討から出ている。割引係数
では「信頼度 0.95 の観測を 2 回」が「1 回の 2 倍の情報」になりうる（0.9 + 0.9 > 1.0 を 1.0 で
クリップするので）。残存エントロピーなら複利で正しく減衰する。

### 27. LLM をホットパスから外すのは「層」では表せない

不変条件 11（LLM をホットパスから呼ばない）を import-linter で検査しようとして、``sbp.reasoning``
全体を禁止できないことに気付いた。同じ層に**ホットパス（信念更新・照合）と非ホットパス（概念
発見・説明）が同居している**。

契約はモジュールを名指しする形にした（``sbp.reasoning.belief``, ``sbp.reasoning.coupling``,
``sbp.reasoning.rules``, ``sbp.reasoning.reconciliation``, ``sbp.bridge.lifting``,
``sbp.bridge.probes``, ``sbp.bridge.calibration``）。層の粒度では表せない不変条件があり、
その場合はモジュール単位で明示する。G6 のテストでも対象モジュールの本文を直接確かめ、契約が
誤って外されたことに気付けるようにした。

### 28. 不変条件 7 が「較正していない旧版」を作らせないので、版の違いは学習量で付けた

G7 のテスト設計は「プローブ v1 で接地 → v2 に上げて再接地 → as-of で両方の判断が返る」である。
最初は v1 を**較正していない版**にしようとした——現実の版上げでは較正手順自体が変わることも
あるからだ。``predict()`` が拒否した。不変条件 7（``belief`` には較正済みの値だけ）が、
較正されていないプローブから信念を作る経路をそもそも塞いでいる。

**不変条件が先に立っていることの確認になった**が、同時にテストで表現できる版差が狭まった。
v1 = 30 エポック、v2 = 500 エポック + 較正、という学習量の差に落とした。現実の版上げに近い形で
はあるものの、「アルゴリズムを変えた版上げ」の挙動は確かめていない（G7 の記録に明記した）。

### 29. 「runbook に従って第三者が実行できる」は機械では検査しきれない

ゲート G7 の条件に「runbooks に従って別セッションが再接地を実行できる」がある。自動テストに
できるのは**手順書が参照する記号が実在すること**まで——``plan`` / ``run`` / ``RegroundingReport``
が ``sbp.knowledge`` にあるか、という検査である。手順の分かりやすさ、前提の書き漏れ、
「この状態のときどうするか」の抜けは、人が読んで実行しないと分からない。

G7 を「条件つき通過」と記録した。**何を検査して何を検査していないかを区別せずに「通過」と
書くと、次に読む人は全部が検査済みだと受け取る。**

### 30. 二時制の UI に正規化キャッシュは使えない

M7-04 で GraphQL クライアント（Apollo / urql）を入れるか検討して、やめた（ADR-0008）。
正規化キャッシュは「同じ ID なら同じエンティティ」を前提に、新しい応答で古い値を上書きする。
**二時制ではこの前提が誤りである**——``asOf`` が違うだけの同じ ``subject`` は別の事実であり、
上書きすると「過去の判断を今の判断で塗り潰した」表示になる。

キャッシュを無効化して使うなら入れない方が単純で、依存が減ると型検査とテストが数秒で終わる。
**検査が遅いと検査しなくなる**ので、これは速度の話ではなく「完了の定義を毎回満たせるか」の話
である。

### 31. UI で最も重要な判断は「何を入力させないか」だった

不一致キューに「正しい値」の入力欄を置かなかった。解決の入力は**どの前提が崩れていたか**の
分類（記録が誤り / 観測が誤り / 定義の食い違い / 系統的な偏り / 判断不能）であり、真偽の宣言
ではない。「正」フラグを作らない（CLAUDE.md のやってはいけないこと）は、データモデルの話だと
思っていたが、**UI の形に出ないと意味が無い**ことが分かった。入力欄があれば人はそこに真偽を
書き、基盤は受け取ってしまう。

同じ理由で、理由の記入を必須にした（10 文字以上）。種別だけでは学習信号にならない——何を見て
そう判断したかが残らないと、後で信頼性モデルの更新を説明できない。設計書 §8.3 の「解決入力が
学習信号になる」は理由まで含めての話だった。

### 32. 「0 件」と「経路が動いていない」を UI が区別しないと、静かな故障が緑に見える

期待ボードの違反列、不一致キュー、概念提案のいずれも、空のときに注意書きを出すようにした。
「違反 0 件」と「違反を検出する経路が走っていない」は違う情報である。前者は良い知らせだが、
後者は障害であり、**画面上はどちらも空のリストに見える**。

読み込みが失敗したときも同じ問題がある。最後に成功した内容を出したまま黙っていると、空の
キューが「不一致なし」として読まれる。失敗を明示し、「空のキューを不一致なしと読まないこと」
と書いた。

### 33. プライバシー検証は陽性対照が無いと「測れていない」ことに気付けない

潜在復元攻撃を書いていて、最初の実装は「個体を同定できなかった」で成功としていた。これは
**攻撃の実装が壊れていても同じ結果になる**。区別するには、復元できるべきものが同じ攻撃で
復元できることを確かめる必要がある。

``PrivacyAudit.is_conclusive`` を入れ、陽性対照が失敗した監査は「安全」ではなく「測れていない」
として扱う（``leaks`` は安全側に真を返す）。シークレット走査でも同じ構えを取り、偽の鍵を食わせて
検出されることをテストにした——実装直後に自分のテストファイルを 3 件検出したので、走査が
空振りしていないことは確認できている。

攻撃を 2 種類に分けたのも同じ検討から出ている。**属性復元が成功するのは違反ではない**
（潜在から軸受温度が戻るのは基盤が機能している証拠、実測 R² > 0.8）。危険なのは個体同定だけで、
混同すると「潜在は何も表現してはいけない」という使えない結論になる。

### 34. ABAC を「既定は拒否」にすると既存のテストが落ちる。それが正しい

API に ABAC を入れたとき、``principal_resolver`` 未設定で信念クエリが全拒否になり、既存の
API テスト 3 件が落ちた。「未設定なら通す」経路を残せば落ちなかったが、**それは開発中の全開放
がそのまま本番に残る形**である。テスト側に要求者を渡すように直した。

拠点の判定でも同じ選択をした。グラフ名から拠点が取れなければ拒否する——「拠点が判らない＝
誰でも見てよい」と解釈すると、グラフ名の規約が変わった日に全拠点へ漏れる。

唯一「許可があれば見せる」にしなかったのが人に関わる概念である。外観埋め込み・従業員 ID は
ロールが許可していても返さない（不変条件 9）。**許可の設定ミスがそのまま個人情報の漏洩になる**
ので、許可の内側ではなく外側で止める。

### 35. ワーカーの「処理件数」は取得件数ではない

``step()`` の戻り値を「取り込んだイベント数」にしかけて、やめた。入れなかったイベント
（フルーエントを取り出せない、真偽でない、時刻が戻った、監査隔離）が件数に混ざると、
**何も信念を更新していないのに「100 件処理した」と見える**。戻り値は信念を更新した件数にし、
入れなかったものは理由別に ``ingest.skipped`` へ積んだ。

静かに捨てないことが要点である。パーティション設定の誤りは「実体内で時刻が戻った」の件数として
現れるが、捨てた記録が無ければその兆候が消える。

### 36. イベントが無いループでも周期判定を進める必要がある

最初の実装は「イベントが取れなければ早期 return」だった。これだと**イベントが止まっている間は
実体間結合も止まる**。結合はイベントとは独立に回すべき処理（信念の整合を取る）なので、
取得件数で分岐してはいけない。所見 32（「0 件」と「経路が動いていない」）と同じ構図が、
ワーカーのループにも現れた。

``sink`` が無いときに計算も止めないのも同じ理由である。書き込み先が無いときに計算まで止めると、
配線の誤りが「何も起きない」としてしか現れず、source と sink のどちらが欠けているか分からない。

### 37. 監査隔離はプローブ由来と記録由来で挙動が違う（意図的）

配線のテストで「監査対象の情報源から来たイベントは除外される」と書いたら落ちた。
``AuditMask.excludes_event`` は**記録由来のイベントだけ**を除外し、プローブ由来は除外しない。

これが「物理から記録を監査する」ことの中身である（不変条件 6）。物理観測まで除外したら、
記録を疑うための独立な証拠が無くなり、監査がそもそも成立しない。テストの前提が誤っていたので、
**両方の挙動を明示的に検査する形**に書き直した——非対称性は意図なので、テストで固定する価値がある。

### 38. import 境界の検査が `sbp` だけを見ていて、実運用で動くコードが外れていた

import-linter の `root_packages` が `["sbp"]` だけで、``services/`` と ``scripts/`` が
検査対象の外にあった。契約 7 本はすべて KEPT だったが、**ワーカーから真値（オラクル）を読んでも
検出されない状態**だった——不変条件 10 を機械で守っているつもりで、実運用で動く側が抜けていた。

`root_packages` に両方を足し、オラクル境界と LLM SDK の契約に `services` / `scripts` を加え、
「ワーカーは API 層を経由しない」契約を 1 本追加した（層を 1 周して依存が循環する形を防ぐ）。

**追加した契約が実際に落ちることを、違反を仕込んで確認した。** 落ちない契約は装飾である。
``services.runtime`` に ``from sbp.api import create_app`` と ``from sbp.testing.synth import
SynthWorld`` を一時的に入れ、両方が報告されることを見てから戻した。

このコミットで ``services/belief_worker.py`` の import を増やしたばかりだったので、
穴がちょうど広がった直後に気付いた形になる。

### 39. 「脆弱性なし」は skip を数えないと読めない

``pip-audit`` を入れて X-05 を実行可能にした。``--strict``（skip を失敗にする）は使えない
——sbp 自身が editable install なので PyPI に無く、必ず skip される。

``--strict`` 無しで走らせると、**照会できなかったパッケージがあっても「No known
vulnerabilities found」と出る**。所見 33（陽性対照）と所見 32（0 件と経路が動いていない）と
同じ構図である。``make audit`` で skip の表を読み、sbp 以外が skip されていたら落とすようにした
（この awk の判定も、偽の出力を食わせて動くことを確認済み）。

``make check`` には入れていない。脆弱性 DB の照会にネットワークが要り、`make check` は
Compose もネットワークも不要で通る、という方針を崩したくないためである。CI では独立したジョブに
し、`check` に依存させていない——**脆弱性は自分のコードの状態と無関係に増える**ので、lint が
落ちている間も結果は知りたい。

2026-10-03 の実施結果: ``uv lock --upgrade`` は差分なし（112 パッケージ、既に最新解）、
既知の脆弱性 0 件。

## 設計上の判断（ADR に至らなかったもの）

ADR を起票するほど大きくないが、後から「なぜこうなっているか」を問われる判断の記録。

| 判断 | 理由 |
|---|---|
| MIL は max ではなく noisy-OR 定式化 | max では 1 標本にしか勾配が流れず、長いバッグで学習が進まない |
| 勾配の適用を `LinearProbe.apply_gradient()` に集約 | MIL が private 属性を直接書き換えるのをやめ、学習則を 1 箇所に置いた。能動学習・連合学習を足すときも更新規則が 1 箇所で済む |
| 包含確率はモンテカルロ（標本 2000） | 一般のポリゴンに対する 2 次元ガウスの積分は解析解を持たない。標準誤差 0.011 は閾値（θ_1 = 0.8 など）に対して十分細かい |
| `most_likely_zone` は閾値未満で `None` | 「どこにあるか言えない」が、適当に最大値を返すより正しい答えである |
| 証拠が無い束縛は確率が事前（0.5）付近に留まる | 根拠なしに束縛しないことを、閾値ではなく確率計算の構造で保証する |
| 業務記録由来イベントの様相は `observed` | 「この記録が存在する」ことは観測された事実。記録が主張する状態の信念は `reasoning` が `inferred` で出す |
| 書き戻しの `dry` 判定を writer 呼び出しより手前に置く | 「dry のつもりで実際に書いた」事故を構造的に防ぐ。dry では writer を一度も呼ばない |
| 補償アクションを `WritebackCommand` の必須フィールドに | 既定値を持たせず、省略すると構築に失敗する。取り消せない書き戻しを基盤から出さない |

## 次の着手

**計画上のマイルストーン（M0〜M7）は出し切った。** ゲート G0〜G7 を通過し、`docs/TASK.md` の
§3 に未チェックのタスクは無い。ここから先は性質が変わる。

### 残っているもの 3 種

**1. 横断タスク（`docs/TASK.md` §4）。** 最も効くのは **X-01（CI 整備）** である。現在
`make check` と統合テストは手元で走らせているだけで、**壊れたことに気付く仕組みが人の記憶に
依存している**。サービスコンテナ付きの GitHub Actions で `make check` + `make test-int` +
`make ui-check` を回すのが次の 1 手。

**2. 配線が残っている箇所（上の表を参照）。** 共通しているのは「型と判定は実装済み、周期実行と
イベント消費が未実装」という形である:

- イベント消費の配線（`services/*` の `step()` が処理件数 0 を返す）
- 学習信号の適用（人の判断を受けて実行するワーカー）
- `ObservationRequest` → `ObservationQuery` → 実行 → `observed` の還流
- 発見ループの周期実行

これらは**どれも「人の承認を経る」設計**なので、配線する順番は「人が判断を入力できる経路が
あるもの」から。M7-04 の UI がその入口になった。

**3. 合成データでは確かめられないもの。** これが最も重要で、かつ本リポジトリでは解決できない。

| 項目 | なぜ合成では足りないか |
|---|---|
| プローブの AUROC | SynthWorld の難度が低い（所見 25）。AUROC 1.0 は「機構が動く」の証拠であって性能の証拠ではない |
| 概念発見 | 仕込んだ `Accessible` が実質 `¬Running` で、発見がやや自明になる |
| 潜在復元攻撃 | 実データの潜在でなければ、個体同定の危険を測ったことにならない |
| 照合の適合率 | 注入ハーネスが作る不一致は、注入した通りに検出される |
| 再接地の所要時間 | 文の数が実運用と桁で違う |

**ユースケース検証は別リポジトリで行う**（CLAUDE.md、ADR-0001）。本リポジトリの役目は、
そのときに「何を測ったのか」が分かる形で基盤を渡すことである——そのためにゲートの記録には
実測値と**その数値が証明していないこと**を併記してきた。

### 引き継ぐ注意点

- **数値を 1 つで語らない。** 昇格ゲートの AND 条件（AUROC + ECE + 整合残差）、予測の
  被覆率 + CRPS、概念発見の件数 + 人の採用率。被覆率だけなら区間を広げれば買える（G5 の記録）。
- **「0 件」を良い知らせと読まない。** 不一致 0 件・違反 0 件は、検出経路が動いていない姿と
  区別できない（所見 32）。指標（`discrepancies_raised` など）と併せて見る。
- **陽性対照を取る。** 「検出されなかった」は、安全の証拠にも計測の失敗の証拠にもなる
  （所見 33）。プライバシー検証とシークレット走査では構造として入れた。同じ構えが必要な場所は
  他にもある（照合の適合率、プローブの昇格判定）。
- **不変条件が先に立つ。** G7 のテスト設計は不変条件 7 に阻まれて変更した（所見 28）。
  これは障害ではなく、不変条件が機能している証拠である。回避策を書く前に、**なぜ塞がれたかを
  読む**。
