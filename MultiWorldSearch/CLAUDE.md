# CLAUDE.md — Multi-World Search (MWS) 開発運用ガイド

> **このドキュメントの役割**
> 本書は MWS リポジトリで **「どう作るか」** を定める開発運用ガイドです。Claude Code はタスク着手前に本書を読みます。
> **「何を・なぜ・何をもって成功とするか」（プロジェクト定義）は `PROJECT.md`** にあります。設計判断に迷ったら必ず `PROJECT.md` を先に確認してください。
> 本書とコードに齟齬がある場合は、本書の意図を確認し、必要なら本書を更新してから実装を変えます。

## 0. ゴールデンルール（最優先・例外なし）

1. **着手前に `PROJECT.md` と対象モジュールの責務を読む。** 推測で書き始めない。
2. **クラウド呼び出しは2箇所だけ。** Gemini を呼んでよいのは `mws/embedding/`（埋め込み）と `mws/agents/`（LLM）のみ。他モジュールから Gemini へネットワーク呼び出しを書かない。
3. **埋め込みは `gemini-embedding-2` 単一。** 文書もクエリも同じモデルで埋め込む（生徒モデルは廃止）。クラウド往復のレイテンシ/コストは content-hash キャッシュ・単発マルチ Content バッチ・Batch API（オフライン索引化）で抑える。mock モードは決定的スタンドイン。
4. **すべての乱数に seed を通す。** seed を取らない確率的処理を新規に書かない。
5. **シークレットをコミットしない。** API キーは環境変数のみ。コード・設定・ログ・テストに鍵やトークンを書かない。
6. **依存方向を破らない。**（[2.2](#22-依存方向ルール)）下位層は上位層を import しない。
7. **テストはデフォルトでクラウドに触れない。** ライブ Gemini 呼び出しはオプトインのマーカー付きテストのみ。
8. **実験結果を上書きしない。** `runs/` の成果物は追記のみ。再現に必要な manifest を必ず残す。
9. **依存パッケージを勝手に増やさない。** 追加が必要なら理由を明記し、`pyproject.toml` と本書の前提に反しないか確認する。
10. **Non-Goals を尊重する。**（`PROJECT.md` §2.3）実機・本番スケール・実 ERP 接続・新規モデル学習には踏み込まない。

## 1. 開発環境セットアップ

### 1.1 前提

- OS: macOS（Apple Silicon 想定）
- Python: 3.11 以上
- パッケージ／環境管理: **uv**（高速・ロック管理）

### 1.2 初期構築

```bash
# 仮想環境と依存の同期（pyproject.toml / uv.lock を正とする）
uv sync

# 開発用も含める場合
uv sync --extra dev

# 動作確認
uv run python -c "import mujoco, lancedb, duckdb; print('ok')"
```

### 1.3 シークレット（環境変数）

`.env`（gitignore 済み）に置き、コードからは設定層経由でのみ参照する。

```bash
# Gemini（LLM via ADK / Embedding 2）
GOOGLE_API_KEY=...           # ローカル開発用。実値はコミットしない
# MWS 動作モード
MWS_CLOUD_MODE=mock          # mock | live （既定は mock。live は明示的にのみ）
MWS_RUN_DIR=./runs           # 実験成果物の出力先
```

- `MWS_CLOUD_MODE=mock` が既定。**ライブのクラウド利用は明示的に `live` を設定した時だけ。**
- 鍵が未設定でも `mock` で全パイプラインが動くこと（[5.4](#54-オフラインmock-モード)）。

### 1.4 MuJoCo / Apple Silicon の注意

- `mujoco`（CPU）は arm64 で問題なく動く。並列環境は基本 CPU で確保する。
- **MJX（JAX/XLA 版）の GPU 並列は Apple Silicon では限定的。** 既定では MJX に依存せず、CPU MuJoCo で複数インスタンスを並列／時分割する。MJX を使う場合は seed・決定性・性能を別途検証してから導入する。
- オフスクリーン描画（RGB-D 生成）は環境依存で詰まりやすい。描画系の変更時はヘッドレスでの再現を確認する。

## 2. リポジトリ構造と依存方向

### 2.1 ディレクトリと責務

`PROJECT.md` §7 のコンポーネントに対応。各ディレクトリは単一責務を守る。

```
mws/
├── core/          # 記憶アトムのスキーマ・封筒・来歴・アクセスポリシー（最下層・他に依存しない）
├── worldmodel/    # 4Dシーングラフ（実体ノード・関係・時間）
├── storage/       # ポリグロット永続化アダプタ（vector/graph/timeseries/spatial/blob）
├── embedding/     # Gemini Embedding 2（単一モデル）・content-hash キャッシュ・非同期インデクサ
├── retrieval/     # 多重インデックス検索・クエリプランナ・融合リランカ・消費者適応投影
├── consolidation/ # episodic→semantic 蒸留・重複排除・TTL剪定
├── federation/    # エッジ↔クラウド・QoRルーティング・予測プリフェッチ
├── reactive/      # standing query(pub-sub)・好奇心ループ
├── agents/        # Gemini ADK エージェント・A2A・MWS検索ツール(MCP互換)公開
├── vla/           # 検索拡張VLA・スキル実演アトムの想起/注入
├── sim/           # MuJoCo 世界・センサー・複数インスタンス・状態フォーク
├── business/      # 合成業務データ(ERP/WMS/CMMS/MES/SOP/SDS) 生成・スタブ
├── scenarios/     # 検証シナリオ実装
├── eval/          # 指標・関連性ラベル自動生成・レイテンシ分解・レポート
├── configs/       # 世界/実験/モデルの設定（コードでなく設定）
└── cli.py         # 統一エントリポイント
tests/             # ユニット/統合テスト（mws/ と対称）
runs/              # 実験成果物（gitignore・追記のみ）
data/              # 合成業務データ等のローカル生成物（gitignore）
```

### 2.2 依存方向ルール

下から上へのみ依存可。上位を import しない。

```
core  ←  worldmodel  ←  storage  ←  embedding  ←  retrieval
                                                      ↑
            consolidation ─────────────────────────────┤
            federation / reactive ──────────────────────┤
   （消費者: agents / vla / scenarios）─────────────────┘
   sim / business → core へアトムを供給（外部世界の入力源）
   eval は全モジュールを read してよい（出力専用・他から依存されない）
```

- `core` は他の MWS モジュールに依存しない。
- 循環 import を作らない。共有型は `core` に置く。
- 外部I/O（DB・ファイル・ネットワーク）は各アダプタ層に閉じ込め、純粋ロジックから分離する。

### 2.3 クラウド境界（最重要のガードレール）

- Gemini への呼び出しは `embedding/`（教師）と `agents/`（LLM）に**のみ**実装する。
- それ以外のモジュールがクラウドを必要とする設計になったら、それは設計ミスのサイン。`PROJECT.md` の意図に立ち返る。

## 3. 実行方法

統一 CLI（`mws/cli.py`）からサブコマンドで実行する。設定は `configs/` を指定し、上書きはフラグで行う。

```bash
# シミュレーション世界を起動して観測アトムを生成
uv run python -m mws.cli sim run --config configs/worlds/warehouse.yaml --seed 0

# 索引化（オフライン・教師埋め込み・Batch）
uv run python -m mws.cli index build --config configs/index/default.yaml

# 検証シナリオを実行（例: シナリオ1 保全引き継ぎ）
uv run python -m mws.cli scenario run --name maintenance_handoff --seed 0

# 評価（指標算出・レポート生成）
uv run python -m mws.cli eval run --run-id <RUN_ID>

# ADK エージェントをローカル起動
uv run python -m mws.cli agent serve --config configs/agents/ops_agent.yaml
```

- ハードコードした絶対パス・鍵・モデル名を CLI 引数や設定外に書かない。
- 長時間処理（索引化・実験）は中断・再開可能に設計する。

## 4. 設定管理

- 設定は `configs/` 配下の YAML を正とし、コード側は型付き設定（pydantic-settings 等）で読み込む。
- **設定とコードを混ぜない。** マジックナンバー・しきい値・モデル名・次元数は設定に出す。
- 設定は階層化する: `worlds/`・`index/`・`embedding/`・`agents/`・`experiments/`・`scenarios/`。
- すべての実行は `seed` を設定で受け取り、manifest に記録する（[9章](#9-再現性と実験規律)）。

## 5. クラウド利用ポリシー（Gemini LLM / Embedding 2）

> 外部 API（ADK・Embedding 2）の正確な引数・モデル ID は変化しうる。実装時に**現行の公式ドキュメントを確認**し、本書の前提（mock 既定・キャッシュ必須・ホットパス禁止）は維持する。

### 5.1 共通

- 呼び出しは必ずアダプタ経由（直接 SDK を散らさない）。リトライ・タイムアウト・レート制御をアダプタに集約。
- 全クラウド呼び出しを**回数・トークン・コスト・レイテンシ**で計測しログに残す（[10章](#10-ロギングと可観測性)）。
- クラウドは非決定的。**再現性が必要な比較では応答をキャッシュ／記録**し、seed と合わせて固定する。

### 5.2 LLM（ADK 経由 Gemini）

- エージェント実行系（ADK）はローカル、推論のみクラウド。ローカルセッション／メモリで開発する。
- MWS の検索は ADK の**ツール（MCP 互換）**として公開し、エージェントはツール経由で想起する。
- マルチエージェント連携は A2A を用いる。

### 5.3 Embedding 2（オフライン索引化のみ）

- 索引化は **Batch API で非同期・低コスト**に行う（ホットパスに置かない）。
- MRL を使い**次元は設定で指定**（既定の出発点は 768、必要に応じ 1536/3072）。次元はインデックスの属性として記録する。
- 二段検索（小次元で粗選別→全次元で再ランク）を採用する場合、両次元を同一モデル空間内で扱う。

### 5.4 オフライン/mock モード

- `MWS_CLOUD_MODE=mock` で、クラウドを決定的なスタブに差し替えて全パイプラインが動くこと。
- ユニット／統合テスト・CI・素早い反復は mock で行う。`live` は明示的な実験時のみ。

### 5.5 コスト規律

- 索引化・実験はトークン量を見積り、Batch を優先。大量再索引は事前に規模とコストをログ／manifest に残す。

## 6. 埋め込み運用ルール

- **埋め込みは `gemini-embedding-2` 単一に統一。** 文書/クエリは非対称タスク指示の接頭辞で埋め込む（生徒モデル・教師/生徒二層は廃止）。往復削減はキャッシュ・バッチ・Batch API で行う。mock モードは決定的スタンドイン。
- **埋め込み空間は混ぜない。** 異なるモデル／次元のベクトルを同一インデックスに入れない・距離比較しない。各ベクトルに `embedding_space`（モデル＋次元＋バージョン）を付与する。
- **モデル更新＝再索引。** 埋め込みモデルを変えたら座標空間が変わり再索引が必要。バージョンを上げ、旧空間と区別する（H に関わる実験対象として明示）。
- **content-hash キャッシュ必須。** 同一内容を二重に埋め込まない。キャッシュキーは内容＋モデル＋次元。
- 視覚アトムのマルチモーダル埋め込みは Gemini 依存（クラウド遅延が残る）。これは既知の制約であり隠さず計測する。

## 7. コーディング標準

- **フォーマット／リント**: `ruff format` と `ruff check`。コミット前に通す。
- **型**: 公開関数・データ構造に型注釈を付け、型チェック（mypy/pyright）を通す。
- **データ構造**: 記憶アトム等のスキーマは pydantic/dataclass で明示。辞書の生渡しを避ける。
- **命名**: モジュール／関数は `snake_case`、クラスは `PascalCase`、定数は `UPPER_SNAKE`。MWS 用語（atom, scene_graph, projection 等）は `PROJECT.md` の用語に揃える。
- **副作用の分離**: I/O・ネットワーク・乱数は端に寄せ、純粋ロジックをテスト可能に保つ。
- **ログ**: `print` でなく構造化ロガーを使う。
- **エラー処理**: 握りつぶさない。クラウド失敗・索引欠落・空ヒットは明示的に扱う。
- **ドキュメント**: 公開 API に docstring。非自明な設計判断は理由をコメントに残す。
- **マジックナンバー禁止**: しきい値・次元・TTL は設定へ。

## 8. テスト方針

- フレームワーク: `pytest`。`tests/` は `mws/` と対称に置く。
- **既定はクラウド非接触。** ライブ Gemini はマーカー（例 `@pytest.mark.live`）付きでオプトイン。CI とデフォルト実行では走らせない。
- **決定性**: seed を固定し、mock クラウドで決定的に。フレーキーなテストを残さない。
- **検索のゴールデンテスト**: sim 真値から関連性ラベルを生成し、Recall@k 等が基準を満たすことを回帰テストする。
- **層別**: 純粋ロジックはユニット、アダプタ結合は統合（ローカルストアに対して）。
- 速いこと。重い sim・索引はフィクスチャで小規模化する。

```bash
uv run pytest                 # 既定（mock・決定的。live と elasticsearch は除外）
uv run pytest -m live         # ライブ・クラウド（明示時のみ）
uv run pytest -m elasticsearch  # ES バックエンド統合（`make es-up`＋`uv sync --extra es`。既定除外）
```

## 9. 再現性と実験規律

- **すべての実行に seed。** 乱数源（Python/NumPy/シミュレータ）を一括初期化する。
- **Run manifest 必須。** 各実行は `runs/<RUN_ID>/manifest.json` に、使用設定・git SHA・依存バージョン・モデル ID・埋め込み空間・seed・クラウドモードを記録する。
- **指標は事前登録。** 比較に使う指標は実行前に宣言し、後付けのチェリーピッキングを避ける（`PROJECT.md` §10）。
- **結果は追記のみ。** `runs/` を上書き／削除しない。
- **統計**: 複数 seed×複数 world で実行し、信頼区間付きで報告する。
- 成果物（メトリクス・図・ログ）は `runs/<RUN_ID>/` 配下にまとめる。

## 10. ロギングと可観測性

- 構造化ログ（JSON 行）を基本とし、`RUN_ID` を全ログに付与する。
- **レイテンシ分解**を計測できるようにする: ローカル ANN / Gemini 埋め込み呼 / Gemini 推論 を区別（p50/p95）。
- **クラウド呼び出しカウンタ**: 回数・トークン・推定コストを集計し manifest に残す。
- 仮想エッジ↔クラウド帯域（送られたはずのバイト数）を計測する仕組みを retrieval/federation に持たせる。

---

## 11. リソース制約（単一 MacBook）

- メモリ予算を意識する。大規模配列・点群はストリーム処理し、一括ロードで OOM させない。
- MuJoCo 並列インスタンス数は CPU/メモリに合わせて設定で絞る。スケール実験は段階的に。
- 索引化はバックグラウンドの非同期インデクサで行い、対話・制御ループをブロックしない。
- 重い処理（索引・consolidation）はバッチ／オフピークで。

- ブランチ: `feature/<topic>` / `fix/<topic>` / `exp/<topic>`。
- コミットは小さく論理単位で。命令形・簡潔なメッセージ（例: `add cross-modal reranker`）。

- PR/変更は単一目的に絞る。設計に触れる変更は `PROJECT.md` 側の意図と矛盾しないか確認する。

## 13. Claude Code の作業フロー

1. **読む**: `PROJECT.md` と対象モジュール、関連する既存コード／設定を確認する。
2. **計画する**: 変更範囲・影響モジュール・依存方向・クラウド境界への影響を明確化。曖昧なら**実装前に質問する**。
3. **小さく作る**: 最小の差分で。1タスク1目的。
4. **守る**: 依存方向（§2.2）、クラウド境界（§2.3）、seed、mock 既定、埋め込み空間の一貫性。
5. **検証する**: `ruff` → 型チェック → `pytest`（mock）を通す。検索系を変えたらゴールデンテストを更新／確認。
6. **記録する**: 実験を伴うなら manifest を残す。設計判断はコメント／本書に反映。
7. **増やさない**: 依存追加・新規クラウド接点・新ディレクトリは理由を述べてから。Non-Goals に踏み込まない。

## 14. よくある落とし穴

- **埋め込み空間の取り違え**: 違うモデル／次元のベクトルを同一インデックスで比較してしまう → `embedding_space` を必ず確認。
- **ホットパスにクラウド埋め込み**: クエリ時に Gemini を呼んでレイテンシ増 → content-hash キャッシュ＋単発マルチ Content バッチで往復を抑える（同一内容は再埋め込みしない）。
- **seed 取り忘れ**: 結果が再現しない → 乱数は一括初期化、manifest に seed。
- **クラウド非決定性を比較に混入**: 応答を固定／記録せず A/B 比較 → キャッシュ・記録して固定。
- **MuJoCo 描画の環境依存**: オフスクリーン RGB-D が落ちる → ヘッドレス再現を確認、MJX/Metal は安易に使わない。
- **Gemini レート制限**: 大量同期呼び出しで詰まる → Batch・非同期・リトライをアダプタに集約。
- **依存方向の崩壊**: `core` から上位を import して循環 → 共有型は `core` に集約。

- [ ] 設計判断とトレードオフが説明されている（コード／コミット／本書）
- [ ] `PROJECT.md` の意図と矛盾しない（必要なら本書を更新）
