# HITL.md — 人の決定を待つ事項の管理簿

- 日付: 2026-10-04（初版）
- 最終更新: 2026-11-08（M10 で H-27 の (3)(4) を実施。H-02 / H-03 を決定。ADR-0033。H-26 を追加。H-04 を ADR-0022 で、H-22 を案 A で決定。H-25 を追加済み。H-01 / H-17 は未対応のまま）
- 前回: 2026-10-17（棚卸し。H-22 / H-23 を追加）
- 対象: SBP の開発・運用で**人が決めなければ進まない／固まらない**事項
- 位置づけ: **判断の待ち行列**。タスクの状態は `docs/TASK.md`、里程の状態は `docs/STATUS.md`、
  判明した事実は `docs/PROGRESS.md`、決定の記録は `docs/adr/`。本書は**まだ決まっていないこと**だけを持つ。
  決まったら ADR を起票し、本書の項目を「決定済み」に移してから次の棚卸しで消す。

## 本書に載せる基準

| 載せる | 載せない |
|---|---|
| 業務仕様・運用方針の選択（基盤側に根拠が無い） | 実装の詳細（コードを読めば決まる） |
| 外部との契約（認証方式、プロバイダ選定、法令対応） | テストで検証できる技術的判断 |
| 不可逆・外部に影響する操作（鍵のローテーション、実データの取り扱い） | ADR で既に決まったこと |
| オントロジーの MAJOR / MINOR を伴う語彙の決定 | リファクタリング |

**推測で埋めない**（CLAUDE.md）。基盤側が勝手に決めると、後から「なぜこうなっているか誰も説明
できない設定」になる（`docs/PROGRESS.md` 所見 88）。

## 状態の凡例

- `待ち` — 判断を待っている
- `暫定` — 既定値で進めているが、決定で変わりうる（コードに既定があり、動いてはいる）
- `期限到来` — 「この時点で再評価する」と決めた時点を過ぎている
- `決定済み` — ADR 起票済み。次の棚卸しで本書から消す

## 1. 優先度 高 — 決めないと先に進めない、または放置に危険がある

### H-01 開発機の `.envrc` に実鍵が平文で置かれている `決定済み・実行待ち`

**2026-11-08 決定: 案 A（3 本ローテーション、鍵は `.env` のみ）。ADR-0028、手順は ローテーション手順書（非公開。ローカルのみ）。ローテーションはプロバイダ側の操作で人が行う。完了したら本項を消す。**

**事実。** `.envrc`（direnv）に LLM プロバイダ 3 社の API キーが平文で入っている。`.gitignore`
の 6 行目で除外されており、`git ls-files` にも出ない（**コミットされたことは無い**）。ただし
**2026-10-04 のセッションでファイルを `cat` したため、値がセッションの文脈を通過した。**

**なぜ人の判断か。** 鍵の無効化・再発行はプロバイダ側のアカウント操作で、基盤側からは実行できない。
また「通過しただけで漏洩とみなすか」は運用方針の問題である。

**選択肢。**

| 案 | 内容 | 利点 / 欠点 |
|---|---|---|
| A（推奨） | 3 本すべてローテーション | 最も安全。コストは発行し直す手間だけ |
| B | 使用実績のあるものだけローテーション | 手間が減る / どれが使われたか追跡が要る |
| C | 何もしない | **非推奨。** リスクを受容したことを明記する必要がある |

**付随して決めること。** 鍵の置き場所を `.envrc`（direnv、シェルに展開される）から `.env`
（`SBP_` プレフィクスで `Settings` が読む）へ移すか。不変条件 12 は「シークレットは `.env` のみ」
と定めており、**`.envrc` に鍵を置くのは規約から外れている**。`.claude/settings.json` の deny に
`.envrc` を追加済みなので今後セッションからは読めない。

**決定後にやること。** ADR 起票（鍵の置き場所の方針）。`.env.example` に鍵の項目があることを確認。
`docs/runbooks/` にローテーション手順を追加。

**2026-10-17 時点。** 未対応。`.envrc` の更新日時は 2026-10-03 のままで、「期限到来」と記録してから
13 日が経っている。本日のセッションは deny 設定により `.envrc` の中身を読んでいない（ディレクトリ一覧で
存在と更新日時だけを確認した）。H-23（リモートへの push）の前に決める必要がある。

**2026-10-25 時点。** 未対応（`.envrc` の更新日時は 2026-10-03 のまま。「期限到来」から 21 日）。本日も
中身は読んでいない。**付随の判断に影響する事実が 1 つ見つかった**: 入れ子の設定（`SBP_BRIDGE_*` /
`SBP_REASONING_*` / `SBP_WM_*` / `SBP_ACTIONS_*`）は `.env` を読まず、環境変数からしか効かない
（`docs/PROGRESS.md` 所見 108、`docs/TASK.md` X-11）。開発機で `.envrc` が設定の置き場として機能していたのは
direnv が環境変数として export するためと考えられ、**鍵と設定を `.env` に移すなら X-11 を先に直す**必要がある。

### H-02 UI の認証方式 `決定済み`（2026-11-08。(c) localhost 限定のまま運用に出さない。ADR-0033）

**2026-11-08 決定**: UI を外部公開する予定は無い。公開する前に認証方式（OIDC + PKCE を第一候補）を ADR で決める。それまで `SBP_ENV=dev` 以外は全拒否のまま。H-25 の偽装（開発用ヘッダ）はこの前提の下でだけ許容する。次の棚卸しで本項を消す。

以下は決定前の記述。

**何が止まっているか。** `apps/ui` は開発用に固定の要求者（`X-SBP-Principal` ヘッダ）を送っている。
ABAC（M7-06）は要求者を受け取る形まで実装済みで、既定は拒否。**本番の認証方式が決まるまで UI を
公開できない。**

**なぜ人の判断か。** 組織の ID 基盤（OIDC プロバイダ、既存の社内認証、拠点ごとの運用）に依存し、
基盤側に根拠が無い。

**選択肢。** (a) OIDC / OAuth2 の Authorization Code + PKCE（新サービスは増えない。IdP は外部）、
(b) リバースプロキシで認証し基盤はヘッダを信頼（Compose にプロキシが 1 つ増える → ADR 必須）、
(c) 開発中は決めず、UI を localhost 限定のまま運用に出さない。

**関連。** ADR-0008 の未決。`sbp.api.factory.dev_principal_resolver` は `SBP_ENV=dev` 以外では
解決器を渡さない（＝全拒否）ので、**誤って公開しても漏れない**作りになっている。

### H-22 ゲート G8 の統合テストで、ワーカーの入力をテストが直接置いてよいか `決定済み`（2026-11-08。案 A）

**事実。** G8 の条件は「4 ワーカー（bridge / belief / reconcile / scheduler）を実物のサービス上で回し、
各 `step()` が非ゼロを返す」。2026-10-17 の棚卸しで、**各データパスの先頭を production で書くコードが
無い**ことが分かった（`docs/PROGRESS.md` 所見 101〜103）——潜在索引への書き込み、プローブ束の投入、
資産台帳の同期、コネクタ → 写像 → `integration.business`、計画の取込、期待の検証。いずれもテストが
置いている。**入力をテストが置いてよいなら、G8 はいまの実装のまま M8-11 だけで書ける。**

**なぜ人の判断か。** 「何をもって M8 完了とするか」は計画のスコープであり、`docs/TASK.md` §2 は
スコープ変更を ADR 必須にしている。ゲートの字面と目的（運用で動く）のどちらに合わせるかは、基盤側の
都合では決められない。

**選択肢。**

| 案 | 内容 | 利点 / 欠点 |
|---|---|---|
| A（推奨） | **外界だけをテストが模擬し、基盤の内側の段は運用コードで通す。** 外界 = 物理の観測窓（`SynthWorld`）、業務システム（SQLite のモック）、人の操作（API コマンド）。潜在化・プローブ束の投入・取込・資産台帳の同期は production のコードが行う | G8 が「運用で動く」を意味する。不変条件 10 とも整合する（`services` / `scripts` は `sbp.testing` を import できないので、外界の模擬はテストのプロセスに残る）/ M8-23・M8-24・M8-25 が M8-11 の前提になり、M8 が長くなる。M8-24 は ADR で「エッジ（本リポジトリ外）」と決めれば、潜在の入口の契約だけで足りる |
| B | 現行の字面どおり、入力をテストが直接置いてよい | M8-11 にすぐ着手できる / **G5 の「完走させたのはテストコード」（所見 89）を繰り返す**。新タスクは M8 に残るが G8 の前提にならない |
| C | B で G8 を通し、M8-23〜M8-29 を M9 として切り出す | 里程の区切りが早い / タスクの移動はスコープ変更なので ADR が要る。M9 のゲートを別に定義する必要がある |

**決定後にやること。** ADR 起票（ゲートの定義）。`docs/TASK.md` の G8 の定義と M8-11 の行を更新する。
C なら M9 の節を起こす。

**2026-10-25 時点。** 判断材料が 1 つ増えた。案 A の前提のうち**記録パス（M8-25）は運用に乗った**——
ingest-worker が業務システム（開発ではファイルの SQLite のモック）を読み、台帳・業務記録・計画を production の
コードで書く。統合テスト `test_ingest_worker_e2e.py` は案 A の形（外界だけをテストが置く）で書いた。案 A で
残る前提は推定パスの先頭（M8-24 の ADR と、M8-23 のプローブ束の投入）である。

**2026-11-08 の決定**: 案 A（外界だけを模擬し、基盤の内側は運用コードで通す）。M8-24（推定パスの先頭）と M8-23（プローブ束の
投入）を M8-11 の前提にした。G8 の定義は M8-11 の ADR に書く。

### H-03 `/stream/{topic}` の去就 `決定済み`（2026-11-08。(a) 消した。ADR-0033）

**2026-11-08 決定**: 外部クライアントが購読する予定は無いので、エンドポイントと `stream_reader` を消した。必要になったら方式と認可を決めて再起票する。次の棚卸しで本項を消す。

以下は決定前の記述。

**事実。** M8-18 / M8-19 で UI の 4 ビューすべてが GraphQL の資源を読むようになり、
**ストリームの購読者が 1 人も居なくなった**（契約テスト `test_the_ui_reads_no_stream_at_all` で固定）。
API 側のエンドポイントは残っているが、`build_app` は `stream_reader=None` を渡すので 503 を返す。

**なぜ人の判断か。** 「残すが使わない」のか「消す」のかは、基盤を外部から使う計画に依存する
（UI 以外のクライアントが購読する想定があるか）。

**選択肢。** (a) 消す（未使用のエンドポイントは「動くはず」と読まれる）、(b) 残して購読方式
（SSE / WebSocket）を決める、(c) 残して「未配線」を応答本文に明記する（現状）。

**関連。** ADR-0008 の未決（購読の UI への反映）。

### H-04 LLM の live 経路で使うプロバイダ `決定済み`（2026-11-08。ADR-0022: anthropic のみ・HTTP 直）

**何が止まっているか。** M8-10（LLM の live 経路）は「任意依存として SDK を 1 つ追加する」タスクだが、
**どれを追加するかが決まっていない**。`routing.yaml` は task 別のルーティングを持ち、モデル ID は
`.env` にしか書かない設計なので、コード側で決まるのは「どの SDK を任意依存に入れるか」だけである。

**なぜ人の判断か。** 契約・コスト・データの所在（どのプロバイダに文書を送るか）は運用方針である。

**選択肢。** (a) `anthropic` のみ（`SBP_LLM_DEFAULT` の既定）、(b) 3 社すべて、(c) live を作らず
replay のまま（概念提案と文書抽出は人が代わりに書く）。

**注意。** fixture が無いときに黙って live へ落ちない挙動（M6-02）は**維持する**。H-01 と連動する
（live を使うなら鍵が要る）。

**2026-11-08 の決定**: (a) anthropic のみ。SDK は足さず `httpx` で Messages API を呼ぶ（ADR-0022）。openai / gemini の
live は未実装。H-01（鍵のローテーション）は未対応のまま——live を使うなら鍵が要る。

### H-05 法令上の消去要求への対応 `待ち`

**2026-11-08**: 方針案を ADR-0034（状態: 提案）に書いた。主体を仮名の IRI で持ち、消去は対応表の行を消すことで満たす（文は消さない）。**法務の確認待ち**——仮名化で消去要求を満たすと見なせるか、再識別の扱い、保存期間。人の主体 IRI の置き場（イベントログ・グラフの来歴・`learning_decisions`）をコードで確かめた結果は ADR にある。

**何が止まっているか。** 不変条件 2（追記専用）と「個人データの消去要求」の両立。`sbp.knowledge` の
ルールは「別途 ADR」としている。**運用開始前までに決める必要がある。**

**なぜ人の判断か。** 法務の判断であり、基盤の設計だけでは決まらない。

**論点。** (a) そもそも個人データを持たない設計にできるか（不変条件 9 で生映像は持たず、`Person` の
個人識別はプローブで型レベルに禁止している。残るのは `decided_by` / `resolved_by` の主体 IRI）、
(b) 消去が必要なら「文を消す」のか「主体を仮名に置き換える」のか、(c) as-of の再構成が壊れる範囲。

**基盤側の現状。** 人を指す IRI が入るのは作業項目表（`learning_decisions.decided_by`、
`discrepancies` の `assignee_role`）とアサーションの来歴である。**ロールで持っている箇所は
個人を指さない**（ADR-0008 の設計）。

## 2. 優先度 中 — 決めなくても進むが、決めると設計が固まる

### H-06 アクションのレート制限を永続化するか `暫定`

いまは `RateLimitState` がワーカーのプロセス内にあり、**再起動で消える**。冪等の鍵
（`decision_id` 由来、所見 93）は「同じ判断の二度適用」を防ぐが、「別の判断で短時間に 2 回」は
再起動後に通る。設計書 §9.3 は「同一対象への短時間の反復を制限する」と定めている。

**選択肢。** (a) `expectations` の `created_at` を数える（新しい表を作らない）、(b) 専用の表、
(c) 現状維持（再起動が稀なら実害が小さい、と判断する）。**関連**: ADR-0014 の未決 1。

### H-07 `ActionEvent` を永続化するか `暫定`

実行の記録がイベントログにも表にも無く、`Expectation.action_event` が ID を持つだけである。
永続化するなら「**実行は主張か**」に答える必要がある——実行したことは観測可能な事実と読めば
`observed` の席があるが、`EventEnvelope` は主張を運ぶもので、実行の記録はそれに当たるか。
**関連**: ADR-0014 の未決 2。

### H-08 補償（compensation）の入口 `待ち`

補償アクションは契約で必須（未定義の ActionType は登録拒否）だが、**実行する入口が無い**。
自動で走らせるのは危険（補償自体が業務システムを変える）なので作っていない。
**選択肢**: (a) 実行と同じく判断キュー経由（人が承認する）、(b) 期待の違反から提案を出し人が承認、
(c) 当面作らない。**関連**: ADR-0014 の未決 3。

**2026-11-08 の注記**: UI のアクション承認（M8-22、ADR-0021）は補償を実行する入口を作らない。契約の要約に補償先を
表示するだけ。入口を作るかは本項の判断待ち。

### H-09 採択した概念提案の「起票されたか」を追跡するか `暫定`

`ACCEPTED` になった提案が実際に `ontology/` に入ったかを基盤は知らない（MINOR 起票は人の手作業。
M6-04 の決定）。追跡するなら「採択したが未実装」という状態が要る。
**関連**: ADR-0015 の未決 1。

### H-10 却下した提案の再提案を抑えるか `暫定`（M8-09 で暫定の決定。ADR-0019）

`curation_note` に理由が残るが、次の発見サイクルが同じクラスタから同じ提案を出すのを止める
仕掛けが無い。M8-09（発見ループの周期実行）を入れると実際に繰り返しが起こる。
**関連**: ADR-0015 の未決 2。

**2026-11-07 の暫定決定**（ADR-0019）: signal の指紋（trigger・実体の集合・類型）で LLM を呼ぶ前に抑える。
`proposed` / `accepted` / `revised` は常に、`rejected` は冷却 30 日（`SBP_REASONING_DISCOVERY_REJECTION_COOLDOWN_DAYS`）
の間。冷却後に同じ signal が出れば再提案する。**変えたければ冷却日数か指紋の定義を変える。**

### H-11 接地する実体型の既定 `暫定`

`SBP_BRIDGE_GROUND_TYPES` の既定は `vocab.core.Asset`。搬送具（carrier）・治具・作業者を含めるかは
ドメインの判断である。**関連**: ADR-0009 の未決。

### H-12 拠点を述語で絞るか（オントロジー MINOR） `暫定`

いまは IRI の規約（`.../site/<site>/...`）で拠点を絞っている。**規約は弱い根拠**で、`sbp:atSite`
述語を置いて `?entity sbp:atSite <site>` で絞るほうが正しい。ただしオントロジーの MINOR 変更に
なるので、変更手順（CLAUDE.md）を先に回す必要がある。件数をログに出して 0 件に気付ける形にしてある。
**関連**: ADR-0009 の未決。

### H-13 観測要求が「満たされた」ことの判定 `待ち`

`observed` のイベントが戻ってきたとき、どの要求を満たしたかを突き合わせる処理が未実装
（`mark_satisfied` の API はあるが呼ぶ側が無い）。実体 × フルーエント × 区間の重なりで判定するのが
素直だが、「**どれだけ測れば満たされたか**」は観測手段によって違う。
**関連**: ADR-0011 の未決。

**2026-11-07 の注記**: 人の回答（M8-29、ADR-0018）に限り、回答が要求の鍵 `(discrepancy_id, fluent)` を名指す
ので「鍵の一致」で満たすと決めた。センサ観測が戻ったときの充足は、この問いのまま残る。

### H-14 1 フルーエントに複数の観測手段を許すか `暫定`

いまは 1 フルーエント 1 手段（`observation/*.yaml`）。複数から選ぶ（安い順に試す等）には
スケジューラの選択に手段次元を足すことになり、別の設計が必要。**関連**: ADR-0011 の未決。

### H-15 拠点 → 中央の転送役 `待ち`

不一致イベントは既定で拠点トピックに出る（ADR-0010）。中央で横断的に見るには転送役が要るが、
未実装。**多拠点運用をいつ始めるか**に依存する。

### H-25 コマンド API の認証と、回答者の同一性 `一部決定済み`

**2026-11-08**: 「誰が」の置き場所を本文の自称から認証の層（`principal_resolver`）へ移した（ADR-0029。本文と要求者の食い違いは 403、解決できなければ 401）。**ただし resolver は開発用ヘッダだけで、偽装は本番の認証方式が決まるまで防げない。** 以下の本文は移す前の事実で、**残り**: コマンドの認可、`decision_id` が主体を含まない件（誰が何を判断してよいか）と回答者ごとの確信度（ADR-0018）、本番の認証方式（H-02）。

`/commands/*`（`resolve_discrepancy` / `curate_concept` / `execute_action` / `answer_observation` / `review_quarantine`）は
`principal_resolver` も ABAC も通らず、`resolved_by` / `decided_by` / `approved_by` / `answered_by` は
**呼び出し側が自由に名乗る**。M8-29 の独立レビューが指摘した（2026-11-07）。人の回答は
`observed` の主張として確信度 0.98 で信念に入り、`answered_by` は監査隔離の単位でもあるので、
他のコマンドより影響が大きい（他人の名で「稼働している」を注入できる）。H-02（UI の認証方式）が
決まるまでは、開発・検証環境以外に公開しない前提である。

**2026-11-08 の追記**（M8-22 のレビュー）: UI のアクション承認ボタンから `execute_action` に到達できるようになり、
`approved_by`（承認の来歴）が自称であることの影響が大きくなった。`decisions` の読み出しも要求者の存在しか見ない
（拠点の分離は保たれる）。コマンドと判断の認証・認可を併せて決める。

**2026-11-08 の追記（コードで確かめた）**: `decision_id` はクライアントが付ける冪等の鍵で、表の主キーが `decision_id` 単独（`ON CONFLICT (decision_id) DO NOTHING`）。そのため (1) 別の主体が同じ `decision_id` を先に送ると、後から来た本物の判断が黙って捨てられる、(2) ハンドラは積む結果を待たずに `accepted: true` を返すので、捨てられたことが呼び出し側に伝わらない。localhost 限定（ADR-0033）の間は許容するが、公開前に鍵を主体で名前空間にするか、積む結果を待って 409 を返す。

**決めること。** コマンドを認証済みの主体に結びつける方式（リクエストの主体から `answered_by` 等を導き、
本文の自称を受けない、が素直）と、回答者ごとの権限・確信度（ADR-0018 の未決）。**関連**: H-02、ADR-0012、ADR-0014、ADR-0018。

### H-27 M9・M10 に入れなかった運用の穴 `待ち`

**事実。** ADR-0030 が M9 に入れなかったもののうち、(3) SHACL 隔離の運用経路と (4) What-if の入口は **M10 で入れた**（ADR-0035・0036。2026-11-08）。残り:
(1) **同一性束縛の運用**（`identity_bind_rate` / `identity_revoke_rate`）— Track の入力となる知覚の契約が本リポジトリに無く、現場のエッジの出力に依る、
(2) **LLM を使う機能の入口**（概念提案・文書抽出・NL→クエリ・説明の文章化）— 運用コードは `sbp.llm` を import しない。

**M10 の限界（次の判断材料）。**
- 隔離は「写像に失敗した行・型がオントロジーに無い台帳の行」を積む。**SHACL の形状（`AssetShape` ほか）を運用の入力に当てていない**——`AssetShape` は `locatedIn` を必須にするが
  台帳に場所の列が無く、当てると全件が違反になる（ADR-0035 の未決: 台帳に場所の列を持つか、形状を緩めるか。オントロジーの判断で、空間束縛の運用経路と合わせて決める）。
- What-if は**介入付きで学習した WM にだけ**答える（運用の WM は、現場のエッジがスプールに `actions` を置くまで拒否する）。計画差分の What-if は条件付けが学習されていないため、
  反実仮想は `ActionEvent` が永続化されていない（H-07）ため、入口が無い。`promote_scenario` の入口も無い（採用はコマンドの設計が別に要る）。

**なぜ人の判断か。** (1) は知覚側の契約（別リポジトリ）、(2) は費用・来歴の方針と優先順。

**選択肢。** それぞれ「M11 に切り出す／当面扱わない」。(1) は知覚の契約が決まるまで扱わないのが妥当。

## 5. 運用手順

**棚卸しの周期**: ゲート通過時、および `docs/TASK.md` §7 を触るとき。

**1 件を決めるときの流れ**（`docs/PROMPT.md` の P-25 に対応）:

1. 本書の該当項目を読み、選択肢と推奨が十分かを確認する（足りなければ小さなスパイクで判断材料を作る）。
2. 人が決める。
3. **ADR を起票する**（P-21 の形式）。影響するタスクを `docs/TASK.md` に反映する。
4. 本書の項目を §4 に移し、次の棚卸しで消す。

**本書に項目を足すとき**: 実装中に「業務仕様が分からない」「外部との契約が必要」と判明したら、
**推測で埋めずに**本書へ足す。コード側には `TODO(question)` を置き、ADR の「未決」にも書く
（3 箇所に同じことを書くのは冗長だが、**どの入口から来た人も気付ける**ことを優先する）。

**ADR の「未決」との関係**: ADR は決定の記録なので、未決の項目は**残したまま**にする（履歴として
読めるべき）。本書はそれを横断して「いま誰の判断を待っているか」に並べ替えたものである。だから
ADR の未決が解決済みでも ADR は書き換えず、本書の §4 に移すことで現在地を示す。
