# ADR-0012: 人の判断は作業キューで受け、5 番目のワーカーが適用する

- 日付: 2026-10-04
- 状態: 採択
- 触る層: knowledge（判断の作業キュー）、api（コマンドハンドラ）、services（learning-worker）、infra（alembic）

## 文脈

不一致の解決（`resolve_discrepancy`）と概念提案の採否（`curate_concept`）は**人の判断**で、
UI（M7-04）が `/commands/*` に POST する形まで作ってある。しかし

- `create_app` の `command_handler` は `None`（M8-13 で実配線したが、ハンドラは渡していない）、
- 判断を受けて書き戻し・プローブ再学習・概念採択を実行するコードが無い、
- そのため `apply_resolution`（M3-06）が出す `LearningArtifacts` は**どこにも適用されない**。

さらに M8 を通して同じ形の欠落が 4 回出た（`docs/PROGRESS.md` 所見 72）: プローブの置き場、
観測要求のキュー、指標、Situation の関係——いずれも読み出しと周期実行はあるのに
**「誰が最初の値を入れるか」が空いている**。その多くは人の判断が入口である。

関連: 設計書 §8.2（解決結果 → 学習信号の表）、§9.2（承認フロー）、§12.2（ワーカー構成）、
ADR-0008（UI）、ADR-0011（作業キューの先例）。

## 選択肢

### 問い 1: 人の判断をどこで受けるか

1. **作業キュー（投影表）に書き、ワーカーが適用する。**
   - 利点: 「人の判断を受け付けた」（速い・失わせてはいけない）と「適用する」（遅い・失敗
     しうる）を分離できる。書き戻しは業務システムへの外部呼び出しで、数秒〜数十秒かかり、
     相手の障害で失敗する。適用の再試行がキューの上で表現できる。
   - 欠点: 表が 1 つ増える。UI は「受け付けた」までしか見えない（適用の結果は後から読む）。
2. API のハンドラで同期的に適用する。
   - 利点: 表が増えない。UI が結果をその場で見られる。
   - 欠点: **人が書き戻しの完了を待つ**。失敗したら判断そのものが失われる（UI が再入力を
     求めることになり、同じ判断が二重に入りうる）。API プロセスが業務システムの資格情報を
     持つことになり、読み取り専用の層に副作用の権限が増える。
3. イベントログに載せる。
   - 欠点: ADR-0011 と同じ理由で載らない。「この不一致は物理が正しかった」は主張だが、
     「それを適用せよ」は指令であり、様相格子に席が無い。**解決そのものは `Discrepancy` の
     状態として記録される**ので、イベントに載せるべきは結果であって指令ではない。

### 問い 2: 適用を誰が実行するか

1. **5 番目のワーカー（`learning-worker`）を足す。**
   - 利点: 書き戻しの失敗・遅延が照合や信念更新に影響しない。1 ワーカー 1 プロセスの規約を保つ。
   - 欠点: CLAUDE.md が挙げるワーカーが 4 → 5 になる（文書の更新が必要）。プロセスが 1 つ増える。
   - MacBook 上のコスト: 既定では起動しない（`make dev --workers` で明示）。常駐しても
     キューを周期で引くだけで、ほぼアイドル。
2. 照合ワーカー（`reconcile-worker`）に相乗りする。
   - 利点: プロセスが増えない。
   - 欠点: **照合は窓を回すホットパス**で、書き戻しは外部システムへの同期呼び出しである。
     詰まった書き戻しが検出を止める。さらに駆動が 2 種類（Kafka の consumer と DB のキュー）
     混ざり、`step()` の意味が曖昧になる。
3. 周期ジョブ（cron 相当）にする。
   - 欠点: SIGTERM の graceful shutdown・疎通検査・冪等の仕組み（`services/runtime.py`）を
     再実装することになる。ワーカーの形に揃えたほうが運用が 1 つで済む。

### 問い 3: どこまで自動で適用するか

学習成果は 5 種類ある（`LearningArtifacts`）。**全部を自動適用しない。**

| 成果 | 本 ADR での扱い | 理由 |
|---|---|---|
| `observation_requests` | **自動で適用**（作業キューに積む） | 観測の要求を積むだけで、副作用は無い。選ぶのはスケジューラで、人への質問には頻度上限がある |
| `corrections`（書き戻し） | **既定 dry で実行**（`SBP_WRITEBACK_MODE`） | 業務システムを変えるので、`live` は運用者が明示する。補償は `WritebackCommand` の必須項目 |
| `reliability_updates` | 記録するだけ（適用しない） | 信頼性モデルは全照合の尤度に効く。1 件の解決で全体の重みを動かすのは、人が見てから |
| `bags`（負例） | 記録するだけ | プローブの再学習は昇格ゲート（AUROC ∧ ECE ∧ 整合残差）を通る別の仕事 |
| `concept_candidates` | 記録するだけ | オントロジーの MINOR 起票は人の手作業のまま（M6-04 の決定） |

## 決定

- **問い 1 は選択肢 1**（作業キュー）。`learning_decisions` 表（alembic 0005）。ADR-0011 の
  `observation_requests` と同じ形で、**行は消さず** `applied_at` / `failed_at` を立てる。
- **問い 2 は選択肢 1**（5 番目のワーカー）。`services/learning_worker.py`。CLAUDE.md と
  `docs/development-rules.md` のワーカー一覧を同じコミットで更新する。
- **問い 3 は上の表**。自動で適用するのは観測要求と（既定 dry の）書き戻しだけで、残りは
  **成果として記録し、適用は人の承認を経る別経路**に残す。

API のコマンドハンドラ（`sbp.api.commands`）は**キューに積むところまで**で、適用しない。
ハンドラが重い仕事をすると、HTTP のタイムアウトが人の判断を失わせる。

## 影響

- **不変条件 2（追記専用）**: 判断キューはアサーションではない。解決の結果は `Discrepancy`
  の状態遷移として記録され、そちらは追記専用の規律に従う。
- **不変条件 3**: 人の判断は `observed`（設計書 §14 のトレースでも人の回答が最上位の事実性を
  持つ）。ただし本 ADR の範囲では判断を**アサーションとして登録しない**——`Discrepancy` の
  `resolution` が記録であり、信念グラフに二重に書かない。
- **不変条件 11**: この経路に LLM は入らない（概念提案の生成は M6-04 で、採否は人）。
- **オントロジー版**: 変更なし（0.5.0）。
- **構成**: ワーカーが 4 → 5。CLAUDE.md・development-rules.md・`scripts/dev.py` の
  `WORKERS` を更新する。
- **テスト**: 単体でキューの意味・ハンドラの検証・ワーカーの適用範囲（自動適用するのは
  観測要求と dry の書き戻しだけ）、統合で実物の Postgres に対するキューの往復。

## 未決

- **適用の再試行回数と打ち切り**。いまは失敗を `failed_at` に記録して候補から外す
  （無限に再試行しない）。打ち切ったものを人が再投入する経路は未実装。
- **`Discrepancy` の永続化が無い**（M8-12）。判断キューは `discrepancy_id` を持つが、
  不一致の本体を読む先が無いので、ワーカーは**判断に含まれる情報だけで**適用する。
  `apply_resolution` は `Discrepancy` を要求するため、本 ADR の範囲では
  `convert_resolution` に渡す不一致を**キューの行から再構成する**——これは M8-12 で
  本体を読めるようになったら差し替える。
- **概念採択（`curate_concept`）の適用**。提案の採否を記録するところまでで、採択後の
  オントロジー MINOR 起票は人の手作業のまま（M6-04 の決定を維持）。
