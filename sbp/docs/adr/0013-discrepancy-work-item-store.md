# ADR-0013: 不一致は作業項目として表に持ち、イベントは通知のままにする

- 日付: 2026-10-04
- 状態: 採択
- 触る層: knowledge（不一致の表）、api（GraphQL 資源）、services（照合ワーカーの書き込み、learning-worker の読み出し）、infra（alembic）

## 文脈

M8-04 で不一致の起票を**イベントとして**出せるようにしたが、そのとき分かったのは
**`EventEnvelope` に不一致の全体を入れる場所が無い**ことである（`docs/PROGRESS.md` 所見 62）。
封筒は `modality` ＋ `belief` ＋ `evidence` を必須に持つ形で、根拠アサーション・状態履歴・
深刻度の内訳・解決・学習信号を入れるフィールドが無い。

結果として、

- UI（M7-04）は不一致キューの型と並べ替えロジックを持つが、**読む先が無い**
  （`fetchDiscrepancies` は `/stream/{topic}` を読み、各イベントの `payload` が
  `Discrepancy` そのものだと仮定している——実際の封筒にその形は無い）、
- `learning-worker`（M8-08）は不一致の本体を読めないので、**判断の行から最小の不一致を
  再構成する**回避をしている（証拠を持たないので記録訂正の提案が出ない）、
- 「どの不一致が未解決か」を引く経路が無い。

関連: 設計書 §8.2（不一致のライフサイクルと五類型）、§6.1（イベントエンベロープ）、
§6.8（投影）、ADR-0010（起票イベント）、ADR-0011（作業キューの先例）、ADR-0012（判断キュー）。

## 選択肢

### 問い 1: 不一致の本体をどこに持つか

1. **投影表（作業項目）に持つ。**
   - 利点: 「未解決の一覧を深刻度順に」「この不一致の履歴」という問い合わせが素直。状態機械を
     持つ作業項目であり、`quarantine` / `observation_requests` / `learning_decisions` と同じ
     形である。UI が読むのはこの形である。
   - 欠点: 「状態はイベントの投影」の原則から外れて見える（後述のとおり外れている）。
   - MacBook 上のコスト: 表 1 つ。行数は未解決の不一致の数で、小さい。
2. 知識グラフにアサーションとして書く。
   - 利点: `sbp-core:Discrepancy` はオントロジーの概念であり、RDF に素直に載る。二時制・来歴が
     そのまま付く。
   - 欠点: **作業項目としての問い合わせが重い**。「未 Assign を深刻度降順に 50 件」を SPARQL で
     書くと、深刻度の内訳（スコア・価値・確信度・持続）を別々の三つ組から集めて並べ替える
     ことになる。状態遷移の履歴も三つ組の列になり、UI が読むたびに再構成が必要である。
     さらに**二時制の意味が合わない**——不一致の状態は「いま誰が持っているか」であって、
     「いつ現実にそうだったか」ではない。
3. イベントログだけで持ち、購読側が自分で畳む。
   - 欠点: **封筒に全体が入らない**（所見 62）。入れるには任意ペイロードを足すことになり、
     「全イベントが同じ形」という §6.1 の前提が崩れる。

### 問い 2: 表は純粋な投影か

**純粋な投影にはできない。** 「状態はイベントの投影」が成立するには、イベントから状態を
再構成できなければならない。しかし起票イベントは通知であって不一致そのものではない
（問い 1 の選択肢 3 と同じ理由）。したがって

- **照合ワーカーが表に直接書く**（本体を持っているのはそこだけ）、
- **イベントは通知のまま**（購読側は「起票された」ことを知り、詳細は表を引く）

という形になる。これは規律の例外なので、**なぜ例外なのかを表のコメントと本 ADR に残す**。

### 問い 3: 列に展開するか jsonb で持つか

1. **問い合わせに使う列だけを展開し、本体は jsonb で持つ。**
   - 利点: `Discrepancy`（pydantic）が契約であり、読み出しで検証できる。モデルにフィールドが
     増えてもマイグレーションが要らない。
   - 欠点: jsonb の中身は SQL から扱いづらい（が、扱うのは展開した列だけでよい）。
2. 全フィールドを列に展開する。
   - 欠点: `Discrepancy` は入れ子（`severity` / `resolution` / `learning` / `suppression` /
     `history`）を持ち、列に落とすと 20 列を超える。**モデルを変えるたびにマイグレーション**に
     なり、加法的な変更（付録 A.2 への追加）が重くなる。

## 決定

- **問い 1 は選択肢 1**（投影表）。`discrepancies` 表（alembic 0006）。
- **問い 2**: 純粋な投影ではない。照合ワーカーが書き、イベントは通知のまま。理由を表の
  コメントに残す。
- **問い 3 は選択肢 1**: 問い合わせ用の列（`site` / `status` / `kind` / `severity_score` /
  `detected_at` / `subjects`）＋本体の `payload jsonb`。読み出しで `Discrepancy` に検証する。

**状態の後退を拒否する。** 書き込みは `Discrepancy.transition()` を通った結果だけが来る前提
だが、表の側でも「終端状態から非終端へ戻す更新」を弾く——複数の経路（照合ワーカーと
learning-worker）が同じ行を触るので、片方が古い状態で上書きする事故が起こりうる。

**API は GraphQL の資源にする。** UI は信念を GraphQL で読んでいるので、不一致も同じ経路に
揃える。`/stream/{topic}` を読む現在の UI は**イベントに全体が入っている前提で書かれており、
その前提は成立しない**ので、UI 側の差し替えが必要になる（M8-16 として分けた——API と UI を
同じ 1 日に入れると粒度を超える）。

## 影響

- **不変条件 2（追記専用）**: 表はアサーションではない。ただし**履歴を上書きしない**——
  `history` は `Discrepancy` が持つ append-only の列で、`transition()` が足す。
- **不変条件 3**: 表に様相は無い（作業項目であって主張ではない）。不一致が根拠にしている
  信念は `assertions` の IRI で参照し、信念グラフ側に残る。
- **不変条件 6（監査隔離）**: 表は推定の入力にならない（UI と learning-worker が読むだけ）。
  `AuditMask` の対象ではない。
- **オントロジー版**: 変更なし（0.5.0）。`sbp-core:Discrepancy` は既存。
- **M8-08 の回避の解消**: `learning-worker` が本体を読めるようになるので、再構成
  （`reconstruct_discrepancy`）は**本体が無いときの代替**に後退させる。証拠を持つ不一致が
  読めれば記録訂正の提案が出る。
- **テスト**: 単体で状態後退の拒否と検証、統合で実物の Postgres への往復と
  「照合ワーカーが書く → learning-worker が読む」の連結。

## 未決

- **UI の差し替え**（M8-16）。`fetchDiscrepancies` を GraphQL に向け、証拠 IRI から信念を
  引く経路を作る。いまの UI の型（`observedEvidence: Belief[]`）は**イベントに信念が
  埋まっている前提**で、成立しない。
- **証拠 IRI から信念を引く経路**。`AssertionStore.query` は主語・述語で絞るが、
  アサーション ID では引けない。UI が証拠を並置するには ID 引きが要る（M8-16 で判断）。
- **古い不一致の整理**。`Learned` / `Suppressed` になった行を落とす運用（パーティション・
  アーカイブ）は未定。行数は未解決の数に比例するので、当面は問題にならない。
