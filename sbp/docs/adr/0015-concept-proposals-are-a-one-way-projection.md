# ADR-0015: 概念提案の作業項目表は一方向の投影で、潜在の重心を持たない

- 状態: 採択
- 日付: 2026-10-04
- 関連: ADR-0013（不一致の作業項目表）、ADR-0012（learning-worker が人の判断を適用する）、設計書 §8.6（概念発見）、§11.2（curation）、M8-19

## 文脈

UI に概念 curation の画面があるが、**読む先が無い**。存在しないトピック
（`central.reasoning.concept`）を読んでおり、型も backend と別物だった（所見 85）。

不一致（ADR-0013）と期待（M8-18）は作業項目表 + GraphQL 資源で解決した。概念提案も同じ形に
するが、**1 点だけ事情が違う**: `ConceptProposal.signals[].cluster` が
`LatentCluster`（`centroid: NDArray[np.float64]` を持つ）を抱えている。

さらに **UI の判断材料が backend の型に無い**。UI は「支持する標本数」と「既存概念での被覆率」で
提案を検査するが（`checkProposal`）、どちらも `LatentCluster` の中（`size` と
`mean_probe_activation`）にある。

## 決定

1. **潜在の重心を表に入れない。** `cluster` は payload から落とす。
2. **判断に要る 2 つのスカラーは導出して持つ。** `support_count`（= 構成標本数の合計）と
   `coverage`（= プローブ活性の平均）を**書き込み時に計算して** payload に入れる。
3. **読み戻しは「cluster を復元しない」ことを明示する。** `from_record` は提供するが、
   signals の `cluster` は必ず `None` になる。これをテストで固定する。
4. **curation が状態を進める。** learning-worker の `_apply_curation` が表の `status` を
   更新する——いまは記録するだけで、採否を入れても提案が `proposed` のまま残り続けていた。

## 理由

### 重心を落とす

- **潜在ベクトルは潜在索引のものである。** 作業項目表に置くと、同じ値が 2 箇所にあり、
  再接地で片方だけが古くなる。索引は WM 版で無効化されるが、この表はされない。
- **誰も読み戻さない。** curation は人が読んで判断する作業で、重心を見ない。`_apply_curation`
  も提案の本体を使わない。
- 不変条件 9 は潜在の永続化を**許す**（禁じているのは生映像・音声）。だから「禁止だから」では
  なく「所有者が別だから」置かない。

### 導出スカラーを持つ

- **UI の検査が機能しなくなる。** 「標本 10 件未満は偶然のクラスタと区別できない」「既存概念の
  被覆率 50% 超なら既存概念の調整で足りる」は設計書 §11.2 の判断で、捨てると curation が
  「名前と定義を読んで決める」になる。
- **読み出しで計算できない。** 重心を落とすので、読む側は標本数を知らない。
- **投影の列と同じ扱いにする**（所見 90 の反省）: 導出値は書き込み時に 1 回だけ計算し、
  読み出しで再計算しない。

### 一方向であることを隠さない

M8-18 では「列とプロパティが同名で違う値」を作ってしまった（所見 90）。同じ失敗を避けるため、
**往復しないことを関数の docstring とテストに書く**。`from_record` が `cluster=None` を返すのは
バグではなく決定である、と読める形にする。

## 選択肢

### A. 重心を落として導出スカラーを持つ（採択）

上記のとおり。欠点: 往復が完全でない。緩和: テストで固定し、docstring に書く。

### B. 重心を JSON 配列で payload に入れる

利点: 完全な往復。
欠点: **却下。** (1) 潜在索引と二重になる（再接地で食い違う）。(2) 次元が増えると payload が
膨らむ（64 次元 × float = 1 提案あたり数 KB）。(3) 読む側が誰も使わない。

### C. 表に入れず、提案をイベントログで運ぶ

**却下。** ADR-0010 / ADR-0011 と同じ理由——`EventEnvelope` に提案の全体を入れる場所が無い。
提案は主張ではなく作業項目である（様相格子に席が無い）。

### D. `ConceptProposal` を pydantic に変える

利点: 直列化が自動になり、読み出しの検証が揃う。
欠点: **今回はやらない。** `__post_init__` の検証・`curate()`・`LatentCluster` の numpy を
抱えたまま移すのは別の変更で、M8-19 の範囲を超える。`ConceptProposalRecord`（表の行）は
pydantic にするので、**API が返す形は検証される**。提案本体の検証は `__post_init__` が行う
（読み戻しで必ず走る）。

## 帰結

### 良くなること

- UI の概念 curation が実在する資源を読む（4 ビューすべてが GraphQL になる）。
- **curation が提案の状態を進める。** 採否を入れた提案がキューから消える——いまは
  `_apply_curation` が記録するだけで、同じ提案が永久に画面に残っていた。
- 判断材料（標本数・被覆率）が表に残り、提案した時点の値で後から監査できる。

### 悪くなること・残る穴

- **書く側がまだ無い。** 概念発見を周期実行するのは M8-09 で、この表に書くのはそれである。
  M8-19 の時点では表が空のまま——ただし**空と「読めない」は UI で区別される**（所見 32）。
- **往復が完全でない**（上記）。
- **導出スカラーは書き込み時の値で固まる。** 後でプローブが増えて被覆率が変わっても、提案の
  行は更新されない。これは**正しい**（提案した時点の判断材料を残す）が、「いまの被覆率」を
  知りたい運用には別のクエリが要る。

## 不変条件への影響

- 不変条件 9（潜在の永続化）: 触れない。重心を**置かない**決定で、禁止の回避ではない。
- 不変条件 2（追記専用）: 表は作業項目でアサーションではない。状態の更新は UPDATE で行う
  （ADR-0013 と同じ）。
- 不変条件 11（LLM をホットパスから呼ばない）: 提案は LLM 由来だが、curation は人の判断で、
  表の読み書きに LLM は関わらない。

## オントロジー版

変更なし（0.5.0）。概念の**採択**がオントロジー MINOR を起票するが、それは人の手作業である
（M6-04 の決定）。

## 未決

1. **採択後の起票を追跡するか。** いま `ACCEPTED` になった提案が、実際に `ontology/` に
   入ったかどうかを基盤は知らない。追跡するなら「採択したが未実装」の状態が要る。
2. **却下の再提案を抑えるか。** `curation_note` に理由が残るが、次の発見サイクルが同じ
   クラスタから同じ提案を出すのを止める仕掛けは無い。
