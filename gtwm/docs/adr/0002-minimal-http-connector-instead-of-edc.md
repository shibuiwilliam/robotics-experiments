# ADR-0002: 2拠点連合に Eclipse Dataspace Components (EDC) ではなく自前の最小 HTTP コネクタを使う

- 日付: 2026-09-13
- 状態: 採用

## 状況

docs/poc_plan.md 5.5「データ空間層（C12）」および H8/EXP-09（3.2、6.2）は、拠点間の予測交換を
ODRL ポリシー（目的限定・保持期間・再共有禁止）で強制する仕組みとして「EDC コネクタ」を挙げている。
docs/prompts.md セッション10のプロンプト自身が「EDC の構築が1日を超えそうなら、ODRL ポリシーを
強制する最小 HTTP コネクタを代替として実装し、その判断を ADR で記録すること」と明示的に許可している。

EDC（Eclipse Dataspace Components）は Java/Gradle ベースの本格的なデータスペース基盤で、実運用には
最低限でも次が必要になる：
- コントロールプレーン・データプレーンの2プロセス構成、DID/Verifiable Credentials による参加者認証、
  Contract Negotiation / Transfer Process という多段プロトコル状態機械。
- PostgreSQL（コントロールプレーンの永続化）、HashiCorp Vault 相当（鍵管理）などの追加ミドルウェア。
- arm64 で動作確認済みの公式イメージの有無、Docker Compose での最小構成の組み方に関する追加調査。

本 PoC は Python（uv, MuJoCo, PyTorch）のシミュレーション基盤であり、Java ベースの EDC を「モック
第二拠点」1本のためだけに統合するコストは、CLAUDE.md の計算予算・作業規律（「30行を超える変更や
新規モジュールは着手前に対象ファイル・テスト・受入基準・所要時間を示す」「実装は最小限にする」）と
比較して明らかに1日（このセッションの作業予算）を超える。

## 検討した選択肢

1. **実際に EDC を統合する**：ODRL ポリシー強制・Verifiable Credentials・監査ログなど、poc_plan.md が
   想定する「本番相当」の連携基盤を体験できる。しかし Java 環境のセットアップ、コントロール/データプレーン
   2プロセス、Postgres 依存の追加により、この PoC の他コンポーネント（Python 一色）との整合性が崩れ、
   実装・デバッグ・CI のコストが本セッションの予算を大きく超える。
2. **最小 HTTP コネクタを自作する**（採用案）：Python 標準ライブラリ（`http.server`、`sqlite3`）のみで、
   「目的限定・保持期間・再共有禁止」を検査する ODRL 相当のポリシーオブジェクト、拒否理由付きの監査ログ、
   信念・予測のみを運ぶ交換用スキーマ（生映像・潜在は型として存在しない）を実装する。EDC が保証する
   厳密な契約交渉プロトコルや参加者認証（DID）は実装しないが、H8/EXP-09 が要求する測定
   （受領側 ECE、ポリシー違反監査ログ件数、漏洩評価）を行うには十分。
3. **コネクタを作らずスキップする**：EXP-09・H8 の検証ができなくなり、ユーザーの「全実装を完了させる」
   という明示的な指示に反する。不採用。

## 決定

選択肢2を採用する。`src/gtwm/dataspace/` に、ODRL 相当のポリシー検査（`policy.py`）、SQLite 監査台帳
（`audit.py`、`grounding/ledger.py` と同じ設計思想）、交換用データモデル（`models.py`。pydantic の
`extra="forbid"` で生映像・潜在フィールドの追加を型レベルで禁止）、コネクタのコアロジック（`connector.py`）
と、それを Docker で動かすための標準ライブラリのみに依存する HTTP サーバラッパー（`server.py`）を実装する。
`docker-compose.yml` の `p2` プロファイルで、site_a / site_b を別 Docker ネットワークに配置したコンテナ
として起動する。

## 結果と影響

- poc_plan.md 5.5「互換性：ウラノス・エコシステムのデータ連携仕様との整合を確認する」は、実際の EDC
  connector を使わないため本 PoC の範囲では評価できない。本番化の判断（poc_plan.md 11章）の際に、
  この自作コネクタを実際の EDC 仕様に置き換える作業が必要になる旨を `docs/status.md` に明記する。
- 参加者認証（DID/Verifiable Credentials）は実装しない。ポリシー検査は「宣言された目的」の文字列比較で
  行う信頼ベースの簡易実装であり、なりすまし対策は無い（PoC のスコープ外、監査ログで事後確認する設計）。
- H8/EXP-09 の合格基準（`experiments/criteria.yaml`）自体への影響はない（コネクタの実装方式は指標の
  定義を変えない）。
