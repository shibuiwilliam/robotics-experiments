# EXP-04 結果

## 目的
整合性ギャップ ε がプロセス逸脱（業務手順変更＝ドリフト）の検知指標として機能するかを検証する（H3、poc_plan.md 3.1・6.2）。

## 設定
- config: `experiments/EXP-04/config.yaml`（`full_run`）
- データ: `exp04_seed{0,1,2}`（実行時自動生成、baseline 14本 + drift 6本 × 3seed）
- ε: `configs/grounding/epsilon.yaml` の h=10s。**F^h 修正後**（commit `10a8458`：F^h が `events.parquet` の業務記録を参照する本来の実装に置換）の初めての本実行
- probe: `configs/grounding/probe_train_full.yaml`、WM: `runs/wm/checkpoints_full/best.pt`
- 実行: `runs/EXP-04/20260914-143908/`
- seeds: [0, 1, 2]
- 所要時間: 101,054s（約28時間。他実験との資源競合下、かつ `run_ground` の逐次実行による）

## 判定
**不合格**（`epsilon_daily_cv` は達成、`drift_detection_auroc` が未達）

## 考察

### 主要な発見：ドリフトが実質的に注入されていない（退行実験）

AUROC の平均は **0.472** で、これは偶然水準（0.5）とほぼ同じです。seed 別に見ても 0.321 / 0.679 / 0.417 と 0.5 を挟んで散らばっており、**符号すら安定していません**。さらに、ドリフト群の平均 ε（0.08491）は baseline 群（0.08629）より**わずかに低い**——期待される方向（ドリフトで ε が上がる）と逆です。

「検知性能が低い」のではなく、**検知すべき信号が存在しない**状態だと判断し、ドリフト注入の実効性を直接検証しました。

`sim/drift.py` は poc_plan.md 6.2 の2種のドリフトを実装しています：

1. `inspection_position_change`：`inspecting` の記録の `zone` を別ゾーンに書き換える
2. `picking_order_change`：`picking` 記録の個体対応を時刻順で反転させる

実データ（`data/sim/exp04_seed0/ep_0000_seed0/events.parquet`、343行）で実測した結果：

```
event_type:  anchor 185 / record 158
biz_step（record のみ）: storing 137, picking 21
inspecting 行数: 0            ← ★
```

**`inspecting` イベントは1件も存在しません。** したがって `inspection_position_change` は
**0行を書き換える完全な no-op** です。poc_plan.md が指定する2種のドリフトのうち、
1種が丸ごと不活性のまま実験が回っていました。

残る `picking_order_change` も、`apply_drift` を実データに適用して計測すると
`entity_gt_id` の変更は **18行（全343行の5.2%）** にとどまります。しかも変更内容は
「どの個体がピッキングされたと記録されるか」の入れ替えであり、ε が比較に使うゾーン
情報そのものは大きく動きません（`zone` 列の変化は8行）。

これは EXP-06（シールドが一度も発動しなかった退行実験）と同型の問題です：
**処置が施されていない状態で処置の効果を測っている**ため、AUROC が偶然水準になるのは
当然の帰結であり、この結果は「ε がドリフトを検知できない」ことの証拠にはなりません。
H3 は**検証されていない**（反証されたのでもない）というのが正確な表現です。

なお `inspecting` が発火しない件自体は既知でした——EXP-08（概念発見）の実装時に
「`inspecting` は秤アンカーの固定位置が実質到達不能なため一度も発火しない」ことが
48エピソードの監査で判明し、EXP-08 側は注入対象を `storing` に振り替えて対処しています
（`docs/status.md` 着手順9参照）。**同じ既知の欠陥が `sim/drift.py` には反映されておらず、
EXP-04 だけが取り残されていました。**

### 副次的な観察

- **`epsilon_daily_cv = 0.111` は目標（≤0.2）を達成**しています。平常時の ε は
  エピソード間で安定しており（変動係数11%）、管理限界を引くベースとしては機能し得る
  ことを示唆します。H3 の2指標のうち「平常時 ε の安定性」側は成立していると言えます。
- ε の絶対水準が smoke 期（0.28〜0.35）から本実行（0.086）へ大きく下がりました。
  F^h 修正（記録参照）と本実行用 probe（`zone_f1_macro=0.808`）の併用により、
  知覚側の誤りが減ったことと整合します。
- ε の3分解（知覚誤り / プロセス不遵守 / オントロジー欠落）の観点では、今回の
  不合格は「(2) プロセス不遵守」を検知する能力を測ろうとして、**そもそも
  プロセス不遵守を発生させられていなかった**ケースに該当します。(1)(3) は無関係です。

## 次のアクション（優先順）

1. **`sim/drift.py` の `inspection_position_change` を、実際に発火する biz_step を
   対象に振り替える。** EXP-08 が `reinspecting_step` で採った対処（`inspecting` →
   `storing`）と同じ方針を適用するか、あるいは `sim/sensors/anchors.py` の秤アンカーの
   到達可能性そのものを修正して `inspecting` を発火させる。後者の方が poc_plan.md の
   意図（検品位置の変更）に忠実だが、シーン設計の変更を伴う。
2. **ドリフトの実効性を実験の前提条件としてテストする。** 「`apply_drift` が
   N行以上を実際に変更すること」をユニットテストで固定し、注入が no-op に退化したら
   赤くなるようにする（EXP-06 の planner チューニング未継承と併せて、
   「処置が施されたことを確認してから効果を測る」という共通の再発防止策）。
3. 上記1・2の後に EXP-04 を seed×3 で再実行し、`drift_detection_auroc` を再判定する。
   閾値（`experiments/criteria.yaml`）は変更しない。
4. 所要時間28時間は実用的でないため、再実行前に `run_ground` のエピソード間並列化か
   サンプリング間引き（`SAMPLE_STRIDE_FRAMES`）の見直しを行う。
