# EXP-11 結果

## 目的
非機能要件（観測→信念KG更新の E2E 遅延、稼働率、区画あたり月額計算コスト）を満たすかを検証する（N1、poc_plan.md 3.1・6.2）。

## 設定
- config: `experiments/EXP-11/config.yaml`（`full_run`：`n_trials: 20`、`duration_s: 300.0`）
- probe: `configs/grounding/probe_train_full.yaml`、WM: `runs/wm/checkpoints_full/best.pt`
- 実行: `runs/EXP-11/20260914-033140/`（probe キャッシュ修正 `3c5a4c6` 適用後）
- seeds: [0, 1, 2]（計60トライアル）
- 所要時間: 426,578s（**約118.5時間 ≒ 5日**。他実験および修正前の旧 EXP-11 プロセスとの資源競合下）

## 結果表

## 判定
**不合格**（`e2e_latency` と `availability` がいずれも未達）

## 考察

### 1. E2E 遅延385秒は「バッチ実装の定義上の帰結」であり、性能問題ではない

現在の `run_ground` は**バッチ実装**です。エピソード全フレームを処理し終えてから `store.add_beliefs()` を一度だけ呼ぶため、`frame_latencies_s` は「フレーム読込開始 → 全処理完了 → コミット完了」の経過時間になります。したがって最初のフレームほど「自分の処理時間＋残り全フレームの処理時間」を待つことになり、**p50 はおおむねエピソード処理時間の半分に張り付きます**。

実際、smoke（30秒エピソード）では p50 ≈ 7.16s、本実行（300秒エピソード）では p50 ≈ 385s と、**エピソード長にほぼ比例**しています（10倍の長さで約54倍ですが、これは資源競合でエピソード処理自体が遅くなっているため）。

つまりこの数値は「ストリーミング処理したときの遅延」を測ってはおらず、N1 が意図する「観測から信念KG更新までの遅延 ≤1秒」とは**別の量**を測っています。悲観的な上限としては誠実な値ですが、**この実装のままではどれだけ最適化しても目標を満たせません**（定義上、エピソード長に比例するため）。ストリーミング化（フレーム単位のインクリメンタルなコミット）が前提条件です。

### 2. 稼働率0.717——17件の失敗の原因が記録されていなかった（設計上の欠陥）

60トライアル中17件（28%）が失敗しました。これは smoke（3/3成功）では現れなかった新しい結果です。

しかし本実行時点の `measure()` は次の実装でした。

```python
except Exception:  # noqa: BLE001
    continue
```

**例外を握り潰し、種別も件数もトレースバックも一切残していません。** 結果としてログは全10行、`metrics.json` にも `n_success` 以外の手がかりがなく、**17件が何で落ちたのかを事後に特定できません**。稼働率という指標は「落ちた事実」だけでなく「落ちた理由」を残さなければ next action に繋がらない、という設計上の欠陥です。

エピソード生成自体は3seed とも20本すべて完了しているため（`data/sim/exp11_seed{0,1,2}` を確認）、**失敗は `run_ground()` 側**で起きています。

有力な仮説は **ffmpeg の一時的な読み込み失敗**です。本実行は 09-14 03:31 に開始しましたが、この失敗に対するリトライ修正は同日 09:02（`4b33adf`）と 14:38（`5611adb`）に入っており、**いずれも実行開始より後**です。Python は起動時にモジュールを読み込むため、この5日間の実行は終始リトライ無しのコードで動いていました。EXP-04 の本実行では同じ環境で `OSError: Could not load meta information` が実際に複数回発生しており、同一原因である可能性が高いと考えています。ただし**ログが残っていない以上これは未確認の推測であり、断定はしません**。

**対処（本レポート作成時に実施）**：`measure()` が例外クラス名ごとの件数を集計し、`failure_types_csv` として `metrics.json` に出力するよう修正しました（例：`"OSError:5,ValueError:1"`）。併せて `structlog` で失敗ごとに trial 番号・seed・例外種別・メッセージを警告ログに残します。再実行すれば原因は即座に特定できます。

### 3. 月額コスト試算 $180/区画（report_only）

`experiments/criteria.yaml` で `report_only` に指定されているため合否判定の対象外です。実測の生成速度（300秒エピソードを約75秒で処理）から、1区画を24時間監視する場合の計算時間を按分し、GPU 単価を1ドル/時と仮定したナラティブな概算です。単価はクラウド事業者・リージョン・割引で大きく変動するため、あくまで桁感の提示にとどまります。

### 4. 所要時間118時間という運用上の問題

probe キャッシュ修正（`3c5a4c6`）により、当初見積もりの70時間超（1トライアルごとにαを6000ステップ再学習していた）は回避したはずでしたが、それでも118時間かかりました。主因は以下と考えられます。

- 60トライアル × 300秒エピソード（生成＋300フレームの推論）という単純に大きい計算量
- EXP-04 本実行（28時間）との資源競合
- **修正前の旧 EXP-11 プロセスを停止できず、5日間ずっと並走していた**（同一マシンで同じ計算を二重実行）

## 次のアクション（優先順）

1. **`run_ground` をストリーミング化する。** フレーム単位で信念をコミットし、`frame_latencies_s` を「そのフレームの観測→そのフレーム由来の信念がKGに入るまで」に定義し直す。これをやらない限り N1 の遅延要件は定義上達成不可能。
2. **稼働率0.717 の原因を特定する。** 今回入れた `failure_types_csv` とログを有効にした状態で、`n_trials` を小さく（例：5）して短時間で再現させる。ffmpeg リトライ修正（`5611adb`）適用後なので、仮説が正しければ稼働率は大きく改善するはず。
3. 上記2点の後に EXP-11 を seed×3 で再実行し、`e2e_latency` と `availability` を再判定する。閾値（`experiments/criteria.yaml`）は変更しない。
4. 再実行前に所要時間を短縮する（`n_trials` の見直し、エピソード処理の並列化、旧プロセスの確実な停止）。118時間は実用的な検証サイクルではない。
