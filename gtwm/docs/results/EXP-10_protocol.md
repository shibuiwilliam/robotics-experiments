# EXP-10 オペレータ評価 実施手順書

**この文書が定めるのは人手評価の手順である。Claude Code は模擬例外セットと記録機構
（`src/gtwm/grounding/exp10_harness.py`、`gtwm dashboard` の「EXP-10 例外対応」
「EXP-10 SUSアンケート」タブ）を用意するだけで、評価そのものは実行しない**
（CLAUDE.md「絶対条件」：「EXP-10（人手評価）は人が手動で行う。Claude Code は
模擬例外セットとUIだけを用意する」）。

出典：`docs/poc_plan.md` 3.1（H9）・3.2（H9詳細）・6.1・6.2（EXP-10詳細）。数値・
文言は転記であり要約ではない。

## 検証仮説

H9（3.1）：オペレータの例外処理が改善する。

## 対象者（3.2 転記）

現場リーダー・作業者**5名以上**。

## 段階

P2（3週）。

## 比較条件（3.2・6.2 転記）

- **従来手順**：記録と現物の目視突合（`gtwm dashboard` の「EXP-10 例外対応」タブで
  「traditional」を選択すると、業務記録と現物確認メモのみが提示される。乖離台帳の
  構造化表示は使わない）。
- **ダッシュボード条件**：乖離台帳ダッシュボード（同タブで「dashboard」を選択すると、
  乖離台帳のエントリ形式で提示される）。

## 手順（6.2 転記）

現場リーダー・作業者5名以上に、模擬例外10件を従来手順とダッシュボードの両方で
処理してもらう（**順序は無作為化**）。

### 順序の無作為化（実施者が満たすべき条件）

- 各評価者について、(a) どちらの条件を先に行うか、(b) 10件の模擬例外をどの順序で
  提示するか、の両方を無作為化すること。
- 推奨手順：評価者ごとに乱数（例：評価者IDのハッシュ、またはくじ引き）で
  「traditional→dashboard」か「dashboard→traditional」かを決め、10件の提示順序も
  評価者ごとに独立にシャッフルする。同一の10件を両条件で処理させる場合は、学習効果
  （2回目の条件で速くなる）を条件の順序無作為化で相殺する。
- 模擬例外10件は `gtwm.grounding.exp10_harness.generate_mock_cases()` が返す決定的な
  10件（`exp10_case_01`〜`exp10_case_10`）。H4の5型（未スキャン移動・誤棚入れ・
  誤スキャン・遅延登録・幽霊在庫）から各2件ずつ含む。

## 記録する項目（6.2「出力」転記）

解決時間、正答率、訂正反映率、SUS、自由記述。

具体的には、評価者・条件・ケースごとに `gtwm dashboard`「EXP-10 例外対応」タブで
以下を記録する（`runs/exp10_resolutions.sqlite` に保存される）：

1. **解決時間**：「対応開始」ボタン押下から「対応完了」ボタン押下までの経過秒数
   （`Exp10Harness.finish_case()` の戻り値）。
2. **正答率**：評価者が入力した対応内容が `MockCase.correct_resolution`（評価者には
   非提示の正解）と一致するかを自動判定する（自己申告ではない）。
3. **訂正反映率**：評価者が「訂正が実際に反映された」チェックボックスを付けた割合。
4. **SUS**：全ケース終了後、条件ごとに「EXP-10 SUSアンケート」タブで標準10問
   （`Exp10Harness.SUS_QUESTIONS`）に1〜5で回答してもらい、
   `compute_sus_score()`（標準SUS計算式）でスコア化する。**条件ごとに1回ずつ**
   （従来手順を使い終えた直後、ダッシュボードを使い終えた直後）記録すること。
5. **自由記述**：「対応完了」時の備考欄（`notes`）、または評価後の口頭/別紙での
   自由記述を別途記録し、`docs/results/EXP-10.md`（本実行後に作成）にまとめる。

## 合格基準（H9、3.1 転記。`experiments/criteria.yaml` が正）

- 解決時間 ≥ 30%短縮（ダッシュボード条件 vs 従来手順）
- 訂正反映率 ≥ 95%
- SUS ≥ 70

## 未達の場合の判断

poc_plan.md 3.2 に H9 専用の延長基準は明記されていない（3.3「総合判定」の一般規則：
未達は原因分析と改善案を添えて1か月延長を1回まで、2回目の未達で「不成立」として記録）。

## 実施時のチェックリスト

- [ ] 評価者5名以上を確保した
- [ ] 評価者ごとに条件順序（traditional/dashboard のどちらを先にするか）を無作為化した
- [ ] 評価者ごとにケース提示順序を無作為化した
- [ ] `gtwm dashboard` が起動しており、`runs/exp10_resolutions.sqlite` が書き込み可能である
- [ ] 各評価者が10件×2条件＝20回の対応を終えた後、条件ごとに1回SUSに回答した
- [ ] 自由記述を別途収集した
- [ ] 実施後、`Exp10Harness.summary()`（または `runs/exp10_resolutions.sqlite` への
      直接クエリ）で条件別の平均解決時間・正答率・訂正反映率を集計し、
      `docs/results/EXP-10.md` に `.claude/rules/experiments.md` のレポート形式で記録した

## Claude Code が用意した準備物（本セッションで完了）

- `src/gtwm/grounding/exp10_harness.py`：模擬例外10件の生成、解決時間・正答率・
  訂正反映率の記録、SUSスコア計算（`tests/unit/test_exp10_harness.py` で
  ユニットテスト済み）。

  （`streamlit.testing.v1.AppTest`）で、開始→対応入力→完了→SUS送信の一連の操作が
  例外なく完了し、`runs/exp10_resolutions.sqlite` に実際に記録されることを確認済み
  （正答判定・SUSスコア計算とも期待通りの値）。
- 本評価は上記の準備物を使って**人が実施する**。実施後は `/exp-report` 相当の手順で
  `docs/results/EXP-10.md` を作成し、`docs/status.md` の実験表を更新すること。
