## 0. この記事について

物流倉庫の1区画を対象に、**世界モデル（潜在ツイン）** と **オントロジー（記号ツイン）** を「接地層」で結び、**整合性ギャップ ε** という単一の量で「現場で実際に起きていること」と「システムの記録上そうなっていること」のズレを検知する——そんな二層デジタルツインの PoC を、ゼロから実装して検証しました。

## 1. 背景：なぜ「二層」なのか

### 1.1 現場で起きている問題

物流倉庫には常に2つの「真実」が存在します。

- **物理の真実**：パレットが実際にどこにあり、誰が何を運んだか
- **記録の真実**：WMS（倉庫管理システム）が「そうなっているはず」と保持している状態

この2つは日常的にズレます。スキャンし忘れたまま荷物が移動する、指示と違う棚に置かれる、登録が数時間遅れる、システム上は存在するが現物がない（幽霊在庫）——現場の方なら心当たりがあるはずです。従来はこのズレを、棚卸しという「全数目視突合」で定期的に潰してきました。

このズレを**連続的に、自動で検知できないか**。これが出発点です。

### 1.2 世界モデルだけでは足りない

近年の世界モデル（World Model）は、映像から潜在状態を推定し、その先の動態を予測する能力を急速に高めています。倉庫にカメラを置いて世界モデルを学習させれば、物理の真実は捉えられそうです。

しかし世界モデルの潜在表現は、そのままでは業務判断に使えません。「潜在ベクトル z_t が前フレームから 0.3 ずれた」と言われても、それが「パレット0042がゾーンBに移動した」のか「照明が変わっただけ」なのかは分かりません。**業務上の意味を持つ記号**に落とさなければ、記録と突き合わせることもできません。

### 1.3 オントロジーだけでも足りない

逆に、オントロジー（記号ツイン）は「パレット」「ゾーン」「危険物隣接禁止」といった概念と制約を厳密に定義できますが、**時間とともに変化する過程そのもの**を表現するのは不得手です。

ここで有用なのが、上位オントロジー（BFO 等）が古典的に立てている区別です。

- **継続体（continuant）**：物・場所・組織・契約・制約。時間を通じて同一性を保つもの。→ **オントロジーが定義する**
- **生起体（occurrent）**：移動・荷役・検品・待機といった過程。時間の中で展開するもの。→ **世界モデルが学習する**

この役割分担が、本 PoC の設計上の背骨になっています。オントロジーに動態を書き下そうとして破綻する、あるいは世界モデルに制約を暗黙に学ばせようとして保証が得られない——その両方を避けるための分割です。

## 2. アーキテクチャ：5層と接地層

### 2.1 全体構成

| 層 | 責務 | 主な構成要素 |
|---|---|---|
| 業務システム | 記録上の真実の保持、指示の発行 | WMS/WES、EPCIS イベント、オーダー |
| オントロジー層（記号ツイン） | 継続体の定義、事実の格納、制約検査 | BFO / EPCIS 2.0 / SOSA / PROV-O、RDF ストア、SHACL |
| **接地層** | α：潜在→記号、γ：記号→潜在、整合性検査、乖離台帳、同一性解決 | 学習ヘッド群、微分可能推論、台帳DB |
| 世界モデル層（潜在ツイン） | 生起体の学習と予測、潜在空間での計画 | 視覚エンコーダ、物体中心表現、潜在動態モデル |
| 物理世界 | 観測とアンカーイベントの供給 | カメラ、RFID/バーコード、扉・秤、PLC |

この2つのツインを繋ぐのが**接地層**であり、本 PoC の中核です。

### 2.2 形式的な定義

記号を導入します。

- `Z`：世界モデルの潜在状態空間。`z_t ∈ Z` は時刻 t の潜在状態（物体中心スロットの集合として実装）
- `S`：オントロジーと整合するインスタンス集合（ABox スナップショット）。`s_t ∈ S`
- `f: Z × A → Z`：世界モデルの動態（行動 a に条件付けられる）
- `F: S × E → S`：業務プロセスの遷移（EPCIS イベント e による記録の更新）
- `α: Z → Δ(S)`：**接地（抽象化）**。潜在から事実集合の確率分布を出す
- `γ: S → Z`：**条件付け（具体化）**。記号的文脈を潜在に埋め込む

そして本 PoC が測ろうとする中心量が、**整合性ギャップ**です。

```
ε_h = E_t[ d( α(f^h(z_t)),  F^h(α(z_t)) ) ]
```

日本語にすると、**「潜在空間で h ステップ先に進めてから記号化したもの」と「今すぐ記号化してから業務プロセスを h ステップ進めたもの」の差**です。物理が予測する未来と、記録が想定する未来のズレ、と言い換えてもよいでしょう。

`d` は事実集合間の距離で、事実種別ごとの不一致率を業務重要度で加重平均します（位置0.4 / 状態0.3 / 関係0.2 / 型0.1。位置の不一致はゾーン一致を0、隣接ゾーンを0.5、それ以外を1とする）。この重みは設定ファイルに置き、コードには一切書きません。

### 2.3 ε の3分解——これが効く

ε が大きいというだけでは「何かがおかしい」しか分かりません。実務で使うには**原因の切り分け**が要ります。そこで、外部から真値として扱える離散イベント＝**アンカー**（RFIDゲート通過、バーコードスキャン、秤の計量確定、扉開閉、PLC信号）を基準に、ε を3つに分解します。

| ε の発生源 | アンカー時刻での挙動 | 対応 |
|---|---|---|
| (1) 知覚・接地の誤り | アンカーで α の出力が真値と食い違う | 接地層の再学習、センサ配置見直し |
| (2) プロセス不遵守 | α はアンカーと一致するが F の予測と食い違う | 乖離台帳へ登録、業務側で確認 |
| (3) オントロジーの不完全性 | 残差が特定の潜在領域に集中し、既存の記号で説明できない | 概念発見ループへ |

「モデルが悪いのか、現場が手順を守っていないのか、そもそも語彙が足りないのか」を、同じ枠組みの中で区別できる——ここが、単なる異常検知との違いです。

## 3. 検証計画：先に基準を固定する

実装より先に、**仮説と合格基準を数値で固定**しました。

| ID | 仮説 | 主指標 | 目標値 |
|---|---|---|---|
| H1 | 潜在状態から業務事実を高精度に復号できる | 位置事実F1、型精度、ID切替率 | F1 ≥ 0.90、型 ≥ 0.95、ID切替 ≤ 0.05 |
| H2 | 記号条件付けは予測を改善する | 誤差改善率、有効ホライズン | 60秒先20%改善、H* 1.5倍 |
| H3 | ε はプロセス逸脱の検知指標になる | ドリフト検知 AUROC | ≥ 0.85 |
| H4 | 物理と記録の乖離を自動検知できる | 検知率、誤報、遅延 | ≥90%、≤2件/日、≤60秒 |
| H5 | オントロジー制約を計画のハード制約にできる | 違反率、性能損失 | 違反0、低下 ≤5% |
| H6 | WHAT-IF の反実仮想予測は実測と整合する | 相対誤差、区間被覆率 | ≤15%、≥80% |
| H7 | 未知の概念を残差から発見できる | 注入概念の上位5出現 | 3種中2種以上 |
| H8 | 拠点間で予測を安全に交換できる | ECE、復元SSIM、再識別 | ≤0.05、≤0.3、≤1.2倍 |
| H9 | オペレータの例外処理が改善する | 解決時間、SUS | ≥30%短縮、SUS ≥70 |
| N1 | 非機能要件を満たす | E2E遅延、稼働率 | ≤1秒、≥99% |

これらは `experiments/criteria.yaml` という**唯一の置き場**に転記し、コード内に閾値をハードコードすることを禁止しました。理由は単純で、**実験が終わってから閾値を動かせないようにするため**です。

### 3.1 盲検（ブラインド）を機械で強制する

乖離検知の実験（EXP-05）では、注入した乖離の台帳（「いつ・どのパレットに・どんな異常を仕込んだか」の答え）を検知側コードから読めてはいけません。人間の善意に頼るとこれは簡単に破れるので、**テストで境界を守る**ことにしました。

```python
# tests/unit/test_blindness.py（概念）
# grounding/ と wm/ 配下の全 .py を AST 解析し、
# `data/injections` への参照と `gtwm.sim.wms_mock` の注入シンボル import を禁止する。
# 台帳を読んでよいのは eval/scoring.py だけ。
```

import 文の静的検査なので、実行時に通るかどうかに関わらず検出できます。このテストは最後まで一度も落ちませんでした。地味ですが、**検証の信頼性を支えているのはこの1ファイル**です。

### 3.2 smoke と本実行の二段構え

全実験に「5分以内で終わる smoke モード」を必須としました。smoke の結果は**必ず「参考（smoke）」判定に固定**され、合格・不合格を名乗れません（`runner.py` が構造的に強制）。合否は seed×3 の本実行でのみ判定します。

これは開発速度と結果の信頼性を両立するための設計で、実際に非常によく機能しました。

## 4. 実装

### 4.1 環境制約という設計条件

実行環境は MacBook Pro（Apple Silicon）1台。GPU は MPS のみで、CUDA も Isaac Sim も使えません。この制約は最初から「絶対条件」として明文化しました。

- 物理シミュレーションは **MuJoCo 3.x**（計画書の Isaac Sim は全て読み替え）
- レンダリングは `mujoco.Renderer` の**オフスクリーンのみ**、GUI ウィンドウは開かない（EGL/OSMesa は macOS で使えないため）
- PyTorch は **float32 固定**（MPS で bf16 は使わない）
- 学習1ランは2時間以内、プロセスメモリは12GB以内

制約を先に固定したことで、後から「動かない」に遭遇する回数を大きく減らせました。

### 4.2 シミュレーション層

12m × 8m の倉庫を MJCF で構築しました。ゾーン6、ラック4本（スロット36）、ドック2、コンベア1、AGV 2台、作業者3体、パレット20＋ケース40、固定カメラ4台。

出力は1エピソードあたり、4カメラ分の MP4、セグメンテーションマスク、深度、遮蔽率、姿勢（Parquet）、イベント（Parquet）、メタ情報です。

ここで設計上重要なのは、**イベントに `t_true`（真値時刻）と `t_obs`（観測時刻）の両方を持たせた**ことです。センサのジッタや記録遅延は「物理の中」ではなく**書き出し時に注入**し、真値は必ず別に残します。これにより、後段が「遅延した記録」を見ている間も、評価側は正解を保持できます。

性能面では、30秒エピソードの生成が **7.1秒**（実時間の約0.24倍）に収まりました。目標「実時間の2倍以内」に対して大きな余裕があり、物体数の削減は不要でした。

### 4.3 オントロジー層——最初の ADR

PoC 拡張オントロジー（`gt:` 名前空間）を定義し、標準語彙（EPCIS 2.0、SOSA/SSN、PROV-O、BFO）を実際に取得して配置しました。SHACL 形状を3本（単一ゾーン、危険物隣接禁止、ゾーン容量）実装しています。

ここで最初の設計判断が必要になりました。当初計画では、信念（確信度・出所・有効時刻を伴う事実）を **RDF-star** の埋め込み三つ組で表現する予定でした。

```turtle
<< :Pallet_0042 gt:currentZone :Zone_B >> gt:confidence 0.93 ; gt:source gt:WM .
```

ところが、固定していた rdflib 7.6.0 には **Turtle-star / SPARQL-star のパーサが存在しない**ことが実装中に判明しました（`rdflib.plugin.plugins(kind=Parser)` に該当プラグインがなく、`<< s p o >>` 構文は N3 パーサが `BadSyntax` で拒否）。

選択肢は3つありました。

1. Oxigraph をインプロセス既定にする（RDF-star ネイティブ対応だが、既定バックエンドが Docker 依存になりオフライン CI が壊れる）
2. star 対応のパーサを探す／バージョンを上げる（安定版に存在しない）
3. **標準 RDF 具象化（reification）を共通表現として採用する**

採用したのは3で、これを **ADR-0001** として記録しました。rdflib と Oxigraph の両バックエンドで同一表現・同一テストを使えることを優先した判断です。

> 教訓：**「契約」に当たるもの（オントロジー、指標定義、文法）の変更は、コードより先にドキュメントを直す。** 逆に、ドキュメント通りに実装できないことが判明したら、黙って迂回せず ADR を書く。この規律があると、半年後の自分が「なぜ RDF-star じゃないんだっけ」で悩まずに済みます。

なお、CBV（GS1 Core Business Vocabulary）だけは機械可読な RDF を取得できず（`ref.gs1.org` 配下が404、`gs1.org/voc/` が403）、実際に使う URI だけを定義した**スタブであることを明記**して進めました。取得できなかったものを「取得したことにしない」のは、地味ですが重要です。

### 4.4 世界モデル層

インタフェース契約を先に固定しました。

```
Encoder.encode(frames: [B,T,C,3,H,W]) -> tokens [B,T,C,P,De]
SlotModule(tokens) -> slots [B,T,K,D], type_logits [B,T,K,6]
Conditioner(subgraph: KGSubgraph) -> cond [B,Dc]
Dynamics.rollout(slots_t, cond, actions, h) -> [B,h,K,D]
Probe(slots) -> list[Belief]
Consistency.epsilon(z_t, s_t, h) -> EpsilonRecord
```

実装は、凍結した `facebook/dinov2-small` ＋学習可能アダプタをエンコーダに、Slot Attention（K=16、D=128）で物体中心表現を作り、カメラごとのスロットを MJCF から読んだカメラパラメータで床面座標に投影して統合、4層 Transformer（d=256）のアンサンブル3本で動態を予測する、という構成です。計画は MPPI。

本実行用の学習は **613秒**で完了し、ピークメモリは約1.09GB（12GB 予算に対し大幅な余裕）、MPS fallback は **0件**でした。

### 4.5 接地層

- **α（probes.py）**：存在・型・位置（ゾーン分類＋床面座標）・状態・関係の各ヘッド。温度スケーリングで較正
- **γ（conditioning.py）**：KG 部分グラフ → R-GCN 埋め込み、およびテキスト直列化の2実装を設定で切替
- **ε（consistency.py）**：設定ファイルの重みで距離 d を計算し、h ∈ {10s, 60s, 5min, 30min} の ε_h と3分解を返す
- **同一性（identity.py）**：ハンガリアン割当。遮蔽中は WM 予測位置で保持し、アンカーで強制再同定
- **乖離台帳（ledger.py）**：SQLite。状態遷移は `open → confirmed/dismissed → resolved` のみ

α の学習で1つ、重要な発見がありました。アンカー時刻のみを教師とする自己教師あり学習で、**重み無しの交差エントロピーだと多数派ゾーンへの一様予測に崩壊する**のです。accuracy は 0.61 と一見それらしい値が出るのに、macro-F1 は 0.21 しかない。逆頻度クラス重みを入れて解消しました（macro-F1 0.658）。

> 教訓：**単一の accuracy で「学習できた」と判断しない。** クラス不均衡下では、崩壊した予測器ほど accuracy が高く見えます。

seed×3 の本実行まで到達した8実験の結果です。合格基準は一切動かしていません。

| EXP-01 | H1 接地精度 | 位置F1 **0.898**（目標0.90）、型精度 **0.714**（目標0.95） | **不合格** |
| EXP-02 | H1 遮蔽下の同一性 | ID切替率 **0.166**（目標0.05）※baseline 0.394 から58%改善 | **不合格** |
| EXP-03 | H2 記号条件付け | 60秒改善率 **測定不能（NaN）**、有効ホライズン比 **1.0**（目標1.5） | **不合格** |
| EXP-04 | H3 ε とドリフト検知 | AUROC **0.472**（目標0.85／偶然水準）、日次変動係数 **0.111**（目標0.2以下 ✅） | **不合格** |
| EXP-06 | H5 シールド付き計画 | 違反 **0/100**、スループット低下 **0.0** | 合格（※実質性に疑義） |
| EXP-07 | H6 反実仮想の忠実性 | 相対誤差 **0.694**（目標0.15）、区間被覆率 **0.0**（目標0.80） | **不合格** |

| EXP-09 | H8 連合と漏洩 | ECE **0.580**（目標0.05）、復元SSIM **0.193**（目標0.30 ✅）、再識別 **2.47倍**（目標1.2倍） | **不合格** |

EXP-05（H4）と EXP-11（N1）は本実行が現在も継続中です。EXP-10（H9）は**人手評価が本質的に必要**な実験のため、ハーネス（模擬例外10件、解決時間・正答の記録機構、SUS 質問票、評価手順書）を準備済みで、実行そのものは人が行います。評価者の判断を機械で捏造しないことを設計上の原則としました。

**唯一、明確に達成したと言えるのは EXP-09 の復元SSIM 0.193（目標0.30以下）** です。これは「生映像も潜在も交換せず、信念と予測だけを交換する」というアーキテクチャ上の制約が直接効いた結果で、交換スキーマに画像・潜在フィールドが**構造的に存在しない**（pydantic の `extra="forbid"`）ことをテストで固定してあります。設計で保証したものが、評価でも保証された形です。

## 6. 得られた教訓

ここからが本題です。11本の実験を回して分かったことを、再利用可能な形で整理します。

### 6.1 「指標が動いていること」と「意味があること」は別問題

これが最大の学びでした。**機械的には合格しているのに、実質的には何も検証できていない**実験が2本ありました。

#### 事例A：シールドが一度も発動していなかった（EXP-06）

H5「オントロジー制約を計画のハード制約として保証できる」の検証で、100タスク×3seed を回した結果はこうでした。

```
violations_with_shield:    0.0
violations_without_shield: 0.0     ← ここ
task_cost_with_shield:     6.694228534698486
task_cost_without_shield:  6.694228534698486  ← 完全一致
```

`violations_with_shield == 0` は合格基準を満たします。しかし**シールドを外しても違反が0**で、コストが小数点以下まで完全一致している。これは「シールドが正しく守った」のではなく、**シールドが候補を除外する場面が一度も発生しなかった**ことを意味します。検証としては空振り（vacuous test）です。

原因は設定の継承漏れでした。smoke 実行では MPPI のパラメータ（`noise_std=25`、`shortcut_bonus=30`）を、smoke 用の小さな WM に対して「候補行動がゾーン予測を実際に動かす」ようチューニングしてありました。ところが本実行用の設定ブロックがこの `planner:` サブブロックを上書きしないため、**まったく別のアーキテクチャで学習した本実行用チェックポイントに、smoke 用のチューニング値がそのまま適用された**のです。

#### 事例B：1個のクラスタが3種類の概念に「命中」した（EXP-08）

H7「未知の概念を残差から発見できる」では、注入した3種の未登録概念すべてに命中し、合格基準（3種中2種以上）を満たしました。しかし内訳を見ると：

```
n_candidates: 1                    ← 候補は1個だけ
injected_concept_top5_hit: 3       ← なのに3種命中
```

命中判定は「候補クラスタのメンバーが観測された時刻が、注入イベントの時刻と5秒以内で近接するか」という時間的近接性の代理指標です。つまり、**広い時間範囲にまたがる1つの「キャッチオール」クラスタができてしまえば、3種の注入が別々の時刻に起きていても全部命中扱いになる**。これも「3つの異なる新概念を区別して発見した」ことの実証にはなっていません。

#### 事例C：realism の ON/OFF で ε がビット単位で同一だった

これが最も示唆的でした。センサノイズ・記録遅延・乖離注入を有効にした場合と無効にした場合で、ε_60s を比較したところ：

```
realism ON:  0.3515151515151509
realism OFF: 0.3515151515151509    ← 表示可能な全桁が一致
```

「有意差なし」ではありません。**浮動小数点で完全に同一**です。ここまで一致するのは偶然ではあり得ないので追跡したところ、構造的な原因が判明しました。

`compute_epsilon` の F^h（業務プロセスの遷移）が、こう実装されていたのです。

```python
expected_future_zone_idx = s.perceived_zone_idx  # 恒等写像
```

つまり「h 秒後に記録が想定するゾーン」を、**世界モデル自身の現在の知覚ゾーンで代用していた**。realism 設定が変更するのは `events.parquet`（業務記録）だけなので、記録を一切参照しないこの実装では、realism は数学的に ε に影響し得ません。

ε は「物理と記録のズレ」を測る量のはずが、実態は**世界モデル内部の一貫性しか見ていなかった**わけです。定義上の中心概念が、実装では骨抜きになっていた——しかも全テストは緑のまま。

修正後は、`events.parquet` の直近の記録ゾーンを参照する本来の F^h に置き換えました（分離テストで 0.0 → 0.00815 と実際に反応することを確認）。

#### 事例D：ドリフトを注入したつもりが、注入されていなかった（EXP-04）

H3「ε はプロセス逸脱の検知指標として機能する」の本実行は、28時間かけてこう出ました。

```
drift_detection_auroc: 0.472        ← 偶然水準（0.5）
  seed別: 0.321 / 0.679 / 0.417     ← 0.5 を挟んで符号すら不安定
baseline_epsilon_10s_mean: 0.08629
drift_epsilon_10s_mean:    0.08491  ← ドリフト群の方が「低い」（期待と逆）
```

「ε の検知性能が低い」と結論づけたくなる数字です。しかし**ドリフト群の ε が baseline より低い**——期待と逆方向であることが引っかかりました。検知が弱いなら差が小さくなるはずで、逆転する理由はありません。そこで**処置が本当に施されたのか**を実データで確認しました。

`sim/drift.py` は poc_plan.md が指定する2種のドリフトを実装しています。検品位置変更（`inspecting` 記録のゾーン書き換え）と、ピッキング順序変更（`picking` 記録の個体対応の反転）です。実際に生成されたエピソード（343行）を数えると：

```
event_type:  anchor 185 / record 158
biz_step:    storing 137, picking 21
inspecting:  0 件      ← ★
```

**`inspecting` イベントが1件も存在しません。** つまり検品位置変更は**0行を書き換える完全な no-op** でした。2種のドリフトのうち1種が丸ごと不活性です。残るピッキング順序変更も、実測で `entity_gt_id` の変更は 18/343 行（5.2%）にとどまります。

処置がほぼ施されていないのですから、AUROC が偶然水準になるのは当然です。**この結果は「ε がドリフトを検知できない」ことの証拠にはなりません。H3 は反証されたのではなく、未検証**というのが正確な表現です。

さらに苦いのは、この欠陥が**既知だった**ことです。EXP-08 の実装時に「`inspecting` は秤アンカーの位置が実質到達不能なため発火しない」ことが48エピソードの監査で判明し、EXP-08 側は注入先を `storing` に振り替えて対処済みでした。しかし `sim/drift.py` には反映されず、EXP-04 だけが取り残されていたのです。

そして既存のユニットテストは**全て緑でした**。理由は明快で、テストの合成フィクスチャに `inspecting` 行が含まれていたからです。

```python
# 従来のフィクスチャ（テストは通るが、実データには存在しない行）
{"biz_step": CBV_BIZSTEP["inspecting"], "zone": "Inspect", ...}
```

変換ロジックは正しく、テストも正しくそれを検証していました。**間違っていたのは「そのロジックが実データに適用され得る」という前提**の方です。

再発防止として、変更行数を返す `drift_change_report()` を追加し、`drift_rows_changed` / `drift_inspecting_rows` を EXP-04 の指標として `metrics.json` に出すようにしました。これで「検知性能が低い」と「処置が施されていない」が数字の上で区別できます。テストも、実データと同じ構成（`inspecting` 行なし）のフィクスチャで no-op が露見することを確認する形に追加しました。

#### この4つに共通する検出法

いずれも、**「差が出ないこと」「差が想定と逆なこと」を異常として扱った**から見つかりました。

> **チェックリスト：指標が「動いている」ことを疑う**
> - 対照条件（あり/なし、ON/OFF）で数値が**完全に一致**していないか
> - 差が**想定と逆方向**に出ていないか（弱い信号では説明できない）
> - 「効くはず」の設定を変えたのに結果が変わらなくないか
> - 合格した指標について、**不合格になり得る経路が存在するか**を説明できるか
> - 分母・母数（`n_candidates`、`n_samples`、変更行数）が想定通りか
> - **処置そのものが施されたことを、効果とは独立に計測しているか**

最後の2つが決定的でした。医学試験で言えば「投薬したことの確認」に相当します。効果を測る前に、**処置が実際に行われた証拠を別の指標として残す**——これを最初から仕込んでおけば、EXP-04 の28時間と EXP-06 の38分は救えました。

そして「不合格になり得る経路を説明できるか」も同じくらい重要です。「シールドを外したら違反が出るはずだ」という反実仮想を説明できないなら、その合格は検証になっていません。

### 6.2 配線バグは、エラーを出さずに静かに失敗する

本実行に移行する段階で、**「本実行の設定が一切効いていない」**というバグを3件発見しました。

**(1) `full_run` ブロックがマージされていなかった**

各実験の設定ファイルには、本実行用のパラメータを書いた `full_run:` ブロックが最初から用意されていました。ところが `runner.run()` はこれを**一度も読んでいなかった**のです。`smoke: false` に切り替えても、smoke と同じエピソード数・同じ長さ・同じチェックポイントで3回走るだけ。「本実行」という名の smoke の3連実行でした。

**(2) `SMOKE=0` が Makefile のレシピシェルに渡っていなかった**

(1) を直した後も、`make exp EXP=EXP-06 SMOKE=0` で実行した結果の `metrics.json` に `"smoke": true` が残っていました。環境変数がサブシェルに伝播していなかったためです。

**(3) `seq_len` の拡張漏れで測定対象が消えた**

EXP-03 の本実行設定で、ホライズンを60秒相当まで拡張したのに、シーケンス窓長 `seq_len` を smoke の値（20）のまま据え置いていました。結果、16秒以降のサンプルが恒常的にゼロ件になり、主要指標が全て NaN に。

3件とも例外を投げません。**それらしい数値が最後まで出てきます。** (1)(2) に至っては、発見が遅れていれば「本実行の結果」として報告されるところでした。

> **対策：設定が効いていること自体をテストする**
> ```python
> def test_run_merges_full_run_overrides_when_not_smoke(): ...
> def test_run_keeps_smoke_config_when_smoke_true(): ...
> ```
> 「設定を読み込めること」ではなく「**設定を変えたら振る舞いが変わること**」をテストするのがポイントです。設定システムは、本番でしか通らない経路を持ちがちです。

### 6.3 「配線してあること」と「学習してあること」は違う

EXP-07（反実仮想の忠実性）の相対誤差は 0.694（目標0.15）と大きく外れました。診断の結果、原因は明快でした。

WHAT-IF の `do(コンベア速度 := 1.2 * current)` のような介入は、`Dynamics` の行動チャンネルに書き込まれます。この配線は正しく実装され、named channel への解決も動いています。しかし——

```python
# wm/train.py の学習ループ
modules.dynamics.rollout(slots, cond, actions=None, h)   # 常に None
```

**学習時に一度も実際の行動を渡していない**。つまり `action_in` の重みはランダム初期化のまま勾配を受け取っておらず、`do()` に何を入れてもロールアウトは意味のある方向に変化しません。配線は完璧、モデルは未学習、という状態です。

同じ構造の問題が EXP-03（記号条件付け）にもありました。条件付けあり（dynamic）が条件なし（none）より**わずかに悪い**という結果が出ており、`Conditioner` の出力を受け取る経路も同様に学習されていない可能性が高い、と切り分けられました。

> 教訓：**インタフェースが通っていることは、機能していることを意味しません。** 新しい入力経路を足したら、「その入力が学習時に非自明な値を取っていたか」を必ず確認する。`actions=None` のような無害に見える既定値が、経路全体を死んだコードにします。

### 6.4 プラットフォーム固有の落とし穴

Apple Silicon / MPS 環境と外部 API で、それぞれ実際に踏んだものを共有します。

**MPS：推論経路でだけ落ちる SDPA dropout**

```
NotImplementedError: scaled_dot_product_attention for MPS does not support dropout
```

`nn.TransformerEncoderLayer` の既定 dropout（0.1）を使うと、**`torch.no_grad()` 経路（推論）でのみ**この例外が出ます。学習時の勾配ありパスでは再現しません（SDPA のバックエンド選択が異なるため）。しかもこれは「未サポート演算の CPU フォールバック」ではなく明示的な非対応なので、`PYTORCH_ENABLE_MPS_FALLBACK=1` では救えません。学習が通ったから安心、とはならない典型例です。

**ffmpeg：リトライを置く場所を間違えると無意味になる**

高負荷下で `OSError: Could not load meta information` が頻発しました。`ffprobe` で確認するとファイル自体は正常なので、一時的な資源枯渇と判断してリトライを入れました——が、**再発しました**。

原因は、imageio-ffmpeg が **ffmpeg サブプロセスを `get_reader()` ではなく最初の `get_data()` で遅延初期化する**ことでした。`get_reader()` だけをリトライで包んでも、失敗するのはその後です。open + read + close の**一連の操作全体**を1つのリトライ単位にし直して解決しました。

このとき書いたテストが教訓を体現しています。最初のテストは `get_reader()` を失敗させるものだったので、**修正前のコードでも通ってしまっていました**。`get_data()` を失敗させるテストに書き直して初めて、バグを再現できました。

> 教訓：**リトライは「失敗する場所」に置く。** 遅延初期化するライブラリでは、API の見た目と実際の副作用発生点がずれます。そしてリトライのテストは、**修正前のコードで落ちること**を必ず確認する。

**外部 LLM API：モデル世代でパラメータ契約が変わる**

概念命名タスクで実 API を叩いた際、2つ連続で落ちました。

```
1. Unsupported parameter: 'max_tokens' is not supported with this model.
   Use 'max_completion_tokens' instead.
2. Unsupported value: 'temperature' does not support 0.0 with this model.
   Only the default (1) value is supported.
```

2番目が厄介です。JSON 厳格出力タスクでは温度0が定石ですが、推論系モデルは温度を固定しており、**指定すること自体がエラー**になります。「特定のエラーを検知したら temperature 無指定で1回だけ再試行する」という形に落としました。

なお、**モデル識別子は設定ファイルにのみ置き、コードには書かない**という規約が、この修正を局所化してくれました。加えて `gtwm llm ping` は「API キーの認証が通るか」しか確認せず**モデル名の実在は確認しない**ため、最小の実呼び出しで確かめる必要がありました。疎通確認と機能確認は別物です。

### 6.5 呼び出しごとの再学習は、桁で効く

EXP-11（非機能）の本実行が **11時間経っても 9/20 トライアル**しか進んでいませんでした。このペースだと完了まで70時間超です。

原因は単純でした。

```python
for i in range(n_trials):
    result = run_ground(episode_id, set_name, probe_config=probe_config)
    #                                          ↑ 毎回 α を6000ステップ再学習
```

`run_ground()` は `pretrained` を渡さなければプローブをフル学習し直します。20トライアル×3seed = 60回、毎回ゼロから学習していました。ループの外で1回学習して使い回すよう修正しています。

同型の問題は WHAT-IF エンジン（1回の呼び出しごとに6000ステップ再学習、3介入×3seed で9回）と概念発見ループにもありました。**3箇所で独立に同じパターンを踏んでいる**ということは、これは個別のミスではなく、`train_probes()` が「呼べば学習する」という API 設計であることに起因する構造的な誘因だと考えるべきでしょう。

> 教訓：**「重い初期化を隠した便利関数」は、ループの中で呼ばれた瞬間に事故ります。** キャッシュ可能な引数（`pretrained=`）を用意するだけでなく、それが**既定で効く**設計にするか、少なくとも呼び出し側が気付けるログを出すべきでした。

### 6.6 並列実行は「見えないところ」で壊れる

11実験を1台の MacBook で並列実行した結果、ロードアベレージが13〜22（コア数を大きく超過）に達し、以下が起きました。

- 実験1本あたりの所要時間が数倍に伸び、見積もりが崩壊
- ffmpeg サブプロセスの起動が一時的に失敗（前述）
- バックグラウンドジョブが `Error 143`（SIGTERM）で静かに死ぬケースが頻発
- 同一実験が二重起動し、無駄な API 課金が発生

さらに、**同じマシンで動いていた無関係のプロセス**も競合していました。他プロセスがアイドルになった瞬間、ロードアベレージは8台まで下がりました。単独マシンでの並列実験は、思ったよりずっと早く飽和します。

長時間ジョブの起動は、最終的に「`nohup` ＋ `disown` ＋ 直接 python 呼び出し（Makefile 経由を避ける）」に落ち着きました。プロセスグループとシグナルの扱いが、ツール経由だと制御しきれなかったためです。

## 9. まとめ

「世界モデル × オントロジー」の二層ツインは、**アーキテクチャとしては期待通りに機能しました**。継続体と生起体の役割分担は破綻せず、接地層という結節点に問題を局所化できました。実際、本記事で挙げた不具合のほとんどは「接地層のどの経路が死んでいるか」という形で切り分けられています。これは、層の切り方が正しかったことの傍証だと考えています。

一方で、**指標としての ε を実際に機能させるには、まだ距離があります**。定義は正しく、3分解という切り分けの枠組みも有用でしたが、実装が定義通りであることを保証するのは別の仕事でした。F^h が恒等写像だった件は、その最も明確な例です。

Physical AI のシステムでは、シミュレータ・学習器・記号推論・外部 API・データ基盤が長い鎖で繋がります。鎖のどこか1箇所が「エラーを出さずに何もしない」状態になったとき、パイプライン全体は**それらしい数値を出し続けます**。テストは緑のまま、指標は範囲内、レポートは自動生成される。

だからこそ、以下の3つを設計に埋め込む価値があると考えます。

1. **合格基準を先に固定し、コードから閾値を追い出す**（後から動かせなくする）
2. **盲検境界のような「守るべき性質」は、機械で強制する**（`test_blindness.py`）
3. **「差が出ないこと」を異常として扱う**（対照条件で完全一致したら、まず自分の実装を疑う）

3番目は特に、自動化されたエージェントに開発を任せる場合ほど重要になります。数値が出ること自体は簡単なのです。その数値が**不合格になり得る経路を持っているか**を問うこと——これが、検証を検証たらしめる最後の一線だと感じました。
