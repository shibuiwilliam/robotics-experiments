`experiments/criteria.yaml` の H5 と一致させること）。

## 検証仮説

H5（3.1）：オントロジー制約を計画のハード制約として保証できる。

## 段階

P0（P1は助言のみ）（3週）。

## 手順（6.2 転記）

P0の模擬AGVで、進入禁止ゾーン・危険物隣接・容量制約を含む100タスクを、シールド有／無で

## 対象と制約例（3.2 転記）

対象：AGV/フォークリフトの経路と一時置き場の選定（助言のみ、実行はしない）。P0の

隣接禁止、棚容量、賞味期限順（FEFO）。

## 出力（6.2 転記）

違反件数、タスク完了時間、経路長。P1では助言表示のみとし、オペレータの採否を記録。

- スループット低下 ≤ 5%

## Smoke モードでの簡略化（docs/status.md にも記載）

- poc_plan.md は「進入禁止ゾーン・危険物隣接・容量制約を含む100タスク」を要求するが、
  smoke では**進入禁止ゾーンのみ**（`gt:ZoneCapacityShape` を capacity=0 として解釈、
  `grounding/shield.RestrictedZoneShield`）を対象に**3タスク**で検証する
  （`experiments/EXP-06/config.yaml`）。危険物隣接・容量制約シールドへの拡張は本実行時に行う。
- シールドは 256 候補 × 20 ホライズンの pyshacl 検証を毎回実行する代わりに、
  `grounding/constraints.py` と同じ意味論（ゾーン所属確率＝違反度）を α のゾーン確率に
  直接適用する（`shield.py` の docstring 参照）。これは `gt:ZoneCapacityShape` の
  決定的チェックを連続値の予測確率に対して行う近似であり、本実行時に離散版の
  ダブルチェック（`KGStore.validate`）への拡張余地を残してある。
- 「タスク完了時間」「経路長」はいずれも smoke 規模の代理指標（実行コスト関数値、
  行動ベクトルのL2ノルム合計）であり、poc_plan.md が想定する実際の物理的完了時間・
  移動距離ではない（`exp06.py` のモジュール docstring 参照）。
- コスト関数に「禁止ゾーンを通過すると得になる」近道ボーナスを意図的に加えている。
  これがないと、そもそもシールド無しでも違反が発生せず、シールドの効果を検証できない
  （ハード制約とソフトなコスト誘因が対立する状況を作って初めて意味のある比較になる）。
- **smoke は参考値であり、合否判定には使わない**。本実行には poc_plan.md 6.2 通りの
  100タスク・危険物隣接／容量制約シールドへの拡張が必要（config.yaml の full_run 節参照）。

## smoke での実測（参考値）と発見した実バグ

既定の MPPI 設定（`noise_std=1.0`）では候補行動が小さすぎて smoke WM のゾーン予測を
ほとんど動かせず、シールド有無で結果が変わらなかった（`violations_with_shield` /
`violations_without_shield` が共に0）。探索幅と近道ボーナスを強めた設定
（`config.yaml`）に調整したところ、シールド無しでは3/3タスクが禁止ゾーンに違反する
一方、シールド有りでも当初1/3が違反する、という結果になった。

原因を調査した結果、`wm/planner.py MPPIPlanner.plan()` の一般的なバグを発見した：
シールドで棄却された候補はコストが `+inf` になり除外されるが、**受理された候補どうし
の重み付き平均（凸結合）自体がシールドを満たす保証はない**（`Probe.zone_probs` は
行動に対して非線形なので、2つの受理候補の中間の行動が、どちらの受理候補とも異なる
禁止ゾーン確率を持ちうる）。これを、平均後の行動を再検査し違反していれば単一の
最小コスト受理候補にフォールバックする「安全網」を `plan()` に追加して修正した
（`tests/unit/test_wm_planner.py` に非凸受理領域での最小再現テストを追加）。
修正後は smoke で `violations_with_shield=0`、`violations_without_shield=3`（3タスク中）
となった。`throughput_loss` は約1.42（142%）で目標の5%を大きく超えるが、これは
コスト関数に意図的に強い「禁止ゾーンへの近道ボーナス」を入れて対立状況を作った
ストレステスト設定によるもので、実際のタスクでの数値ではない（本実行時に現実的な
コスト関数で再測定する）。
